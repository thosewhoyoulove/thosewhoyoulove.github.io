# 中文技术文章自然润色

把“信息都在，但读起来像自动生成的提纲”改成能连续阅读、能理解、也能在面试中表达的技术文章。自然不等于删短：保留推导、例子和必要限制，删除没有解释作用的格式和套话。

## 先确定文章承担的任务

先阅读 `.cursor/rules/knowledge-base.mdc`、目标文章与它直接关联的深文或速记页。批量润色时先画清主题分工；本仓库不是顺序编排的技术书，不要按文件排序把无关文章当成前后章。

按页面用途选择编辑方式：

- **原理深文**：遵循仓库根目录下的 `.cursor/skills/knowledge-article-author/SKILL.md` 的结构。标题后首先是 `## 面试回答`，保留一句话总结、核心原理、常见误区、高频追问、延伸阅读。改善各节内部的叙述，不为减少 AI 味而删除面试入口。不新增“面试定位”。
- **面试速记与复习清单**：以检索、口述提示和跳转为主。保留必要的列表、优先级与问题，不把每项扩写成深文。
- **系列教程或源码讲解**：以一个具体问题串起每篇，检查关联篇目的重复。用户明确要求连续教程体时，按该要求安排结构，不强套面试深文模板。

局部措辞修改只处理目标段落；整篇或多篇重写再做结构调整。已有本地改动应先识别并保留，不覆盖与本次润色无关的内容。

动笔前明确：文章要回答什么、读者已经知道什么、哪个例子能暴露问题、哪些机制应回指其他文章。默认读者掌握 JavaScript 和常见前端 API，但未读过相关框架源码。

## 先核事实，再改表达

旧文是待核查材料，不是事实来源。涉及执行顺序、版本差异、数据结构和源码入口时，对照实际源码、测试或官方资料。

- 仓库中的示例代码与教学实现，只能证明该实现的行为。不要据此概括所有 React、Vue 或浏览器版本。
- 讲外部框架而本地没有对应源码时，核实官方文档或相应版本源码；记录核查版本。不要把知识库自身的依赖版本当成文章讨论的框架版本。
- 区分直觉模型、教学实现和生产实现；仅在读者可能错误外推的位置说明差异。
- 不凭印象补函数名、执行时机或 API 支持情况。无法验证时收窄结论，明确剩余不确定性。
- 改动可执行示例时，在对应运行环境验证关键结果；伪代码明确标识，不把简化实现描述成完整 polyfill。

必要时参照仓库根目录下的 `.cursor/skills/technical-accuracy-review/SKILL.md` 的相关领域检查，不把单纯润色扩大成全仓技术审计。

## 用因果组织正文

推荐从“可观察的现象 → 问题 → 最小例子 → 机制怎样运行 → 为什么这样设计”推进。这是推导顺序，不是每节必须复制的标题模板。

面试深文的口述入口保持在前；核心原理部分尽早给出具体矛盾，例如“调用 setState 后，为什么当前变量仍是旧值”。后续解释口述稿中的重要术语，避免先堆一页名词，再逐项下定义。

代码与解释相邻。说明输入或前提、关键判断与状态变化、最终结果，以及结果为什么出现。不逐行翻译语法；用一个可追踪的例子解释机制，复杂时再用树、队列或时间线呈现关系。

表格用于真正的横向比较；列表用于步骤、检索与并列信息。不要把整段推导拆成碎片，也不要把 Trace、流程图和比较表一律改成散文。标题数量由主题决定，不机械限制每篇只能有三个核心节。

## 让句子像人在解释

优先写具体主语和动作，用短句交代关键变化，稍长的句子解释因果。一段通常围绕一个问题展开，避免每句单独成段和连续相同句式。

例如：

```text
生硬：这里需要注意，当前仓库会在后续阶段完成文本更新的处理。
自然：Commit 读到 Update 标记后调用 commitTextUpdate，文本节点才发生变化。
```

示例中的函数名也必须与被讲解的实现吻合；没有源码依据时，用准确的机制描述。

审视“当前仓库”“这意味着”“因此”“这里需要注意”“边界”“一句话”“先看一个最小例子”等反复出现的表达。它们不是禁词，不做批量替换；检查是否可由具体事实直接承接。保留仓库要求的一句话总结，避免正文每节再重复一遍总结。

少用加粗代替推导，少写连续的“不要／不能”规则。常见误区仍可清楚对比错误与正确理解，但要解释错误为何发生。限制放在可能引发误解的位置，不在每段重复免责声明。

口述稿应能直接说出口。润色时保留「先报层面，再按首先 / 第二 / 第三讲，关键句加粗，机制名旁边写职责，结尾写不等于什么」。不要把这种回答压成没有层次的一段，也不要为了去掉函数名删掉已经解释过职责的名字。正文负责把口述稿讲透，不再复制另一套相同回答。

## 合并重复，保留阅读入口

同一机制选择最合适的深文完整解释，其他页面用一句必要背景和站内链接承接，再讲本页新增内容。例如 this 与 call/apply/bind 可互相回指；面向对象文章重点讲原型、new、继承与组合，无需复制整套绑定规则。

速记页保留足够独立回忆的短解释，不清空成纯链接列表。系列教程只在前文知识足够支撑时回指；不要让消除重复变成频繁跳页。

不额外添加正文目录、机械预告或每节固定的“总结／Q&A”。保留有实际用途的高频追问和复习清单。批量完成后连读关联文章，检查重复的例子、开头和结尾，以及回指之后是否仍能理解本段。

站内链接以 `docs/` 为根，使用 `/md/分类/文件.md`，路径空格写 `%20`。优先保留原文件名与标题锚点；需要改名或改标题时，检查所有引用。仅润色正文不改导航；新增、改名或调整导航时，参照仓库根目录下的 `.cursor/skills/docsify-knowledge-site/SKILL.md` 更新侧栏源数据并生成产物，不只手改 `_sidebar.md`。

## 校验与汇报

编辑完成后人工核查：核心问题是否清楚，例子是否能推导结果，口述与正文是否一致，跨文是否重复，事实及版本是否有依据，标题、代码围栏、链接与锚点是否有效。文本搜索可辅助发现套话和冲突标记，不能代替通读。

按仓库实际脚本检查，在仓库根目录执行：

```bash
git diff --check
npm --prefix docs run check
```

`check` 运行侧栏一致性与内容检查，不能证明事实正确或所有锚点有效。运行前重新确认 `docs/package.json` 脚本仍适用。导航有改动时先执行 `npm --prefix docs run generate-sidebar` 并审查差异。

Docsify 直接加载 Markdown，当前 `docs/package.json` 没有文档 build 脚本。需要页面验证时使用现有 `dev` 脚本预览并检查排版与链接；仓库根目录的 build 用于 interview-copilot，不能冒充文档构建。缺少依赖或检查失败时，区分环境问题、原有问题和本次引入的问题，不为通过检查扩大修改范围。

多篇大改且具备可用的独立审阅能力时，可安排独立审阅，重点检查阅读自然度和事实准确性；小范围编辑自行复核即可。未实际执行的验证不能写成通过。

汇报具体说明：修改了哪些文件、移除了哪些阅读障碍、合并了哪些跨文重复、修正了什么事实问题，以及实际运行的检查和结果。没有发现事实错误就如实说明，不用“出版级”“全面提升”等无法验证的评价。
