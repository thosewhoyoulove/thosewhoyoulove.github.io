# 防抖与节流

## 面试回答

> 防抖和节流都是用闭包保存定时器或时间戳，把高频触发的事件压成可控次数，避免主线程和接口被打爆。防抖的核心是「等停下来再执行」：每次触发都清掉上一次定时器，重新计时，只有安静一段时间后才跑回调，适合搜索联想、窗口 resize 结束后算布局、表单校验。节流的核心是「固定节奏至少执行一次」：在一个时间窗口内最多执行一次，适合 scroll 懒加载、拖拽跟手、按钮防连点里「每隔 N ms 仍要反馈」的场景。
>
> 实现上两者都依赖闭包：外层函数保存 `timer` 或 `last`，返回的内层函数才是真正绑到事件上的监听器。要注意 `this` 和参数：事件回调里要用 `apply`/`call` 把当前元素和 event 传进去；leading / trailing 决定窗口开始还是结束时触发。和 Vue / React 结合时，要在卸载时清掉定时器，否则组件销毁后回调还跑，可能 setState 到已卸载组件，或闭包拖住 DOM/状态造成泄漏。
>
> 选型上不是谁更高级：要的是最终结果用防抖，要的是过程采样用节流；有的场景还会组合，比如输入防抖请求、滚动节流算位置。

**一句话总结：**

> 闭包保存 timer/last → 防抖重置等待（停了再跑）→ 节流窗口限频（节奏执行）→ 绑事件时保住 this/参数 → 卸载清理。

## 核心原理

### 1. 为什么需要

浏览器事件可以极高频：`input`、`scroll`、`resize`、mousemove。若每次都：

- 打接口 / 算布局 / 同步大量 DOM

主线程会出现 Long Task，INP/滚动掉帧，后端也被刷爆。防抖节流是在**业务层**做频控，比指望浏览器自己节流更可控。

### 2. 整体链路

```text
用户高频操作
  → 监听器（内层函数）每次被调用
  → 闭包读/写 timer 或 lastTime
  → 决定：取消上次 / 跳过本次 / 执行回调
  → （可选）trailing 再补一次
  → 组件卸载：clearTimeout，断开引用
```

### 3. 防抖：停下来再执行

白话：电梯门——有人进就重新计时，没人一段时间才关。

```js
function debounce(fn, wait = 300) {
  let timer = null;
  return function (...args) {
    const ctx = this;
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(ctx, args);
    }, wait);
  };
}

// 搜索框：停输入 300ms 再请求
input.addEventListener("input", debounce(fetchSuggest, 300));
```

| 步骤 | timer | 行为 |
| --- | --- | --- |
| 第 1 次输入 | null → 新 timer | 预约 300ms 后请求 |
| 150ms 又输入 | clear 旧 → 新 timer | 重新预约 |
| 之后安静 ≥300ms | 到期执行 | 只打 1 次接口 |

`timer` 必须活在闭包里：每次事件触发的是**同一个**内层函数，才能清到上一次的预约。

### 4. 节流：固定节奏执行

白话：游戏技能 CD——CD 好了才能再放，中间按键无效（或排队到 CD 结束，看实现）。

时间戳版（leading，窗口开头立刻执行）：

```js
function throttle(fn, wait = 200) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= wait) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```

| 当前时间 | last | now - last | 结果 |
| ---: | ---: | ---: | --- |
| 0 | 0 | ≥ wait | 执行，last=0→0 实际记 now |
| 80 | 0 | 80 < 200 | 跳过 |
| 210 | 0 时刻 | ≥ 200 | 执行 |

定时器版更容易做 trailing（窗口结束再补一次）。面试说清一种完整实现 + 另一种思路即可。

### 5. 和 Vue / React 怎么用

- **React**：`useMemo(() => debounce(fn, 300), [])` 或 `useRef` 保存 debounce 实例，避免每次 render 新建导致防抖失效；`useEffect` cleanup 里 `cancel`。
- **Vue**：在 `onMounted` 创建，`onBeforeUnmount` 取消防抖；Composition 里用 `ref` 持有返回函数。
- **请求**：防抖后的请求要带过期标志或 AbortController，避免乱序返回覆盖新结果。

### 6. 设计取舍

| 场景 | 更合适 | 原因 |
| --- | --- | --- |
| 搜索联想、resize 后布局 | 防抖 | 只要最终态 |
| scroll 加载、进度跟手 | 节流 | 过程中持续采样 |
| 提交按钮 | 更常直接 disable / 锁 | 比纯节流语义更清晰 |
| 动画 | rAF | 跟帧，不是任意 ms |

## 常见误区

### ❌ 防抖和节流就是延时执行，没区别

### ✅ 更准确的说法

都是降频，但策略不同：防抖合并为「最后一次」，节流保证「间隔内最多一次」。

### 为什么？

面试官听完定义会追问场景选型；说不清就暴露只背过名词。

---

### ❌ 每次 render 都 `debounce(fn)` 包一层没问题

### ✅ 更准确的说法

每次新函数都有自己的闭包 timer，防抖状态被重置，等于没防抖。

### 为什么？

防抖依赖「同一个返回函数」持续接收事件。

---

### ❌ 只用防抖节流就够了，不用管卸载

### ✅ 更准确的说法

组件卸载必须 `clearTimeout`，并取消进行中的请求。

### 为什么？

否则回调可能在卸载后改状态，或闭包长时间占住大对象。

## 高频追问

### 防抖和节流的区别是什么？

防抖：连续触发只认最后一次安静后的执行。节流：固定时间窗口内最多执行一次。

### 为什么要实现里要用闭包？

需要跨多次事件调用共享 `timer` / `last`；闭包让内层函数一直访问外层变量。

### 如何保证回调里的 this 正确？

用 `fn.apply(this, args)` 把监听器被调用时的 this（通常是 DOM 元素）和参数传下去。

### leading / trailing 是什么？

leading：时间窗口开始立刻执行；trailing：窗口结束再执行。防抖默认偏 trailing；节流两种都常见。

### 和 requestAnimationFrame 怎么选？

跟屏幕刷新、做动画优先 rAF；跟业务时间（300ms 停输入）用防抖节流。

### 项目里怎么验证？

Performance 看 Long Task 是否下降；Network 看请求次数；React/Vue 里故意快速输入，确认只在预期时机打接口。
