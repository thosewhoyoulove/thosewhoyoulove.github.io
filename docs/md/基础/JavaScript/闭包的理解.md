# 闭包的理解

## 一句话理解闭包

函数创建时记住自己写在哪一层，所以外层函数执行完，它仍然能找到那一层里的变量。

---

## 面试回答

> 我理解闭包的核心是：函数能够访问它定义时所在作用域里的变量，即使这个函数要等外部函数执行完才被调用。
>
> 从原理上说，函数创建时会带上当时的词法环境。它换个地方执行，仍然沿着这个环境找变量，而不是看谁调用了它。外部函数执行完，调用栈上的那次执行没有了，但返回去的函数还在，它要用到的那些变量就不能被回收。现代引擎可以优化掉内部函数根本没读过的变量。
>
> 工作里我主要在三个地方用它。
>
> 第一个是把状态包在内部。比如做一个请求管理器，把当前的取消控制器和请求序号放在闭包里，外面只能调用发请求和取消，不能直接改这两个变量。用户连续发两次，后一次开始时打断前一次；前一次即使后返回，序号对不上，也不再写进界面。
>
> 第二个是按业务提前配好函数。不同产品线要带不同的业务标识，我用一个函数先收下这个标识，返回真正发请求的函数。调用的时候就不用每次再传一遍。
>
> 第三个是 React。函数组件每次渲染都会形成一份新的词法环境，事件回调、`useEffect`、定时器都是闭包。异步回调如果抓住的是上一次渲染里的 state，就会出现陈旧闭包。点击按钮把 count 加到 5，空依赖的定时器仍然一直打印 0，因为定时器还在读第一次渲染的那个 `count`。这不是闭包坏了，而是闭包正常工作，我们却以为旧函数会自动读到新一次渲染的变量。
>
> 所以闭包不只是语法。它管的是状态怎么藏起来、异步结果算不算数，以及 React 每次渲染的数据能不能对上。

## 闭包的底层原理

`createCounter()` 已经返回，为什么再调用还能累加？那次调用已经从调用栈上拿掉了。还在的是返回函数所记住的那一层变量。

函数能看见哪些名字，由它写在源码的哪一层决定，不由后来在哪里被调用决定。这就是词法作用域。

```javascript
const name = "global";

function outer() {
    const name = "outer";
    return function inner() {
        console.log(name);
    };
}

const fn = outer();
fn(); // "outer"
```

`inner` 写在 `outer` 里面，所以打印的是 `"outer"`，尽管调用发生在外面。

一次函数调用会创建执行上下文，并放进调用栈。这个上下文带着一份词法环境：里面记下这一层的变量，并链向外层。调用结束，执行上下文从栈上移除。

函数在创建时会记住当时这份词法环境。规范里这个关联叫内部槽 `[[Environment]]`，可以把它理解成「这个函数是在哪一层定义的」。内层函数被返回之后还有人拿着它，这份环境就还能被找到，垃圾回收就不会收走它还要用的变量。闭包就是函数加上它仍然拿着的这份环境。

```javascript
function createCounter() {
    let count = 0;
    return {
        inc() {
            count += 1;
        },
        get() {
            return count;
        },
    };
}

const counter = createCounter();
counter.inc();
console.log(counter.get()); // 1
```

`inc` 和 `get` 来自同一次 `createCounter()`，改的是同一个 `count`。再调用一次 `createCounter()`，是另一套变量，两份计数互不影响。所以闭包留的是变量本身，不是把当时的数字复印一份。若要留下当时的值，得先放进一个新变量，例如 `const snapshot = count`，回调只读 `snapshot`。

引擎可以不保留内部函数从未读过的变量。不能理解成外层所有局部变量都会整包留在内存里。

`var` 和 `let` 的循环差在绑定是不是同一份。`var` 的 `i` 是整个函数里的一个变量，三个定时器共享它，回调执行时循环已经把 `i` 改成 `3`：

```javascript
for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 0);
}
// 3 3 3
```

`for` 里的 `let` 每一轮都有自己的 `i`，每个回调抓住的是自己那一轮，所以是 `0 1 2`。

## 真实工程实践

防抖、节流、柯里化都能用闭包做，但那多半只说明语法会用。社招更有区分度的，是用闭包管住业务状态，并处理异步结果谁才算数。

### 把请求状态包在内部

用户连续发两条消息时，完成顺序不一定等于发送顺序。后发出的请求先回来，或者先发出的请求后回来，都可能把界面写成旧结果。

闭包可以留下两个只有内部能改的变量：当前这次请求的 `AbortController`，以及递增的请求序号。`AbortController` 负责取消上一次还在飞的请求，序号负责认出「这是不是最新一次」。它们不是一回事。

```javascript
function createRequestManager() {
    let currentController = null;
    let requestId = 0;

    async function run(url) {
        currentController?.abort();

        const controller = new AbortController();
        currentController = controller;
        const id = ++requestId;

        try {
            const response = await fetch(url, {
                signal: controller.signal,
            });
            if (!response.ok) {
                throw new Error(`HTTP ${response.status}`);
            }
            const result = await response.json();
            if (id !== requestId) return null;
            return result;
        } finally {
            if (id === requestId) currentController = null;
        }
    }

    return { run };
}
```

`currentController` 和 `requestId` 都在 `createRequestManager` 这一层里。`run` 返回之后仍然能读写它们。每调用一次 `createRequestManager()`，就有一套自己的控制器和序号，互不干扰。外面拿到的只有 `run`，改不了这两个变量。

取消发生在发起新请求的当时。序号判断发生在结果回来的时候：旧请求如果没被取消干净、仍然返回了，`id` 已经对不上，就不再把数据交给界面。`finally` 里只有「我还是最新一次」才把控制器清掉，避免旧请求结束时把新请求的控制器抹掉。

### 按业务提前配好函数

不同产品线访问同一个接口，要带的业务标识不一样。外层函数收下 `productType`，返回的函数一直带着它，调用时就不用再传。

```javascript
function createApiClient(productType) {
    return async function request(path) {
        const response = await fetch(path, {
            headers: {
                "Product-Type": productType,
            },
            credentials: "include",
        });
        if (!response.ok) {
            throw new Error("Request failed");
        }
        return response.json();
    };
}

const salesRequest = createApiClient("sales");
const crmRequest = createApiClient("crm");
```

`salesRequest` 和 `crmRequest` 各记住自己的 `productType`。这是把固定配置先注入进去，调用方只关心路径。

## React 中的闭包

函数组件每次渲染都会重新执行，这次渲染里的 `count` 是一个新变量。事件回调、`useEffect`、定时器抓住的是创建它们那一次渲染里的变量。

```jsx
function Counter() {
    const [count, setCount] = useState(0);

    useEffect(() => {
        const timer = setInterval(() => {
            console.log(count);
        }, 1000);
        return () => clearInterval(timer);
    }, []);

    return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}
```

按钮点 5 次，界面上的数字会变成 5，定时器却一直打印 `0`。

第一次渲染时 `count` 是 `0`。`useEffect` 的依赖是空数组，定时器只在这次提交后创建，清理函数只在卸载时执行。回调里的 `count` 就是第一次的那个变量。后面每次渲染都有新的 `count`，但旧定时器没有重建，仍然访问原来的变量。state 已经更新了，只是这个回调看不到。

React 的陈旧闭包不是闭包失效，而是闭包正常工作，我们却期望旧函数自动读到新一次渲染的变量。

如果定时器确实要读最新的数，有两种常见做法，看需求选。

依赖里写上 `count`，并在清理函数里清掉旧定时器。`count` 一变，旧定时器拆掉，新定时器抓住这一次渲染的 `count`。依赖怎么比较、清理什么时候跑，见 [Hooks](/md/框架/React/Hooks.md)。

不想因为 `count` 变化就反复拆建定时器，就用 `useRef` 保存最新值。定时器始终读这个对象上的 `current`，另一次 effect 在每次提交后把最新的 `count` 写进去。ref 跨渲染是同一个对象，所以空依赖的定时器也能读到后面的数。不要在渲染过程中写 `current`：还没提交的那次渲染可能被丢掉，写进去的会是没显示出来的值。

`setCount((c) => c + 1)` 只影响怎么写入。它用的是更新队列里的上一个值，不读取定时器闭包里的 `count`，所以解决不了 `console.log(count)` 一直是 `0`。

## 风险与误区

闭包是正常的语言机制，不是一用就会漏内存。只有那些会一直留着的回调、事件监听，还拿着已经不用的大对象或从页面上卸掉的 DOM，这些数据才会跟着留在内存里。把回调从监听列表里拿掉，后面没有别的地方再指着它，就可以回收。

```javascript
const listeners = new Set();

function watch(bigList, onChange) {
    const handler = () => onChange(bigList.length);
    listeners.add(handler);
    return () => listeners.delete(handler);
}
```

忘了调用返回的取消函数时，`listeners` 一直拿着 `handler`，`bigList` 也就一直在。

另一类问题是包得太宽。闭包能藏状态，前提是没有把内部对象交出去。方法如果把那个对象返回了，外面拿到引用就能改。为了「看起来私有」把整份 props 或一整张大列表关进回调，藏住的东西变多了，私有性却没有增加。运行时真正的私有字段是 `#`，那是对象自己的隐藏槽，不是闭包，见 [面向对象与原型](/md/基础/JavaScript/面向对象与原型.md)。

依赖写错时，旧函数会留得比预想更久。`useEffect` 或 `useCallback` 的依赖写成 `[]`，函数里却读了 `count`，这个函数就会一直是第一次渲染的那一版。`useCallback` 不会自动换掉闭包里的旧值，它只是在依赖没变时复用同一个函数。依赖漏了，它反倒帮你把旧函数留住。

函数套函数也不等于闭包。嵌套函数如果没有被带到外面，调用一结束就没人引用，那一层变量可以回收。闭包要的是：函数还在，并且还要找它定义时的那些变量。

## 面试官深挖

### 闭包为什么能访问外部函数的变量？

JavaScript 按书写位置决定能看见哪些变量。函数创建时带上那一层词法环境，执行时沿着这层往外找，不看调用它的位置。

继续追问的话：两个内部函数改的是不是同一份？同一次外层调用返回的是同一份。再调用一次外层函数，才是另一套。

### 外部函数执行完，里面的变量为什么还在？

执行完只说明这次调用从栈上移除了。返回的函数如果还被用着，它关联的那层环境就不能回收。内部函数没读过的变量，引擎可以优化掉。

### 闭包一定会造成内存泄漏吗？

不会。只有一直留着的回调或监听还拿着已经不用的大对象、DOM 节点，这些数据才会一直留在内存里。

### 循环里 `var` 和 `let` 为什么结果不同？

`var` 的循环变量通常是整个函数共用的一个。`let` 在 `for` 里每一轮有自己的变量，所以异步回调抓到的不是同一个。

### `useCallback` 能解决陈旧闭包吗？

不能自动解决。它只根据依赖决定要不要复用函数。依赖漏了，复用的就是那个抓着旧 state 的函数。

### 闭包里的变量是拷贝还是引用？

它保留的是继续访问那个变量的能力，不是复印当时的值。同一个变量后来被改了，闭包里能看见。React 不同渲染里的 state 是不同的变量，所以旧回调看不见新渲染里的那个。
