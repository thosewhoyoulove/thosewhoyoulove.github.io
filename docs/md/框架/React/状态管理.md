# React 状态管理

## 面试回答

> React 状态管理我先按作用域选工具，而不是先选库。组件内交互用 `useState`；局部复杂流转用 `useReducer`；兄弟共享先状态提升；主题、当前用户、locale 这类**低频、变更不频繁**的跨层数据用 Context 很合适。只有跨多页面、更新频繁、要中间件/持久化/时间旅行调试，或团队需要强约定时，再上 Redux、Zustand 这类外部 store。
>
> Redux 的核心是「单一数据源 + 纯函数更新」：UI 或副作用 `dispatch(action)` → reducer `(state, action) => newState` 算出新状态（强调不可变）→ store 通知订阅者 → 组件用 selector 取出切片再渲染。中间件（thunk/saga）处理异步。Zustand 更轻：一个 store 对象，直接 `set` 改状态，组件用 hook + selector 订阅；样板少，没有强制 action 类型，适合中小型全局状态。
>
> Context 不是不能传复杂数据，而是 **value 引用一变，所有 `useContext` 消费者都会重渲染**，没有像 Redux/Zustand 那样的默认细粒度 selector。所以复杂、高频的业务状态硬塞一个大 Context，容易整树跟着抖；可以拆多个 Context、拆 value、用 memo，但往往不如上一个带 selector 的 store 省心。

**一句话总结：**

> 作用域选型 → Context 适合低频跨层 → Redux=dispatch→reducer→订阅 → Zustand=store+selector 更轻 → 复杂高频别单靠大 Context。

## 核心原理

### 1. 为什么需要分层

全放组件内：跨层传参地狱。全放全局 store：简单表单也变间接。分层是为了**变更半径可控**。

### 2. 选型链路

```text
组件内部交互 → useState
复杂局部流程 → useReducer
兄弟共享 → 状态提升
低频跨层（主题/用户） → Context
跨页、高频、强规范、要中间件 → Redux / Zustand …
```

### 3. Redux 原理（最小模型）

```text
dispatch({ type, payload })
  → 中间件（可选，处理异步）
  → rootReducer(prevState, action) → nextState（新引用）
  → store 保存 nextState
  → 通知 listeners
  → 组件 selector(nextState) 若切片引用变了 → 重渲染
```

| 概念 | 白话 |
| --- | --- |
| store | 唯一状态树 |
| action | 描述「发生了什么」的普通对象 |
| reducer | 纯函数：旧状态 + action → 新状态 |
| 不可变 | 用新对象表达变更，便于浅比较和回溯 |
| 中间件 | 插在 dispatch 与 reducer 之间，做异步、日志 |

RTK（Redux Toolkit）用 Immer 写「可变风格」仍产出不可变更新，并简化 store/slice 样板，但数据流没变。

### 4. Zustand 和 Redux 差在哪

| 维度 | Redux | Zustand |
| --- | --- | --- |
| 更新入口 | 几乎总是 dispatch(action) | 直接 `set(partial)` / 自定义方法 |
| 样板 | 相对多（RTK 后好很多） | 很少 |
| 订阅 | `useSelector` / connect | hook + selector |
| 中间件/DevTools | 生态极强 | 有，但更轻 |
| 适合 | 大团队、复杂链路、强审计 | 中小型全局状态、快速接入 |

共同点：都靠 **selector** 做细粒度订阅，避免无关字段更新导致整页渲染。

### 5. Context 一般干什么？能不能传复杂数据？

**适合：**

- 主题、国际化、当前登录用户（变更少）
- 依赖注入（把 service/config 往下传）
- 和库配合：只把「稳定的 store API」放进 Context

**也能传复杂数据，但要接受机制：**

```text
Provider value 的引用变了
  → 所有 useContext(该 Context) 的消费者调度更新
  → 不像 Zustand 默认按 selector 结果比较
```

所以：

- 可以：拆 Context（theme / user 分开）、`useMemo` 稳住 value、消费者自己 memo。
- 高频大对象、列表筛选条件狂变：优先外部 store + selector，而不是一个巨型 Context。

**不是「Context 不能传复杂数据」，而是「复杂且高频时，默认重渲染粒度太粗」。**

### 6. 设计取舍

| 方案 | 优化目标 | 牺牲 |
| --- | --- | --- |
| 只用 Context | 零依赖 | 高频更新成本 |
| Zustand | 接入快、选择器 | 超大规范项目可能缺统一约束 |
| Redux | 可预测、工具链 | 心智与样板（RTK 缓解） |

## 常见误区

### ❌ 上了 React 就一定要 Redux

### ✅ 更准确的说法

多数中后台大量状态仍是页面/组件本地；全局库按痛点引入。

### 为什么？

过早全局化会增加跳转成本和心智负担。

---

### ❌ Context 性能差，绝不能传对象

### ✅ 更准确的说法

能传；怕的是高频变更 + 大范围消费者。低频复杂对象（如 user profile）完全可用。

### 为什么？

瓶颈在订阅粒度，不在「是不是对象」。

---

### ❌ Redux 和 Zustand 一个现代一个过时

### ✅ 更准确的说法

模型不同：规范流 vs 轻 store。看团队与复杂度。

## 高频追问

### Redux 原理一句话？

dispatch action，reducer 纯函数算新 state，订阅者按 selector 更新视图。

### 和 Zustand 区别？

Redux 强调 action/reducer 与中间件生态；Zustand API 更薄，直接 set + selector。

### Context 用来干什么？

跨层依赖注入和低频共享状态；不替代所有全局状态方案。

### 复杂数据能放 Context 吗？

能。高频更新时要拆分或换带 selector 的 store，否则易多余渲染。

### 什么时候上状态库？

跨路由共享、更新路径复杂、要持久化/调试/中间件，或 Context 优化成本已经高于引入库。
