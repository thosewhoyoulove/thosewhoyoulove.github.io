# React 状态管理

## 面试回答

> 状态管理我先按**变更半径**选方案，而不是先选库。组件内交互用 `useState`；局部多字段联动用 `useReducer`；兄弟间先状态提升；主题、当前用户、locale 这类低频跨层数据，Context 很合适。只有跨多路由、更新频繁、要中间件 / 持久化 / 强约定或时间旅行调试时，再上 Redux、Zustand 这类外部 store。
>
> 选型前还要先分状态类型：服务端数据更适合交给请求缓存层管理，因为它涉及缓存、失效、去重和重新验证；URL 中可表达的筛选、分页应尽量进 URL；表单草稿优先留在表单或页面内。不要因为多个地方“可能会用”就提前塞进全局 store，也不要在 store 里复制一份能从现有状态推导出的数据。
>
> Redux 的骨架是单一数据源 + 纯函数更新：`dispatch(action)` → reducer 得到新 state → 订阅者按 selector 取切片再渲染；异步与服务能力通常由中间件或 RTK Query 等工具承接。Zustand 更薄：store 上 `set`，组件通过 hook + selector 订阅。两者不只是 API 厚薄不同，更要看团队是否需要明确事件、可追踪数据流和统一约束。
>
> Context 解决的是跨层传值，不等于完整状态库。Provider 的 `value` 变化时，读取该 Context 的消费者会更新；`memo` 不能阻止消费者接收新的 Context。低频配置很适合 Context，高频复杂状态则要拆 Context，或使用支持 selector 的外部 store。外部 store 接入并发 React 时，还要保证订阅与快照一致，React 提供的标准接口是 `useSyncExternalStore`。

**一句话总结：**

> 先分本地状态、URL 状态、服务端缓存和客户端共享状态 → 保持单一数据源、避免冗余 → 再按作用域、频率、订阅粒度和团队约束选择 Context、Redux 或 Zustand。

## 核心原理

### 1. 为什么需要分层

| 极端 | 问题 |
| --- | --- |
| 全放组件内 | props 层层钻，跨页无法共享 |
| 全放全局 store | 简单表单也间接，改一个开关要翻 action |

目标是：**谁变、谁知道、重渲染半径多大**可控。

---

### 2. 选型链路

```text
组件内部 UI 状态 → useState
局部复杂流转 → useReducer
兄弟共享 → 状态提升
低频跨层（主题/用户/locale） → Context
跨页 / 高频 / 中间件 / 强规范 → Redux 或 Zustand
```

#### 先判断它是哪类状态

| 类型 | 例子 | 优先归属 |
| --- | --- | --- |
| 本地 UI 状态 | 弹窗、展开、当前 tab | 最近的组件或页面 |
| 表单草稿 | 输入值、校验、dirty | 表单边界内 |
| URL 状态 | 搜索词、分页、可分享筛选 | 路由 query/path |
| 服务端状态 | 列表、详情、缓存、重新验证 | 请求缓存层，而非手写全局副本 |
| 客户端共享状态 | 跨页面流程、购物车、编辑器会话 | Context / 外部 store |

状态结构同样重要：关联字段一起变化时考虑合并；避免互相矛盾、重复和可推导状态；深层嵌套数据尽量规范化或扁平化。很多“需要 Redux”的问题，实际先是状态建模出了问题。

---

### 3. Redux 最小模型

```text
dispatch(action)
  → 中间件（可选：异步、日志）
  → reducer(prev, action) → nextState（新引用）
  → store 保存
  → 通知订阅者
  → selector(next) 切片引用变化 → 组件重渲染
```

| 概念 | 白话 |
| --- | --- |
| store | 唯一状态树 |
| action | 描述发生了什么 |
| reducer | 纯函数算下一份 state |
| 不可变 | 用新引用表达变更，便于浅比较 |
| 中间件 | 插在 dispatch 与 reducer 之间 |

RTK 用 Immer 写「可变风格」仍产出不可变数据，并减样板，**数据流没变**。

---

### 4. Zustand 与 Redux

| 维度 | Redux | Zustand |
| --- | --- | --- |
| 入口 | 几乎总是 dispatch | `set` / 自定义方法 |
| 样板 | RTK 后可接受 | 很少 |
| 订阅 | `useSelector` 等 | hook + selector |
| 适合 | 大团队、复杂链路、审计 | 中小全局状态、快速接入 |

共同点：靠 selector 控制渲染粒度。

---

### 5. Context：适合什么，卡在哪

**适合：** 主题、i18n、当前用户、把稳定 API / config 注入子树。

**机制 Trace：**

```text
Provider value 换成新引用
  → 所有 useContext(该 Context) 的消费者调度更新
  → 即使子树只用到 value.theme，也会因「Context 变了」而渲染
```

| 做法 | 效果 |
| --- | --- |
| 拆多个 Context | 缩小订阅面 |
| `useMemo` 稳定 value | 减少无意义通知 |
| 外部 store + Context 只传 API | 消费走 selector |

结论：不是「Context 不能传对象」，而是「高频大范围时默认粒度太粗」。

`React.memo` 只能减少相同 props 导致的父子重渲染，不能阻止组件收到它正在读取的新 Context。要缩小范围，需要拆分 Provider/Context、稳定无关 value，或者让消费者通过 selector 订阅外部 store。

---

### 6. 外部 Store、selector 与并发一致性

外部 store 的基本链路是：

```text
组件读取 selector(store snapshot)
  → store 更新并通知订阅者
  → React 再读取 snapshot
  → 选中切片发生变化才重新渲染
```

selector 的价值是控制订阅粒度，但它依赖稳定的比较语义：不可变更新让引用比较有意义；返回新对象时可能需要 shallow equality 或稳定派生结果。

并发 Render 下，React 可能在不同时间读取外部数据。如果订阅和快照读取没有统一协议，可能出现 tearing——同一屏的不同组件看到不同版本。`useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)` 是 React 为外部 store 提供的标准桥接接口；成熟状态库通常会在内部处理这一层。

---

### 7. 设计取舍

| 方案 | 优化目标 | 牺牲 |
| --- | --- | --- |
| 只用 Context | 零额外库 | 高频更新成本 |
| Zustand | 接入快 | 超大规范项目可能缺统一约束 |
| Redux | 可预测、工具链 | 心智与组织成本（RTK 缓解） |

## 常见误区

### ❌ 上了 React 就一定要 Redux

### ✅ 更准确的说法

多数状态仍是页面 / 组件本地；全局库按痛点引入。

### 为什么？

过早全局化增加跳转与心智成本。

---

### ❌ Context 性能差，绝不能传对象

### ✅ 更准确的说法

能传；怕的是高频变更 + 大范围消费者。

### 为什么？

瓶颈在订阅粒度，不在「是不是对象」。

---

### ❌ Redux 过时、Zustand 才现代

### ✅ 更准确的说法

规范流 vs 轻 store，按团队与复杂度选。

### 为什么？

工具新旧不是架构理由。

---

### ❌ 有了状态库就不需要理解 React 自己的更新

### ✅ 更准确的说法

库最终仍驱动组件 render；selector 与不可变更新仍建立在 React 渲染模型上。

### 为什么？

状态库题常会拐回渲染原理。

## 高频追问

### 怎么选状态方案？

先作用域与变更频率，再问要不要中间件 / 持久化 / 强约定；最后才选库。

### Redux 原理一句话？

dispatch → reducer 纯函数出新 state → selector 订阅切片更新视图。

### Zustand 和 Redux 核心差？

API 厚度与是否强制 action/reducer；订阅优化思路相近。

### Context 能放复杂业务状态吗？

能。高频时要拆分或换带 selector 的 store，否则易多余渲染。

### 什么时候上状态库？

跨路由共享、更新路径复杂、要持久化/调试/中间件，或 Context 优化成本已高于引库。

### selector 为什么重要？

把「store 变了」变成「我关心的切片变了才渲染」，这是全局方案能用的关键。

### 服务端数据要不要放 Redux/Zustand？

可以，但不要只把请求结果复制进 store。服务端状态还有缓存键、过期、去重、重试和重新验证语义，通常优先使用 RTK Query、TanStack Query 或框架数据层；只有确实需要与客户端工作流统一时再整合。

### `useSyncExternalStore` 解决什么？

它规范 React 读取外部 store 快照和订阅变化的方式，让并发渲染及 SSR 场景下的数据观察保持一致，避免 tearing。
