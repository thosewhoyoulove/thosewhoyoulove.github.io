# React 组件设计能力

## 面试回答

> 我设计 React 组件会先分清通用组件和业务组件。通用组件盯 API 稳定、受控/非受控、可组合、样式扩展、无障碍和 loading/empty/error 等边界；业务组件盯流程清晰、状态放对层级、副作用隔离、可测。
>
> 状态只把「本地交互」留在组件内，跨组件先提升，再跨页才考虑 store。复用优先组合：`children`、compound components、自定义 Hooks；能 Hook 解决的逻辑不先上多层 HOC。性能上不默认包 `memo`，先看是不是状态放太高、props 每轮新引用；确认无效渲染后再 `memo` / 稳定回调 / 状态下沉。好组件的标准是：职责单一、状态归属清楚、API 可组合、边界完整、以后加需求不用拆开重写。

**一句话总结：**

> 职责与状态归属 → API 可组合 → 边界状态完整 → 组合优于层层 HOC → 测量后再 memo。

## 核心原理

### 1. 为什么面试官问组件设计

这题验证的不是「会不会写 JSX」，而是：

```text
边界清不清
  → 状态谁拥有
  → 变化半径多大
  → 复用方式会不会把人绕进 props 迷宫
```

---

### 2. 设计主链路

```text
分清通用 / 业务
  → 定职责（一个组件一类问题）
  → 定状态归属（本地 / 提升 / store）
  → 定 API（受控与否、扩展点）
  → 补边界状态与 a11y
  → 有真实复用场景再抽象
  → 有性能证据再优化
```

| 维度 | 要点 |
| --- | --- |
| 职责边界 | 一个组件一类问题 |
| 状态归属 | 谁拥有，谁更新，谁只读 |
| API | 命名稳定，少暴露内部结构 |
| 可组合 | children、插槽式 props、compound、自定义 Hook |
| 边界 | loading / empty / error / disabled / readonly |
| 无障碍 | 键盘、语义、aria |
| 性能 | 先结构，后 memo |

---

### 3. 受控 vs 非受控

| | 受控 | 非受控 |
| --- | --- | --- |
| 值在哪 | 父组件 state | 组件内部 / DOM |
| 适合 | 校验、联动、外部驱动 | 简单表单、只要最终值 |
| 通用组件 | 常同时支持 `value` + `defaultValue` | |

因果：表单要和外部世界同步时，受控更可预测；只是「内部暂存」时非受控更简单。

---

### 4. 复用：Hook / 组合 / HOC

| 方式 | 解决什么 | 代价 |
| --- | --- | --- |
| 自定义 Hook | 状态 + 副作用逻辑复用 | 不负责 UI 结构 |
| children / compound | UI 结构灵活组合 | API 要设计好上下文 |
| HOC | 整树包裹（鉴权壳、埋点壳） | 嵌套、props 来源不清、ref 要转发 |

```jsx
function withAuth(Wrapped) {
  return function AuthGuard(props) {
    const user = useUser()
    if (!user) return <Login />
    return <Wrapped {...props} user={user} />
  }
}
```

优先 Hook；需要「包住一整棵子树」时再用一层清晰的包裹 / HOC，避免叠罗汉。

---

### 5. 何时抽象、何时 memo

抽象：出现第二、第三个真实场景再抽；不要为假想需求加十个 props。

性能：

```text
先问：状态是否太高？列表是否整表渲染？
  → 再问：是否每轮新对象/新函数打穿子组件？
  → 最后才 React.memo / useMemo / useCallback
```

---

### 6. 设计取舍

| 选择 | 得到 | 风险 |
| --- | --- | --- |
| 高度可配置 props | 一时灵活 | API 膨胀、难测 |
| 组合 + 小组件 | 扩展点干净 | 文件变多，需目录约定 |
| 过早 memo | 心理安慰 | 代码噪、比较成本 |

## 常见误区

### ❌ 组件越多、props 越全越好

### ✅ 更准确的说法

职责清晰、扩展点稳定即可；为假想需求加开关是过度设计。

### 为什么？

可维护性比「全能组件」更重要。

---

### ❌ 逻辑复用就上 HOC

### ✅ 更准确的说法

多数逻辑复用用自定义 Hook；HOC 留给整树包裹场景。

### 为什么？

Hooks 后 HOC 的主战场变窄了。

---

### ❌ 先 memo 再谈结构

### ✅ 更准确的说法

先状态下沉与拆分渲染范围，再针对性 memo。

### 为什么？

memo 治不好状态放错层。

---

### ❌ 业务组件和通用组件用同一套标准

### ✅ 更准确的说法

通用组件更抠 API / a11y / 边界；业务组件更抠流程与状态归属。

### 为什么？

评价维度不同，混为一谈会答得很空。

## 高频追问

### 受控和非受控怎么选？

要外部校验/联动 → 受控；内部暂存、外部只要最终值 → 非受控；库组件常两者都支持。

### 什么时候抽自定义 Hook？

有状态或副作用、能与 UI 分离、且至少两处真实复用时。不为三行代码强行抽象。

### 怎么避免过度设计？

先打穿当前场景；第二、三个场景出现再抽扩展点。

### HOC 现在还用吗？

用，但更少。优先 Hook；鉴权壳、错误边界外观等包裹场景仍常见。

### 如何定位组件重渲染问题？

先看状态位置与 props 是否稳定，再用 profiler / why-did-you-render 类工具验证，最后才加 memo。

### 通用组件 API 有什么原则？

少而稳、命名接近领域、默认行为安全、进阶能力可选，不把内部 DOM 结构泄漏成必须依赖。
