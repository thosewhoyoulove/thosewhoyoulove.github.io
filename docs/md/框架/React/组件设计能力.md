# React 组件设计能力

## 面试回答

> 我设计 React 组件会先分清通用组件和业务组件。通用组件盯 API 稳定、受控/非受控、可组合、样式扩展、无障碍和 loading/empty/error 等边界；业务组件盯流程清晰、状态放对层级、副作用隔离、可测。
>
> 设计顺序通常是先定义组件承担什么职责、哪些状态合法，再决定状态由谁拥有。复杂交互不要堆多个可能互相矛盾的 boolean，而应建模成明确状态，例如 `idle | loading | success | error`。能从 props 和 state 推导出的值不重复存；共享状态放到最近公共祖先，跨区域再考虑 Context 或 store。
>
> 通用组件的 API 应表达业务语义，而不是泄漏内部 DOM。需要父组件完全驱动时用受控模式；只需要初始值和最终结果时可用非受控模式。若同时支持 `value` 和 `defaultValue`，要明确单一数据源，避免运行过程中在受控与非受控之间切换。扩展优先使用组合、`children`、明确的 slot props 或 compound components，而不是不断增加布尔开关。
>
> 逻辑复用优先自定义 Hook，结构复用优先组合；HOC 留给确实需要包装组件能力的场景。性能上先缩小状态和 Render 范围，再用 Profiler 找证据，最后才考虑 `memo`、稳定引用和列表虚拟化。一个成熟组件不仅要跑通正常路径，还要覆盖 loading、empty、error、disabled、键盘操作、焦点管理以及异步竞态，并提供稳定、可测试的契约。

**一句话总结：**

> 定职责与合法状态 → 确认状态归属和单一数据源 → 设计受控/非受控 API 与组合扩展点 → 补齐异常、无障碍和异步边界 → 测量后优化。

## 核心原理

### 1. 为什么面试官问组件设计

这题验证的不是「会不会写 JSX」，而是：

```text
边界清不清
  → 状态谁拥有
  → 变化半径多大
  → 复用方式会不会把人绕进 props 迷宫
```

---

### 2. 设计主链路

```text
分清通用 / 业务
  → 定职责（一个组件一类问题）
  → 定状态归属（本地 / 提升 / store）
  → 定 API（受控与否、扩展点）
  → 补边界状态与 a11y
  → 有真实复用场景再抽象
  → 有性能证据再优化
```

| 维度 | 要点 |
| --- | --- |
| 职责边界 | 一个组件一类问题 |
| 状态归属 | 谁拥有，谁更新，谁只读 |
| API | 命名稳定，少暴露内部结构 |
| 可组合 | children、插槽式 props、compound、自定义 Hook |
| 边界 | loading / empty / error / disabled / readonly |
| 无障碍 | 键盘、语义、aria |
| 性能 | 先结构，后 memo |

#### 先设计状态，而不是先写 JSX

```text
用户能触发哪些事件
  → 组件有哪些合法状态
  → 哪些状态之间允许转换
  → 哪些值可以由现有数据推导
  → 状态应该由谁拥有
```

例如请求组件如果同时维护 `isLoading`、`isError`、`hasData`，就可能出现三个值互相矛盾。使用 `status: 'idle' | 'loading' | 'success' | 'error'`，或用 reducer 表达事件与转换，能直接排除非法状态。

---

### 3. 受控 vs 非受控

| | 受控 | 非受控 |
| --- | --- | --- |
| 值在哪 | 父组件 state | 组件内部 / DOM |
| 适合 | 校验、联动、外部驱动 | 简单表单、只要最终值 |
| 通用组件 | 常同时支持 `value` + `defaultValue` | |

因果：表单要和外部世界同步时，受控更可预测；只是「内部暂存」时非受控更简单。

同时支持两种模式时，应在首次 Render 确定数据源：

```jsx
function Input({ value, defaultValue, onChange }) {
  const isControlled = value !== undefined
  // 受控：展示 value，变更只通知 onChange
  // 非受控：内部保存由 defaultValue 初始化的值
}
```

`defaultValue` 只表示初始值，不应该在之后被当成持续受控值。组件也不应在生命周期中随意从非受控切到受控，否则状态来源会变得不确定。

---

### 4. 复用：Hook / 组合 / HOC

| 方式 | 解决什么 | 代价 |
| --- | --- | --- |
| 自定义 Hook | 状态 + 副作用逻辑复用 | 不负责 UI 结构 |
| children / compound | UI 结构灵活组合 | API 要设计好上下文 |
| HOC | 整树包裹（鉴权壳、埋点壳） | 嵌套、props 来源不清、ref 要转发 |

```jsx
function withAuth(Wrapped) {
  return function AuthGuard(props) {
    const user = useUser()
    if (!user) return <Login />
    return <Wrapped {...props} user={user} />
  }
}
```

优先 Hook；需要「包住一整棵子树」时再用一层清晰的包裹 / HOC，避免叠罗汉。

#### 组件 API：语义优于开关数量

```jsx
// ❌ 布尔组合会快速膨胀
<Dialog compact noHeader renderFooter dangerMode />

// ✅ 用组合暴露稳定结构
<Dialog>
  <Dialog.Header>删除项目</Dialog.Header>
  <Dialog.Body>此操作无法撤销</Dialog.Body>
  <Dialog.Footer><DeleteButton /></Dialog.Footer>
</Dialog>
```

Compound Components 适合结构稳定、内容需要组合的组件，但通常依赖 Context 协调内部状态。slot/render props 适合把某个局部渲染权交给调用方。不要为了“灵活”同时提供多个互相重叠的扩展入口。

---

### 5. 异步、错误与无障碍边界

一个可复用组件至少要回答：

| 边界 | 需要考虑 |
| --- | --- |
| 异步 | 重复提交、取消、旧响应覆盖新响应、卸载后回调 |
| 错误 | 局部错误 UI、重试入口；Render 错误由 Error Boundary 承接 |
| 空状态 | 无数据和加载中不是同一状态 |
| 可访问性 | 语义元素、键盘操作、焦点进入/归还、label/aria |
| Escape hatch | 必要时通过 ref 暴露少量命令式能力，不暴露整个内部实现 |

Error Boundary 能捕获后代在 Render、生命周期及构造过程中的错误，但不能替代事件处理和普通异步流程中的 `try/catch`。函数组件可以作为其子节点，但传统自定义 Error Boundary 本身通常仍由类组件实现，或直接使用框架提供的错误边界。

---

### 6. 何时抽象、何时 memo

抽象：出现第二、第三个真实场景再抽；不要为假想需求加十个 props。

性能：

```text
先问：状态是否太高？列表是否整表渲染？
  → 再问：是否每轮新对象/新函数打穿子组件？
  → 最后才 React.memo / useMemo / useCallback
```

---

### 7. 设计取舍

| 选择 | 得到 | 风险 |
| --- | --- | --- |
| 高度可配置 props | 一时灵活 | API 膨胀、难测 |
| 组合 + 小组件 | 扩展点干净 | 文件变多，需目录约定 |
| 过早 memo | 心理安慰 | 代码噪、比较成本 |

## 常见误区

### ❌ 组件越多、props 越全越好

### ✅ 更准确的说法

职责清晰、扩展点稳定即可；为假想需求加开关是过度设计。

### 为什么？

可维护性比「全能组件」更重要。

---

### ❌ 逻辑复用就上 HOC

### ✅ 更准确的说法

多数逻辑复用用自定义 Hook；HOC 留给整树包裹场景。

### 为什么？

Hooks 后 HOC 的主战场变窄了。

---

### ❌ 先 memo 再谈结构

### ✅ 更准确的说法

先状态下沉与拆分渲染范围，再针对性 memo。

### 为什么？

memo 治不好状态放错层。

---

### ❌ 业务组件和通用组件用同一套标准

### ✅ 更准确的说法

通用组件更抠 API / a11y / 边界；业务组件更抠流程与状态归属。

### 为什么？

评价维度不同，混为一谈会答得很空。

## 高频追问

### 受控和非受控怎么选？

要外部校验/联动 → 受控；内部暂存、外部只要最终值 → 非受控；库组件常两者都支持。

### 什么时候抽自定义 Hook？

有状态或副作用、能与 UI 分离、且至少两处真实复用时。不为三行代码强行抽象。

### 怎么避免过度设计？

先打穿当前场景；第二、三个场景出现再抽扩展点。

### HOC 现在还用吗？

用，但更少。优先 Hook；鉴权壳、错误边界外观等包裹场景仍常见。

### 如何定位组件重渲染问题？

先看状态位置与 props 是否稳定，再用 profiler / why-did-you-render 类工具验证，最后才加 memo。

### 通用组件 API 有什么原则？

少而稳、命名接近领域、默认行为安全、进阶能力可选，不把内部 DOM 结构泄漏成必须依赖。

### 多个 boolean 状态有什么问题？

它们容易组合出业务上不可能的状态。先列合法状态和事件，互斥状态用枚举或 reducer 建模，可推导值不要重复存。

### Error Boundary 能捕获哪些错误？

主要捕获后代 Render、构造和生命周期中的错误；不会自动捕获事件处理器、任意异步回调、服务端渲染或边界自身抛出的错误，这些场景需要各自处理。
