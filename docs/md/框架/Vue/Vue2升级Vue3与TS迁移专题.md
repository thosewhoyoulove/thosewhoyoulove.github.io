# Vue 2 升级 Vue 3 与 JS→TS 迁移专题

## 面试定位

加分项常写成「中大型项目 Vue 2 → Vue 3」「JavaScript → TypeScript」。面试官真正听的不是「我升过」，而是：

1. **为什么升**（痛点，不是追新）。
2. **怎么控风险**（分阶段、兼容层、回归、回滚）。
3. **踩过哪些坑、如何验证收益**。
4. **TS 怎么渐进引入**，而不是「全仓一夜改完」。

仓库里已有原理文与项目案例：差异看 [Vue 2 和 Vue 3 区别](/md/框架/Vue/vue2和3的区别.md)，项目叙事看 [项目架构的整体升级方案](/md/面试准备/项目与架构/项目架构的整体升级方案.md)，compat 细节看 [Vue 兼容包的作用](/md/面试准备/技术/vue兼容包的作用.md)。**本文是面试口述专题**：帮你把做过但不算极熟的经历，讲成有结构、有边界、经得起追问的答案。

## 面试回答

可以这样答（约 60～90 秒，按你真实项目改数字与库名）：

> 我参与过中大型业务从 Vue 2 升到 Vue 3，同时推进 JS 向 TypeScript 的渐进迁移。升级动机不是追版本，而是开发体验、生态维护、复杂组件可维护性和类型安全几块痛点叠在一起。策略上我坚持分阶段：先稳住构建与依赖清单，再用 `@vue/compat` 把运行时切到 Vue 3 生态并收集 deprecation warning，然后按模块清兼容、升 router/store/UI 库，新代码用 Composition API，老代码不搞 Big Bang。JS 迁 TS 也是渐进的：先 `allowJs`、公共类型与接口层先行，再按页面/模块打开 `checkJs` 或改 `.ts/.vue`，用类型错误当迁移地图而不是一次性堵死开发。验证上靠核心路径回归、兼容警告清零节奏、以及启动/构建或缺陷类指标。我清楚自己不是把每个底层实现都啃透，但迁移链路、风险点和回滚意识是清楚的，遇到第三方断更会走平替、局部隔离或 patch，而不是硬升拖垮业务。

一句话总结：

> 升级成功 = 分阶段降风险 + compat 过渡 + 破坏点清单回归 + TS 渐进铺开；收益要用指标说。

## 核心原理

把升级看成「换底座，业务不停」：

```text
盘点痛点与依赖
  → 定阶段与回滚点
  →（可选）先稳构建工具
  → Vue3 + @vue/compat 跑通
  → 清 warning / 升生态
  → 去 compat，新代码 Composition
  → JS→TS 并行渐进
  → 指标验证 & 文档沉淀
```

和「只会背 Vue2 vs Vue3 差异」的区别：差异是知识，**迁移是工程风险管理**。

## 1. 面试怎么立住「我升过，但不装专家」

诚实且有底气的说法：

| 可以说 | 别硬撑 |
| --- | --- |
| 我负责/参与过哪些模块、哪些阶段 | 「全公司升级都是我一个人设计的」却答不出阶段 |
| 我清楚破坏性变更清单和回归重点 | 背不出 Proxy 实现细节就硬讲源码 |
| 我用 compat warning 当待办列表 | 声称「一天升完毫无兼容问题」 |
| 这个点我当时是查文档/和同事一起定的 | 把没做过的微前端隔离讲成亲历细节 |

追问到不会时的标准接法：

> 这个点我当时没有沉到源码层，我的抓手是官方迁移指南和 compat 警告。现场若再做，我会先用最小复现确认是框架行为还是业务用法，再决定改业务还是换依赖。

**要点**：加分来自**方法论与结果**，不是假装全知。

## 2. 推荐分阶段策略（口述主轴）

### 阶段 A：评估与清单

- 业务是否还要在 Vue 2 上活 1 年以上？生态是否已停更？
- 依赖表：`vue-router` / `vuex` / UI 库 / 图表 / 编辑器 / 内部组件库。
- 标出「无 Vue3 版」依赖 → 提前定平替 / 隔离 / 暂缓。

### 阶段 B：运行时切换（compat）

```text
安装 Vue 3 生态
  → alias vue -> @vue/compat
  → 打开迁移构建，跑起来
  → 按 warning 建看板（生命周期 / filters / EventBus / v-model …）
```

目标：**功能可用**，不是代码优雅。

### 阶段 C：清兼容与生态升级

| 类别 | 常见动作 |
| --- | --- |
| 路由 | vue-router 3 → 4，守卫与 `this` 差异 |
| 状态 | vuex 3 → 4，新模块倾向 Pinia |
| UI | Element UI → Element Plus（或你们实际库） |
| 全局 | `Vue.prototype` → `app.config.globalProperties` |
| 事件总线 | `$on/$off` → mitt / 显式 store |
| 指令 | 钩子名对齐生命周期 |

### 阶段 D：去 compat + 代码形态

- 新功能：`<script setup>` + Composition。
- 老模块：改到哪、稳到哪；复杂页单独排期。
- compat 配置从全局兼容收到特性级，最终删除。

### 为何不「一步到位」

同时换构建工具 + 框架 + TS + UI 库，故障无法归因。面试里强调：**一步一个验证目标**。完整项目拆法可对标 [项目架构的整体升级方案](/md/面试准备/项目与架构/项目架构的整体升级方案.md)。

## 3. 破坏性变更速记表（高频追问弹药）

| 点 | Vue 2 | Vue 3 迁移动作 |
| --- | --- | --- |
| 入口 | `new Vue` | `createApp` |
| 销毁生命周期 | `beforeDestroy` / `destroyed` | `beforeUnmount` / `unmounted` |
| 过滤器 | `{{ x \| f }}` | 方法 / computed |
| 事件总线 | `$on` `$off` `$once` | 移除，换 mitt 等 |
| `.sync` | `.sync` | `v-model:prop` |
| 默认 v-model | `value` + `input` | `modelValue` + `update:modelValue` |
| 多根节点 | 需单根 | Fragment 允许多根 |
| `$listeners` / `$scopedSlots` | 分开 | 合并进 `attrs` / `slots`（注意版本行为） |
| 响应式新增字段 | 常需 `Vue.set` | Proxy 下通常直接赋值 |

原理层展开：[Vue 2 和 Vue 3 区别](/md/框架/Vue/vue2和3的区别.md)。

## 4. JavaScript → TypeScript：加分项怎么讲

目标不是「全仓 strict 一天完成」，而是 **类型覆盖率与关键路径安全上升**。

### 渐进路径（好讲、好落地）

```text
1. 引入 TS 工具链，allowJs: true
2. 先为 API 层、DTO、枚举写 .ts
3. 公共 utils / composable 优先改 TS
4. 新文件默认 .ts / <script setup lang="ts">
5. 老文件按模块改；打开较严选项要分目录/分 package
6. 用 vue-tsc / CI 类型检查挡回归
```

### Vue 3 为什么更适合 TS（一句就够）

Composition API 是函数组合，`ref`/`props`/`emit` 推断路径清晰；Vue 2 + Options + mixin 的 `this` 合并对类型不友好。

### 组件里常见写法（口述可提）

```ts
// 示意：script setup + 类型化 props/emits
const props = defineProps<{
  orderId: string
  readonly?: boolean
}>()

const emit = defineEmits<{
  submit: [payload: { id: string }]
  cancel: []
}>()
```

### 迁移坑（显得你做过）

- 第三方无类型：先 `@types/*` 或本地 `*.d.ts` 垫片，别阻塞主路径。
- `any` 泛滥等于没迁：约定「边界 any 要注释原因」。
- `.vue` 模块声明、路径别名与 `tsconfig` paths 要和构建一致。
- 与 ESLint 规则分批开，避免上千 error 让团队放弃。

### 如何证明 TS 有价值

- 线上/测试阶段的「undefined 读属性」类缺陷下降。
- 重构时编译期拦住的接口变更。
- 新人改核心模块的安全感（可举一次被类型挡住的事故）。

## 6.1 完整示例项目（记不清细节时先用这套）

### 一句话背景

> 我参与过公司内部的运营管理后台升级：Vue 2.6 + Vue CLI + Element UI + Vuex，跑了大概三年，大约 80+ 路由、200+ 业务组件，覆盖客户管理、工单、数据报表几个域。我主要负责「客户管理 + 工单」两条业务线的兼容清理，并推动接口层先迁 TypeScript。

### 填好的举证卡（对照第 6 节模板）

```text
背景：B 端运营后台，约 80 路由 / 200+ 组件，Vue2 使用约 3 年
痛点：冷启动 30s+；Element/部分插件停更风险；复杂工单页 Options 难维护；接口字段靠人肉记
角色：参与整体升级；负责客户管理、工单域 warning 清理与接口 TS 化
策略：先 Vue CLI→Vite（仍 Vue2）→再 Vue3+@vue/compat → 分域清警告 → 去 compat；TS 先 API 层
难点：Element UI→Plus；全局 EventBus；报表页老图表库；过滤器与 .sync 散落
处理：UI 按使用量排期；EventBus 换 mitt；图表页短期 compat 特性保留；过滤器脚本批量替换
结果：冷启动约 35s→2s；HMR 秒级→百毫秒内；compat 警告从 400+ 清到个位数后去兼容包；
      新页面全 TS，核心接口 100% 有类型；升级后两周无 P0
反思：应更早冻结依赖大版本，并先做登录/工单提交的 E2E 黄金路径
```

### 口述版（可直接背）

> 当时是一个跑了三年的运营后台，Vue 2 + webpack，页面不算少，客户管理和工单是我负责的域。升级不是为了追新：本地冷启动经常三十多秒，热更新也要数秒；Element UI 和个别内部组件对 Vue 3 支持滞后；工单详情这种大页 Options API 里 data、watch、methods 缠在一起；接口字段全靠口口相传，联调经常对错字段。
>
> 我们把构建和框架拆开做。先迁到 Vite，业务先不动，确认构建稳定；再上 Vue 3 和 `@vue/compat`，先保证全站能跑，靠控制台 warning 建看板。我这边优先清工单和客户域：生命周期改名、`.sync` 改 `v-model`、过滤器改方法，全局 EventBus 收到一个 mitt 单例里。Element 升 Plus 按组件使用频率排期，表格、表单、弹层先过，冷门组件后置。有一个报表用的老图表封装短期升不动，就先开 compat 特性顶着，后面换成 ECharts 官方用法。
>
> TypeScript 没有全仓一周改完：先 `allowJs`，把 `api/` 和订单/工单的 DTO 写成 `.ts`，新页面强制 `lang="ts"`，老页面改到哪补到哪。收益上开发启动从大约 35 秒降到 2 秒左右，兼容警告清得差不多后去掉 compat；升级后核心链路回归通过，新功能都在 TS 下交付。

## 6.2 四个好讲的具体坑（追问时当例子）

### 例子 A：全局 EventBus 静默坏掉

**现象**：工单列表「打开详情抽屉」偶发不响应，compat 下有时还能用，去兼容后必现。

**原因**：历史代码用 `Vue.prototype.$bus` + `$on/$off`；Vue 3 移除实例事件 API。

**处理**：

```js
// 迁移前（示意）
this.$bus.$emit('open-ticket', id)
this.$bus.$on('open-ticket', handler)

// 迁移后：src/utils/bus.ts
import mitt from 'mitt'
export const bus = mitt()
bus.emit('open-ticket', id)
bus.on('open-ticket', handler)
```

上线前全局搜 `$bus`、`$on(`，抽屉开关、消息提醒两条路径手测 + 单测锁 mitt 封装。

**面试一句**：

> 最大的坑不是语法改名，而是 EventBus 这种隐式通信，去掉 compat 后才集中爆出来，所以我们用搜索清单 + 黄金路径回归兜底。

### 例子 B：Element UI → Element Plus 的弹层销毁

**现象**：升级后「新建客户」弹窗关闭再开，表单残留上次数据，偶发校验状态错乱。

**原因**：Plus 的 `destroy-on-close` / 插槽写法与旧版不完全一致；原先有些逻辑写在 `destroyed` 里清理，生命周期改名后漏改。

**处理**：统一 `beforeUnmount/unmounted`；弹窗加 `destroy-on-close`；表单用 `:key="visible"` 强制重置；把客户创建弹窗列入回归必测。

**面试一句**：

> UI 库升级我按使用频率排期，表格表单对话框优先；弹层我重点看销毁和重置，这是 B 端最容易隐性翻车的点。

### 例子 C：过滤器 + 金额展示批量替换

**现象**：compat 报大量 `FILTERS` 警告；列表金额、时间列全是 `{{ v | money }}`。

**处理**：`filters/money.js` 改成 `utils/format.ts` 导出函数；模板改 `{{ money(v) }}`；用脚本扫 `|` 统计剩余量，每周清一波。

**面试一句**：

> 过滤器没有技术难度，但量大。我们当成工程任务：脚本统计、公共 format 收口、分域清零，而不是开发时顺手改两个。

### 例子 D：JS→TS 先堵住「工单状态」误用

**现象**：工单状态后端是 `0|1|2|3`，前端各处魔法数字，曾把「已关闭」当成「处理中」展示。

**处理**：

```ts
// types/ticket.ts
export type TicketStatus = 0 | 1 | 2 | 3

export interface TicketDTO {
  id: string
  status: TicketStatus
  customerId: string
  updatedAt: string
}

export const TicketStatusLabel: Record<TicketStatus, string> = {
  0: '待处理',
  1: '处理中',
  2: '已关闭',
  3: '已驳回',
}
```

`api/ticket.ts` 先类型化；列表/详情只引 `TicketStatusLabel`；CI 开 `vue-tsc`，新文件禁止新增裸数字状态。

**面试一句**：

> TS 的收益我用业务例子说：工单状态枚举化之后，改状态文案和判等有编译期提示，比空谈「类型安全」更有说服力。

| 阶段 | 大约耗时（示例） | 完成标准 |

## 7. 模拟追问速答

### 你们为什么要升级？

> 因为维护成本和生态风险已经大于迁移成本：依赖老化、复杂页难拆、类型几乎靠自觉。升级是为交付效率和稳定性，不是为了简历写 Vue 3。

### @vue/compat 能不能一直留着？

> 不能当终态。它是望远镜和缓冲垫，靠 warning 驱动清理；长期留着等于永远背兼容税，也拿不到纯 Vue 3 的一部分优化预期。

详见 [Vue 兼容包的作用](/md/面试准备/技术/vue兼容包的作用.md)。

### 升级最大的坑是什么？

优先答你真实经历的一类；若用本文示例，直接讲 **例子 A（EventBus）** 或 **例子 B（弹层重置）**：

> 最大坑是历史 EventBus：`$on/$off` 在去 compat 后集中坏掉，工单抽屉打不开。我们换成 mitt，全局搜调用点，并把手动打开详情列入黄金路径回归。框架语法有指南，隐式通信和 UI 库销毁细节才是爆炸面。

### Options 要不要全改 Composition？

> 不需要也不划算。新代码新范式，老代码改动时顺手收；用可维护性ROI决定，而不是意识形态。

### TS 会拖慢业务吗？

> Big Bang 会；渐进不会。接口与公共层先类型化，业务页面分批，CI 只挡新增长错误，存量用债务看板消化。

### 和「只会 Vue3 新项目」的人比，你的优势？

> 新项目不暴露兼容与组织协调问题。升过的人更懂存量约束、回归策略和怎么跟业务换窗口期。

## 高频追问

### Vue 3 响应式变化和迁移有什么关系？

少写 `Vue.set`、数组下标更直觉；但迁移重点仍是 API/生态，不是重写所有 `data`。原理见 [Vue 3 响应式原理](/md/框架/Vue/vue3响应式原理.md)。

### 过滤器没了怎么平迁？

全局 `app.config.globalProperties` 挂方法，或局部 computed；模板里改成函数调用。先搜 `|` 用量再批量改。

### 如何处理升不了的老插件？

平替 → 源码 patch（`patch-package`）→ iframe/微前端隔离 → 业务降级。原则：先保业务。展开见架构升级方案文末策略。

### 迁移期如何保证协作不乱？

冻结大面积风格改造；约定新文件规范；compat 警告责任到模块；发布窗口与业务需求错峰。
