# 依赖预构建

## 面试回答

> Vite 开发态把业务源码当原生 ESM 按需编译，但 `node_modules` 里很多包仍是 CommonJS/UMD，浏览器不能直接吃；还有像 `lodash-es` 这种内部文件极多的 ESM，一个 `import` 可能打出几百个请求。依赖预构建就是启动（或发现新依赖）时，用 **esbuild** 把这些依赖转成浏览器友好的 ESM，并尽量合并成更少模块，结果缓存在 `node_modules/.vite`。
>
> 它主要服务**开发**；生产构建走 Rollup，CJS 兼容由生产插件链处理，不要说成「预构建替代了生产打包」。缓存会随 lockfile、相关 Vite 配置、`NODE_ENV` 等变化失效，不行就 `--force`。链接依赖、插件动态注入的 import，可能要 `optimizeDeps.include/exclude` 手动纠偏。

**一句话总结：**

> 预构建：CJS→ESM + 合并碎依赖 → 开发少请求；缓存看 lockfile；只服务 dev。

---

## 核心原理

### 1. 为什么要预构建（两个问题）

| 问题 | 没有预构建会怎样 |
| --- | --- |
| 格式不兼容 | `require` 包在原生 ESM 页面里挂 |
| 请求爆炸 | 深树 ESM 一次成百上千请求，即使 HTTP/2 也卡 |

---

### 2. 执行链路

```text
扫描源码中的 bare import（从 node_modules 解析）
  → esbuild 预构建入口依赖
  → 写入 node_modules/.vite
  → 浏览器带强缓存拉预构建产物
  → 运行中遇到新依赖 → 再预构建并可能刷新
```

| 概念 | 职责 |
| --- | --- |
| 源码按需编译 | 处理你写的 TS/Vue/… |
| 依赖预构建 | 处理第三方包形态与粒度 |
| 生产 Rollup | 最终产物优化（另一条链） |

---

### 3. 缓存何时失效

常见触发：锁文件变化、相关 config、环境变量等。强制：删 `.vite` 或 `vite --force`。预构建资源常用长时间 `immutable` 缓存，依赖版本变化靠查询参数失效。

---

### 4. include / exclude 直觉

| 情况 | 倾向 |
| --- | --- |
| 大包、CJS、扫描发现不了（插件生成 import） | `include` |
| 已是干净小 ESM、想直接走浏览器 | 可考虑 `exclude` |
| monorepo 链接包 | 常当源码；非 ESM 时要额外 include |

---

### 5. 设计取舍

换开发体验；增加「缓存与优化范围」心智。调试改 `node_modules` 时要会清缓存。

---

## 常见误区

### ❌ 预构建是生产构建的一部分

### ✅ 更准确的说法

主要是开发优化；生产另有打包与 CJS 插件。

---

### ❌ 所有依赖预构建后都变成一个文件

### ✅ 更准确的说法

按入口依赖优化；目标是合法 ESM + 减少过量碎请求，不是绝对单文件。

---

### ❌ 清不清缓存无所谓

### ✅ 更准确的说法

改依赖或本地 patch 后，旧缓存会导致「改了没生效」的假象。

## 高频追问

### 预构建解决哪两件事？

兼容 CJS/UMD；合并碎模块降请求。

### 用什么做预构建？

开发用 esbuild（快）。

### 缓存坏了怎么办？

`--force` 或删 `node_modules/.vite`；先确认 lockfile/配置是否变了。

### 和生产 commonjs 插件什么关系？

场景不同：一个服务 dev ESM 管道，一个服务 prod 打包图。
