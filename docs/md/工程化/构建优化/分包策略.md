# 分包策略

## 面试回答

> 分包不是拆得越碎越好，而是在**首屏体积、缓存命中、请求数量**之间取平衡。常见做法：路由 `import()` 把非首屏页面拆走；React/Vue/图表等稳定依赖打成 vendor，避免业务一改就让大依赖缓存失效；多页共享的业务抽 common；大弹窗/编辑器组件级懒加载。拆完要用首屏 JS、瀑布图、LCP、路由切换耗时验证。过细会增加请求与解析调度成本；HTTP/2 能缓解并发，消不掉执行与调度本身。

**一句话总结：**

> 按路由/vendor/common/懒加载拆 → 换首屏与缓存 → 用指标防过细。

---

## 核心原理

### 1. 为什么要分包

单包过大：首屏下载与解析慢；且业务与框架捆在一起，发版时缓存命中差。

---

### 2. 策略表

| 策略 | 目的 | 风险 |
| --- | --- | --- |
| 路由懒加载 | 首屏只带当前页 | 切换等待 |
| vendor 分层 | 稳定依赖长缓存 | 单 vendor 过大 |
| common | 去重共享 | 过度共享变多请求 |
| 组件懒加载 | 重功能延后 | 首次交互延迟 |
| external + CDN | 更大缓存面 | CDN/版本风险 |

```js
// 动态入口分裂点
const Chart = () => import('./Chart')
```

Webpack `splitChunks` / Vite `manualChunks` 是配置层手段，面试先讲**策略维度**再讲 API。

---

### 3. 与 Tree Shaking

摇树：包内删无用代码；分包：代码**何时加载**。常一起用。

---

### 4. 设计取舍

首屏与缓存收益 vs 请求碎片与复杂度；用数据收敛，不凭感觉。

---

## 常见误区

### ❌ chunk 越多越专业

### ✅ 更准确的说法

看首屏与缓存指标；过多 chunk 可能更慢。

---

### ❌ 所有 node_modules 打一个 vendors 就完事

### ✅ 更准确的说法

变化频率不同的库应分层，否则一改图表库就bust 框架缓存。

## 高频追问

### 如何验证分包有效？

主包体积、LCP、瀑布图、缓存命中、懒路由耗时。

### HTTP/2 是否意味不用合并？

并发更好，但解析/执行/缓存粒度仍要设计，不是无限拆。

### 和微前端关系？

微前端是运行时应用边界；分包是构建产物边界，可同时存在但别混概念。
