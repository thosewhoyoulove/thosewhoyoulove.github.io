# HMR 热更新原理

## 面试回答

> HMR 的目标是改代码后**尽量不整页刷新**，只替换变更模块，并尽可能保住运行时状态。dev server 监听文件变化，更新模块图，找到能 `accept` 的热更新边界，经 WebSocket 通知浏览器；浏览器再拉新模块并执行更新回调。Webpack 的 HMR 绑在 bundle runtime 和热更新 chunk 上；Vite 基于原生 ESM，浏览器重新请求变更模块，链路通常更轻。若链路向上找不到边界，就退化成 Live Reload 式整页刷新。所以「快」和「保状态」都取决于边界与框架插件，不是无限保证。

**一句话总结：**

> 监听变更 → 找 HMR 边界 → WS 通知 → 拉新模块 → accept；无边界则整页刷新。

---

## 核心原理

### 1. 主链路

```text
保存文件
  → server 感知变更
  → 更新模块图 / 变换图
  → 定位 accept 边界
  → WebSocket 推送
  → 浏览器请求新模块
  → 执行更新（框架运行时或手写 accept）
```

| | Webpack | Vite |
| --- | --- | --- |
| 载体 | 热更新 chunk + runtime | ESM 模块重新 import |
| 成本 | 与打包图绑定 | 开发态通常更轻 |

---

### 2. 边界直觉

```text
App
 ├─ Button   ← 修改这里
 └─ Chart

有组件级 HMR：只换 Button
无边界：冒泡到 App，再不行整页刷新
```

---

### 3. 与 Live Reload

| | HMR | Live Reload |
| --- | --- | --- |
| 页面 | 尽量不刷新 | 整页刷新 |
| 状态 | 可能保留 | 通常丢失 |

---

### 4. 设计取舍

体验优先；实现复杂，边界处理不好会「更新了但 UI 怪」或静默失败后难查。

## 常见误区

### ❌ HMR 一定保留 React state

### ✅ 更准确的说法

靠框架插件与组件是否可安全替换；很多情况仍丢局部状态。

---

### ❌ Vite 有 HMR 所以改任意文件都瞬间、永不刷新

### ✅ 更准确的说法

无边界或改到入口/配置类仍可能刷新；依赖预构建变更也可能整页更重。

---

## 高频追问

### HMR 如何通知浏览器？

常见 WebSocket；也有轮询降级，视实现而定。

### 为什么 Vite HMR 体感更快？

开发不整包，只处理相关模块请求。

### 自己写 accept 做什么？

声明「这个模块变了由我处理」，截断向上冒泡。
