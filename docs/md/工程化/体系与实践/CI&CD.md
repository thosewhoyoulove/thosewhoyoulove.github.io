# CI/CD

## 面试回答

> CI 是持续把改动合入主干并自动做质量检查；CD 是在检查通过后自动交付到环境（交付到可发布，或直接部署）。前端流水线常见：安装依赖（认 lockfile）→ lint / 类型检查 → 测试 → 生产构建 → 部署预览或测试环境 →（审批）→ 生产 → 健康检查与监控，失败可回滚。工程价值是把「人肉记得跑命令」变成卡点，让主分支默认可发布。密钥进 CI 密钥库，环境隔离，生产变更要可追溯。灰度和监控属于发布策略，和流水线骨架一起答更完整。

**一句话总结：**

> 提交触发 → 检查卡点 → 构建产物 → 分环境部署 → 监控回滚。

---

## 核心原理

### 1. CI 与 CD

| | 含义 |
| --- | --- |
| CI | 频繁集成 + 自动构建/测试，尽早发现冲突与回归 |
| CD（交付） | 产物随时可发布 |
| CD（部署） | 通过后自动上生产（或自动上预发） |

---

### 2. 前端典型流水线

```text
push / MR
  → install（cache + lockfile）
  → lint / tsc
  → unit / e2e（按成本选）
  → build
  → deploy preview / staging
  → （可选人工）deploy prod
  → smoke / 监控
  → 出问题 → 回滚上一产物
```

| 卡点 | 拦住什么 |
| --- | --- |
| lint/type | 低级错误与类型洞 |
| test | 逻辑回归 |
| build | 「我本地能跑」但产物挂 |

---

### 3. 前端特有点

- 产物是静态资源：要带 **hash**、CDN 缓存策略、`index.html` 不长缓存。
- 预览环境：每 MR 一个 URL，Review 可点。
- Node 版本与 lockfile 必须和本地一致，否则「CI 挂我不管」。

---

### 4. 设计取舍

流水线越全越稳，越慢越劝退。用并行 job、缓存、affected（Monorepo）控时间。

---

## 常见误区

### ❌ CI 绿了就等于产品没 bug

### ✅ 更准确的说法

只保证自动化覆盖到的质量面；还需监控与兜底。

---

### ❌ 生产部署失败就再点一次同一流水线不管版本

### ✅ 更准确的说法

要明确产物版本与回滚对象；避免「半发布」状态。

---

### ❌ 密钥写在仓库变量明文里给前端用

### ✅ 更准确的说法

密钥进保密存储；浏览器端本就不应放服务端密钥。

---

## 高频追问

### 前端 CI 最少要有什么？

install + lint + build；有测试更好；部署与回滚看团队成熟度。

### 如何加快 CI？

依赖缓存、并行、只跑受影响包、拆重 e2e 到夜间。

### 灰度怎么和 CI 结合？

CI 产出不可变制品；发布系统按比例切流量；回滚切回旧制品。
