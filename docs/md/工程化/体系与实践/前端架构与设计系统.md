# 前端架构与设计系统

## 面试回答

> 从零做大型 React 项目，我按依赖方向分层，不按文件类型把组件、Hook 堆在顶层目录。app 放路由和全局 Provider，pages 只负责把一个路由上的功能拼起来。features 是用户能感知的能力，比如结账、筛选，它们之间不互相引用。entities 放订单、用户这种业务对象的类型和查询。shared 只留真正跨功能的东西：设计系统、请求客户端，以及和业务无关的工具。依赖只能往内层走。一个功能的改动先落在自己的目录里，第二次真实复用再往下沉。
>
> 抽象看它稳定的是什么。界面和交互稳定，抽组件。状态和副作用能脱离 JSX 复用，抽 Hook。请求、映射和纯计算不碰 React，放 Service。要给多个宿主独立发版，并且承诺兼容，才做成 SDK。只被一个应用使用的模块，留在仓库里就够了。
>
> 组件库我做成可组合的零件，而不是一个带几十个布尔值的万能组件。外观用少量 variant，结构用 children 和插槽，行为用明确的模式枚举。单个正交开关可以留，比如 `disabled`。互相组合后会造出非法结构的布尔值，就改成组合。主题不写死颜色，组件只读语义 token。亮色、暗色和品牌换的是 token 的值，组件代码不动。
>
> 跨业务线复用的是这层稳定契约。业务规则留在各自的 feature，通过配置、插槽和适配器接进来。公共包里不写「如果是某条业务线」。字段由后端或运营决定的表单，我会拆成数据 schema、界面 schema 和组件注册表。渲染器只认白名单里的类型，文案当文本渲染。
>
> 这些包如果总在同一次改动里一起变，用 Monorepo。发布节奏、权限和故障域都不同，就用多仓库。组件库和 SDK 用语义化版本守公开 API，破坏性变更留迁移期。宿主集体异常时，先钉住版本止血，再按版本差定位，最后补契约测试。

**一句话总结：**

> 依赖往内走 → 按稳定的东西决定抽组件、Hook、Service 还是 SDK → 组合加 token，而不是布尔堆叠 → schema 只描述、注册表负责渲染 → 语义化版本和契约测试守住宿主。

## 核心原理

### 1. 为什么要先讲分层

大型项目变慢，通常不是因为少了一个工具，而是改一个功能要穿过很多无关目录，公共包里逐渐出现某一条业务线的判断。分层要保证两件事：一次业务改动落在一个地方；公共层不认识具体业务。

---

### 2. 整体依赖方向

```text
app        启动、路由、全局 Provider
  → pages / widgets    把一个路由或一块区域拼起来
    → features         一个用户能感知的能力
      → entities       业务对象的类型、查询、小型展示
        → shared       ui、请求客户端、纯工具、token
```

这是依赖方向，不是必须照抄的目录名。Feature-Sliced 是一种常见落地：上层引用下层，同一层的切片默认不互相引用。实体之间如果必须互相使用，也只走对方公开出来的入口，不伸进内部文件。pages 可以同时用结账和地址两个 feature。结账不能去 import 地址，否则两条业务就绑死了。

一个 feature 内部再按变化原因就近放：

```text
features/checkout/
  ui/        这个功能的界面
  model/     状态和 Hook
  api/       这个功能自己的请求
  index.ts   对外只导出这一层
```

顶层按 `components/`、`hooks/`、`services/` 分，一个结账改动会散进三个目录。按功能收拢之后，共享代码是抽出去的结果，不是一开始就设一个大杂烩 `shared/`。

#### Trace：谁可以引用谁

| 改动 | 允许 | 为什么越界会耦合 |
| --- | --- | --- |
| 结账页组合地址表单 | `pages/checkout` 引用两个 feature 的公开入口 | 组合发生在页面，两个 feature 仍可单独测 |
| 结账 feature 直接 import 地址 feature | 不允许 | 地址的内部状态变成结账的依赖，拆仓库时拆不走 |
| 按钮组件 import 结账接口 | 不允许 | 设计系统开始认识业务，别的业务线无法使用 |
| 结账 api 使用 shared 里的请求客户端 | 允许 | 客户端只处理鉴权、错误结构和超时，不包含结账规则 |

`index.ts` 是这道边界的实际位置。外部若能引用 `features/checkout/model/internal`，分层就只剩目录名。

---

### 3. 组件、Hook、Service、SDK

| 抽成 | 稳定的是什么 | 里面可以有 | 不应该有 |
| --- | --- | --- | --- |
| 组件 | 界面结构和交互 | 受控状态、组合出去的插槽 | 某一业务线的定价、权限表 |
| Hook | 能脱离 JSX 的状态和副作用 | 订阅、请求生命周期、表单状态 | 固定的页面结构 |
| Service | 输入输出明确的请求、映射、纯计算 | 可在测试里直接调用的函数 | `useState`、JSX |
| SDK | 多个宿主、独立发版、兼容承诺 | 公开 API、changelog、peer 依赖 | 某个页面的私有流程 |

判断顺序是：先放在功能内部。第二个真实场景出现，再上提到 entities 或 shared。多个应用要独立安装、独立升级，才发布成包。过早发布 SDK，会把还在变化的 API 变成所有宿主的兼容负担。

SDK 如果同时给 React 页面和 Node 脚本用，核心包不要依赖 React。React 绑定单独一个包，把 `react` 放在 `peerDependencies`。打进两个 React 副本时，Hook 和 Context 会对不上。

组件级的受控、非受控和组合，见 [组件设计能力](/md/框架/React/组件设计能力.md)。这里补充的是它上面那一层：什么时候根本不该做成组件。

---

### 4. 可扩展的组件库，以及布尔 props

组件库的公开面尽量小：组件、语义 token、图标，再加上文档里写明的行为。调用方依赖这些，不依赖内部 DOM 层级。

扩展方式按它改变的东西选择：

| 要改变的 | 做法 | 例子 |
| --- | --- | --- |
| 外观，而且彼此正交 | 少量 variant | `size="sm" \| "md"`，`tone="neutral" \| "danger"` |
| 结构，调用方要换内容 | `children`、具名插槽、复合组件 | 对话框的头、正文、底栏由调用方拼 |
| 渲染成哪种标签 | 把行为合并到子元素上，常见叫法是 `asChild` | 按钮的行为放到一个链接上，不套多余 DOM |
| 行为模式互斥 | 一个枚举，而不是一组布尔 | `mode: "edit" \| "preview"` |

`disabled`、`readOnly` 这种单轴开关可以留。问题出在一组会互相作用的布尔值。

#### Trace：三个布尔值为什么失控

`<Dialog hideHeader hideFooter danger />` 在类型上有 8 种组合。产品实际只允许三种：普通确认、危险确认、没有底栏的提示。另外五种能通过类型检查，测试也很难覆盖，调用方会各自试出一种「能跑」的组合。

改成组合之后，非法结构写不出来：

```tsx
<Dialog tone="danger">
  <Dialog.Header>删除项目</Dialog.Header>
  <Dialog.Body>此操作无法撤销</Dialog.Body>
  <Dialog.Footer>
    <Button>删除</Button>
  </Dialog.Footer>
</Dialog>
```

没有 Header 就不要写 `Dialog.Header`。危险只影响语气，不再和「有没有头」绑成一个布尔矩阵。

库仍然会变复杂，只是复杂转移到了组合约定和内部 Context。所以不要同时提供 `hideHeader`、`header` 渲染函数和 `Dialog.Header` 三套入口。一套结构扩展点就够。

`asChild` 解决的是另一件事：调用方已经有一个链接或路由组件，只想要按钮的样式和交互。组件把自己的 props 合并到那个子元素上，页面上不会多出一层按钮 DOM。它不负责开关头尾栏。

### 5. Schema 驱动的动态表单

字段集合不由前端写死时，渲染器和字段描述要分开。描述再拆成两份，避免一份 schema 既当校验又当界面：

| 层 | 回答的问题 | 谁来改 |
| --- | --- | --- |
| 数据 schema | 值的类型、必填、范围 | 可以和后端契约对齐，并用 zod 等在运行时校验 |
| 界面 schema | 用哪种控件、标签、顺序、何时出现 | 前端或运营配置 |
| 注册表 | 类型字符串对应哪个组件 | 只有前端能注册 |
| 渲染器 | 读值、判断可见性、把字段交给注册表 | 不认识具体业务 |

```text
界面 schema
  → 用当前表单值过滤可见字段
  → 用类型去注册表取组件
  → 组件写回同一份表单状态
  → 提交前用数据 schema 校验
  → Service 把通过的值映射成接口参数
```

#### Trace：联系方式切换

```ts
const uiSchema = [
  { type: "select", name: "contact", label: "联系方式", options: [
    { label: "邮箱", value: "email" },
    { label: "手机", value: "phone" },
  ]},
  { type: "text", name: "email", label: "邮箱", visibleWhen: { field: "contact", equals: "email" } },
  { type: "text", name: "phone", label: "手机", visibleWhen: { field: "contact", equals: "phone" } },
];
```

| `contact` 的值 | 渲染器留下的字段 | 提交策略 |
| --- | --- | --- |
| `"email"` | select + email | 带 `email`，不带上次留下的 `phone` |
| `"phone"` | select + phone | 带 `phone`，不带 `email` |

隐藏字段必须有明确策略。若只是不渲染、提交时仍把旧值带上，用户改成邮箱后，过期手机号会一起发出去。

注册表是白名单：

```ts
const registry = { text: TextField, select: SelectField };

function renderField(field) {
  const Widget = registry[field.type];
  if (!Widget) {
    reportUnknownField(field.type);
    return null;
  }
  return <Widget {...field} />;
}
```

未知类型在开发环境直接失败，生产环境上报并跳过，不能落到 `dangerouslySetInnerHTML`。后端来的文案按文本渲染。新业务要「行业选择器」时，业务包注册 `industry`，不改渲染器。联动副作用，比如选完行业去请求子类目，放在业务自己的字段组件或提交 Service 里，不写进核心循环。

### 6. 业务线复用，同时不把规则耦合进来

能共享的是稳定契约：设计系统、语义 token、登录态的形状、请求客户端、监控和埋点的调用方式。不能共享的是会按业务线分叉的规则：价格、审批流、某个页面的字段顺序。

依赖方向要反过来。公共组件提供插槽，业务线把自己的规则传进去。公共组件若出现 `if (businessLine === "retail")`，它就开始依赖所有业务线，下一条业务线必须改公共包才能上线。

```tsx
<PricingTable
  rows={rows}
  renderPrice={(row) => <RetailPrice row={row} />}
/>
```

`PricingTable` 只负责布局、空态和键盘操作。零售的价格计算留在 `RetailPrice`。另一条业务线换一个渲染函数，表格不用发布新版本。

跨边界的数据用适配器收口。业务接口的字段名不直接进共享组件的 props。适配器把后端 DTO 收成共享组件认识的视图模型，接口改名时只改适配器。

### 7. Monorepo 和多仓库

| | 适合 | 你会得到 | 你要付出 |
| --- | --- | --- | --- |
| Monorepo | 组件库、应用、类型经常同一次 PR 里改 | 本地直接引用，规范统一 | 仓库变大后必须只构建受影响的包 |
| 多仓库 | 发布节奏、权限、故障域不同；SDK 要给外部团队 | 权限和 CI 天然隔开 | 联调要等发版，类型容易漂移 |

同一家公司的设计系统和三个后台，改一个 token 就要同时改组件和应用，Monorepo 更合适。给外部客户安装的 SDK，和内部应用的发布日不同，也不该让外部仓库看到内部业务，用多仓库，并通过包版本对接。

仓库策略不消灭耦合。Monorepo 里如果 feature 可以任意引用另一个 feature 的内部文件，只是把跨仓等待换成了仓内纠缠。包的公开入口、任务缓存和按影响范围构建，见 [Monorepo](/md/工程化/体系与实践/Monorepo.md)。

### 8. 版本管理和兼容

公开 API 只有文档和包导出里承诺的那一部分。`package.json` 的 `exports` 把内部路径挡在外面，调用方就依赖不了 `src/internal`。

| 变更 | 版本 | 例子 |
| --- | --- | --- |
| 修复，调用方不用改 | patch | 修正焦点归还 |
| 新增可选能力 | minor | 新的 `tone`，默认值保持旧外观 |
| 删除、改默认行为、改 token 名字 | major | 移除 `hideHeader` |

语义化版本描述的是你打算如何兼容，不能代替 changelog。把行为变化放进 patch，宿主按「补丁可自动升」升级后仍会坏。

破坏性变更留一个迁移期。minor 里旧 props 继续可用，开发环境打出替换建议；下一个 major 再删除。能机械替换的用 codemod，行为已经变了的靠迁移说明和一段兼容层。组件库把 `react` 和 `react-dom` 放在 peer 依赖，由宿主提供同一份实例。

发版前用类型快照锁住导出面，并用一组固定的宿主夹具跑行为测试。视觉回归覆盖关键组件。这些检查拦的是「发布之后才知道导出没了」。

### 9. Design Token 与多主题

Token 是设计决定的名字，不是组件里的色值。分三层，组件只读最后被允许读的那一层：

| 层 | 例子 | 谁可以引用 |
| --- | --- | --- |
| 原始值 | `--color-blue-600: #1d4ed8` | 语义层 |
| 语义 | `--color-text-primary` | 组件 |
| 组件 | `--button-bg`，只在某个控件确实要单独微调时 | 这个控件 |

```css
:root {
  --color-blue-600: #1d4ed8;
  --color-text-primary: var(--color-blue-600);
}
[data-theme="dark"] {
  --color-text-primary: #bfdbfe;
}
[data-brand="acme"] {
  --color-text-primary: #0f766e;
}
```

```tsx
<button className="btn">保存</button>
```

```css
.btn { color: var(--color-text-primary); }
```

#### Trace：同一颗按钮

| 根节点 | `--color-text-primary` 的计算值 | 按钮代码 |
| --- | --- | --- |
| 默认 | `#1d4ed8` | `var(--color-text-primary)` |
| `data-theme="dark"` | `#bfdbfe` | 不变 |
| `data-brand="acme"` | `#0f766e` | 不变 |

品牌和暗色都是在换语义变量的值。按钮不读原始色板，否则品牌一换主色，每个组件都要改。两个属性写到同一个变量上时，覆盖顺序要定好：基础主题先写，品牌包只覆盖它需要改的语义变量。

用户可切换的主题适合运行时改 `data-theme`。不同品牌本来就是两套部署时，也可以在构建时产出两份 CSS。Token 名字是 API，改名按破坏性变更处理。

自定义属性会继承进 Shadow DOM，所以用 Web Components 时，token 仍然可以从外层传进去。普通类名则不会穿过 Shadow 边界。

### 10. 公共 SDK 升级把多个宿主打坏

先止血，再定位，最后补上发布前就该有的检查。

```text
确认只有升过版本的宿主出错
  → 钉住上一个可用版本，或暂停这次发布
  → 用版本差缩小到具体变更
  → 在最小宿主里复现
  → 修复后发 patch，或在确认旧版仍然安全时回滚
  → 把这次失败补进契约测试
```

#### Trace：结账页白屏

| 宿主 | SDK | 现象 |
| --- | --- | --- |
| web | 2.3.0 | 结账页白屏，监控里是 Invalid hook call |
| admin | 2.2.1 | 同一条结账路径正常 |

差异落在 `2.2.1` 到 `2.3.0`，不是结账业务当天的改动。Invalid hook call 优先查 SDK 是否把 `react` 打进了自己的包，导致页面上有两份 React。若栈指向某个已删除的导出，再对 changelog 和类型快照。能在一个只安装 SDK 和 React 的夹具里复现，就不必先在每个宿主里加日志。

数据已经被新版本写过时，直接回滚可能比白屏更危险。那种情况发兼容旧数据的 patch，而不是把所有宿主钉回旧包。

定位时同时看三类契约：类型导出、运行时行为、样式是否泄漏到宿主。全局 `button { }` 这种选择器也会让多个应用一起异常，但它不会出现在类型diff 里。

### 11. 设计取舍

| 选择 | 得到 | 代价 |
| --- | --- | --- |
| 按功能分层，共享层保持很薄 | 改动落点清楚 | 初期会觉得抽得不够「通用」 |
| 组件库只留一套组合方式 | API 可测 | 复杂内容要多写几层 JSX |
| 表单用 schema 加白名单 | 字段能配置 | 要自己定义隐藏字段和未知类型的策略 |
| 语义 token | 主题和品牌不用改组件 | 名字要当 API 维护，覆盖顺序要约定 |
| 独立发版的 SDK | 宿主按自己的节奏升级 | 每次变更都有兼容成本；单应用内的模块不必付这个成本 |

## 常见误区

### ❌ 顶层分成 components、hooks、utils 就是架构

### ✅ 更准确的说法

那是文件类型。架构看的是依赖方向：功能之间不互引，公共层不认识具体业务。

### 为什么？

按类型分目录之后，一次业务改动仍然散在多个文件夹，也拦不住按钮去调结账接口。

---

### ❌ props 越多，组件库越灵活

### ✅ 更准确的说法

正交的外观用少量 variant，结构用组合。会组合出非法状态的布尔值是 API 设计失败。

### 为什么？

三个相关布尔值就有八种组合，类型系统不会帮你删掉产品上不存在的那几种。

---

### ❌ Schema 表单就是后端返回什么就渲染什么

### ✅ 更准确的说法

数据 schema 负责值，界面 schema 负责控件和显隐，注册表是白名单。渲染器不执行后端传来的代码或 HTML。

### 为什么？

不分开的话，校验和界面缠在一起；不设白名单，配置系统会变成注入入口。

---

### ❌ Design Token 就是一份色板文件

### ✅ 更准确的说法

组件读语义变量。色板是原始值，主题和品牌替换的是语义变量，组件代码不动。

### 为什么？

组件直接写死 `#1d4ed8` 时，暗色和品牌都要改组件。

---

### ❌ 遵守语义化版本，宿主就可以无脑升级

### ✅ 更准确的说法

语义化版本表达的是兼容意图。patch 里改了默认行为，自动升级仍会坏。发布前要用契约测试核对导出、行为和样式。

### 为什么？

版本号是约定，不是宿主里的自动证明。

## 高频追问

### 大型 React 项目怎么分层？

app 管启动和路由，pages 组合功能，features 之间不互引，entities 放业务对象，shared 只留跨功能契约。外部只能走每个模块的公开入口。第二次真实复用再下沉。

### 什么该抽成组件、Hook、Service 或 SDK？

看稳定的是界面、可复用的状态、与 React 无关的输入输出，还是多个宿主的兼容承诺。单应用内的模块不要为了「像基建」提前发布成 SDK。React 绑定和核心逻辑分包，React 放 peer 依赖。

### 组件库怎么扩展，又不堆布尔 props？

外观用 variant，结构用插槽和复合组件，互斥行为用一个枚举。只保留一套结构扩展点。`disabled` 这种单轴开关可以留。

### Schema 表单的主链路是什么？

界面 schema 决定可见字段，注册表把类型映射到组件，数据 schema 在提交前校验。隐藏字段要规定是否提交。未知类型走白名单的失败策略，文案当文本。

### 业务线怎么复用又不耦合？

共享设计系统、请求客户端和视图契约。业务规则用渲染函数或适配器从外面传进来。公共包里不写业务线分支。

### Monorepo 和多仓库怎么选？

经常同一次改动的设计系统和应用用 Monorepo，并且只构建受影响的包。发布节奏、权限或故障域不同，用多仓库加版本对接。仓库形式本身不代替包边界。

### 组件库的版本和兼容怎么定？

导出面才是公开 API。新增可选能力是 minor，删除和改默认行为是 major。旧 API 先弃用一个版本，能机械替换的给 codemod。类型快照和宿主夹具在发布前跑。

### Token 如何支持多主题和品牌？

组件使用 `--color-text-primary` 这种语义变量。`data-theme` 和 `data-brand` 只替换这些变量的值，并约好谁覆盖谁。Token 改名按破坏性变更处理。

### SDK 升级导致多个宿主异常，怎么处理？

先看是不是只有新版本的宿主坏了，钉住旧版或停掉发布。再用版本差和最小夹具复现，区分类型破坏、双份 React、运行时行为变化和全局样式泄漏。数据已被新版本写过时，用兼容旧数据的 patch，而不是直接回滚。
