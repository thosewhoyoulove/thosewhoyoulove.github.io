# DNS 与 CDN

## 面试定位

DNS 常嵌在“输入 URL 后发生什么”和“首屏为什么慢”中。三年前端要答清解析链路、常见记录、缓存边界，以及 CDN 如何利用 DNS/Anycast 把用户导向合适节点。

## 面试回答

> DNS 的作用是把域名解析成可连接的地址。浏览器请求前通常依次检查自身、操作系统等缓存，未命中时交给递归解析器；递归解析器再从根、顶级域和权威 DNS 获取记录并按 TTL 缓存。实际链路还可能经过 CNAME，最终得到 A/AAAA 地址。CDN 会通过 DNS 调度或 Anycast 把用户引导到较近、负载合适的边缘节点；边缘命中就直接返回，未命中再回源。因此 DNS 优化要减少无意义的第三方域名、谨慎使用 `dns-prefetch`/`preconnect`，CDN 优化则关注缓存键、TTL、回源率和资源版本。DNS 缓存并非只有浏览器一层，修改记录后也不会全球瞬间生效。

一句话总结：

> DNS 解决“去哪里连接”，CDN 解决“由哪个边缘节点更快地返回内容”。

---

## 1. 解析链路

```text
浏览器 / OS 缓存
  → 本地递归解析器
  → Root DNS
  → TLD DNS（如 .com）
  → 权威 DNS
  → A / AAAA / CNAME
  → 客户端连接目标 IP
```

递归解析器通常替客户端完成迭代查询；根服务器不是直接返回网站 IP，而是指向相应 TLD，TLD 再指向权威 DNS。

| 记录 | 用途 |
| --- | --- |
| A | 域名指向 IPv4 |
| AAAA | 域名指向 IPv6 |
| CNAME | 一个域名指向另一个域名 |
| TXT | 域名验证、邮件安全等文本信息 |

## 2. DNS 缓存与 TTL

缓存可能存在于浏览器、操作系统、路由器、递归解析器等多层。权威记录的 TTL 告诉缓存可以保存多久，但真实生效时间还会受各层实现、旧连接和 CDN 配置影响。

- TTL 太长：切流或故障迁移传播慢。
- TTL 太短：权威查询压力和解析延迟增加。
- 改记录前先适当降低 TTL，迁移稳定后再调回，是常见运维策略。

DNS 使用 UDP/TCP 53 是经典认知；现代浏览器/系统也可能通过 DoH 或 DoT 加密 DNS 查询。HTTPS 只会在连接目标错误且证书不匹配时暴露部分问题，本身不能阻止 DNS 污染。

## 3. CDN 请求链路

```text
用户请求静态资源
  → DNS / Anycast 调度到边缘 PoP
  → Edge cache hit：直接响应
  → miss：向源站或上级缓存回源
  → 缓存响应并返回用户
```

CDN 是否命中不仅看 URL，还可能看 Host、查询参数、`Vary` 指定的请求头和 CDN 自定义规则。带 Hash 的静态资源适合长缓存；HTML 通常短缓存或协商缓存，避免引用已经下线的资源版本。

## 4. 前端性能优化与排障

- `dns-prefetch` 只提前解析域名；`preconnect` 还会提前建立连接和 TLS，应只给确定会访问的关键域名使用。
- 第三方域名越多，DNS、连接、TLS 与隐私成本越高，不要无差别预连接。
- DevTools Timing 可观察 DNS、Connection、SSL、Waiting；但连接复用时这些阶段可能显示为 0。
- CDN 故障要看缓存命中头、Age、边缘节点、回源状态与缓存键，不能只清浏览器缓存。

## 高频追问

### DNS 用 UDP 还是 TCP？

传统 DNS 常优先使用 UDP，响应过大、截断或区域传送等场景会使用 TCP；DoH 则通过 HTTPS。回答“DNS 永远只用 UDP”不准确。

### CNAME 和 A 记录有什么区别？

A 直接给出 IPv4；CNAME 把当前名称映射到另一个规范名称，解析器还要继续解析目标。CDN 常让业务域名 CNAME 到调度域名。

### CDN 为什么能加速？

它把可缓存内容放到离用户更近的节点，降低 RTT 和源站压力；同时通过连接优化、压缩、协议升级等改善传输。但动态未缓存请求仍可能回源。
