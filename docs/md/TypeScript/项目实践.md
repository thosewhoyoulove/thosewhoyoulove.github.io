# TypeScript 项目里的类型设计

## 面试回答

> 大型 React 项目里，我不会把类型都堆进一个 `global.d.ts`。我会分成三层，而且只让相邻的层互相引用。
>
> 最外面是接口类型，优先用 OpenAPI 生成，放在 `api/generated`，不手改。这一层是传输形状，字段可能叫 `user_name`，也可能带上页面用不到的字段。每个接口模块负责把它映射成领域类型，比如 `User`。组件和状态只拿领域类型，不直接 import 生成结果。这样后端改一个字段名，改动停在映射函数，不会红到每个页面。
>
> 领域类型跟业务模块走，例如 `features/order/types.ts`。组件自己的 props 跟组件文件走，不进全局目录。真正跨业务的才进 `shared`：分页、`RequestState<T>` 这种异步状态、全局 EventBus 的事件表。
>
> 通用组件要把类型参数留在函数上，并写成 `<const T>`，调用方才能从选项的字面量推出 `"on" | "off"`，而不是扩成 `string`。不要写成 `React.FC`，那会把类型参数弄丢。请求则用 `useRequest` 从异步函数的返回值推出 `T`，再用判别联合把 `loading`、`data`、`error` 收成互斥状态，避免三个字段同时为真。事件总线用一份事件表把事件名和载荷绑在一起，`emit` 传错字段会在编译期失败。
>
> 类型在编译后会被擦掉。生成类型和领域类型都替代不了运行时校验，外部 JSON 进领域层之前仍然要校验一次。

**一句话总结：**

> 生成类型停在 API 边界 → 映射成领域类型 → props 跟组件、跨业务才进 shared → 组件和请求靠泛型推导 → 异步状态用判别联合。

## 核心原理

### 1. 为什么不能只建一个 types 目录

类型要表达的不是「这个字段是字符串」，而是「这一层允许出现哪些状态」。传输层、领域层、组件层混在一个文件里，后端字段、页面状态和按钮 props 会互相引用。后面改接口，组件类型跟着变；改一个下拉框，接口文件跟着红。

分层是为了让每一层只看到自己能处理的形状。

```text
api/generated/          生成的 DTO，不手改
api/user.ts             DTO → User，运行时校验也放在这里
features/user/types.ts  这个业务自己的状态、表单
features/user/UserSelect.tsx   props 跟组件
shared/types/           分页、RequestState、品牌 ID
shared/event-bus.ts     跨页面事件表
```

---

### 2. API 类型、领域类型、组件类型

```ts
type UserDTO = {
  user_id: number;
  user_name: string;
};

type User = {
  id: number;
  name: string;
};

function toUser(dto: UserDTO): User {
  return { id: dto.user_id, name: dto.user_name };
}
```

| 层 | 谁定义 | 组件能不能直接用 |
| --- | --- | --- |
| `UserDTO` | 生成或按文档手写，属于传输 | 不能。字段名和多余字段会漏进 UI |
| `User` | 领域类型，由映射函数产出 | 能。这是页面和 state 的类型 |
| `UserSelect` 的 props | 写在组件旁边 | 只服务这个组件 |

小项目可以手写 DTO。接口一多，就用 OpenAPI 生成，生成文件不要改。映射可以手写，也可以让返回类型从映射函数推出来，但不要把 DTO 用 `as User` 断言过去。断言过了，`user_name` 和 `name` 对不上时编译器不会说话。

`global.d.ts` 只放确实全局的东西，比如给 `Window` 补字段。业务 `User` 放进去之后，任何模块都能偷偷依赖它，重构时找不到真正的边界。声明合并怎么补全局字段，见 [type 和 interface](/md/TypeScript/type%20和%20interface.md)。

### 3. 让通用组件自己把类型推出来

```tsx
type Option<T> = {
  label: string;
  value: T;
};

type SelectProps<T> = {
  options: readonly Option<T>[];
  value: T;
  onChange: (value: T) => void;
};

function Select<const T>({ options, value, onChange }: SelectProps<T>) {
  return (
    <div>
      {options.map((item) => (
        <button
          type="button"
          key={item.label}
          aria-pressed={Object.is(item.value, value)}
          onClick={() => onChange(item.value)}
        >
          {item.label}
        </button>
      ))}
    </div>
  );
}
```

调用时不写 `<string>` 或 `<number>`。`T` 从 `options` 和 `value` 一起推。

```tsx
<Select
  options={[
    { label: "开", value: "on" },
    { label: "关", value: "off" },
  ]}
  value="on"
  onChange={(next) => {
    // next 是 "on" | "off"
    return next;
  }}
/>
```

| 写法 | `onChange` 拿到什么 | 原因 |
| --- | --- | --- |
| `function Select<const T>`，选项值是字面量 | `"on" \| "off"` | `<const T>` 要求按字面量推断，这是 TypeScript 5.0 起的写法 |
| 只写 `function Select<T>` | `string` | 普通类型参数会把字面量扩成 `string`，每个值上再写 `as const` 也推不回联合 |
| `value` 是 `1`，`onChange` 按 `string` 来写 | 报错 | 两个推断位置对不上，不能合成一个 `T` |
| 只有 `onChange`，没有 `options` / `value` | `unknown` | 没有能推出 `T` 的参数 |

类型参数要放在函数上：`function Select<const T>(props: SelectProps<T>)`。`<const T>` 负责保住字面量。不要写成 `const Select: React.FC<SelectProps<T>>`。`React.FC` 要的是一份已经确定的 props，`T` 在那个位置还不存在，调用方也无法再推断。React 19 里 `ref` 可以当普通 prop，泛型函数组件不必再包一层 `forwardRef`。更早的 `forwardRef` 经常把额外的类型参数弄丢，所以新组件优先把 `ref` 写进 props。

两个无关的值不要共用一个 `T`。比如下拉的值和列表的 id 并不是同一个类型，硬写成一个参数，推断会变成它们的交叉，调用时怎么传都不对。没有关联的字段就分开标。

### 4. 类型安全的 `useRequest`

钩子要做两件事：从请求函数推出数据的类型，并且不让「加载中」和「数据已就绪」同时成立。

```tsx
import { useEffect, useState, type DependencyList } from "react";

type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

function useRequest<T>(query: () => Promise<T>, deps: DependencyList): RequestState<T> {
  const [state, setState] = useState<RequestState<T>>({ status: "idle" });

  useEffect(() => {
    let cancelled = false;
    setState({ status: "loading" });

    query()
      .then((data) => {
        if (!cancelled) setState({ status: "success", data });
      })
      .catch((caught: unknown) => {
        if (cancelled) return;
        const error = caught instanceof Error ? caught : new Error(String(caught));
        setState({ status: "error", error });
      });

    return () => {
      cancelled = true;
    };
  }, deps);

  return state;
}
```

```tsx
const state = useRequest(() => fetchUser(id), [id]);

if (state.status === "success") {
  state.data.name;
}
```

`T` 来自 `() => Promise<T>` 的返回值。`fetchUser` 如果返回 `Promise<User>`，`state` 在成功分支里的 `data` 就是 `User`，调用处不用再写 `useRequest<User>`。依赖数组用 React 自己的 `DependencyList`，只表示这些值变了就重跑，不参与 `T` 的推断。

| 时刻 | `status` | 能读到的字段 |
| --- | --- | --- |
| 第一次渲染 | `idle` | 没有 `data`，也没有 `error` |
| effect 开始 | `loading` | 仍然没有 `data` |
| `fetchUser` 成功，且这轮没被取消 | `success` | `data` 是 `User` |
| 请求抛错 | `error` | `error` 是 `Error`，不是 `unknown` |
| `id` 变了，上一轮后返回 | 保持新一轮的状态 | `cancelled` 拦住旧结果，不会把旧 `User` 写回来 |

`catch` 的值是 `unknown`，进状态之前收成 `Error`。否则错误分支又把 `unknown` 散到组件里。

`deps` 不要写成「把 `query` 放进依赖」。内联的 `() => fetchUser(id)` 每次渲染都是新函数，effect 会反复重来。依赖写真正会变的 `id`，和 React 别的 effect 一样。开发环境 Strict Mode 会多执行一次 effect，清理函数把上一轮标成取消，避免第一次的结果覆盖第二次。

这个钩子不解析 `{ code, data }` 信封。信封留在 `api/user.ts`，`fetchUser` 返回的已经是 `User`。组件不要同时知道传输字段和页面字段。

如果刷新时必须继续显示上一次的数据，不要把 `data` 偷偷加回 `loading`，那会把互斥打破。加一个明确的状态：`{ status: "refreshing"; data: T }`。旧数据只在这个状态里出现。

### 5. 判别联合，而不是三个布尔值

```ts
type BadState<T> = {
  loading: boolean;
  data?: T;
  error?: string;
};
```

`loading: true`、`data` 有值、`error` 也有值，类型上完全合法，渲染时每个组合都要猜。判别联合用一个字面量字段把组合限定死：`success` 才有 `data`，`error` 才有 `error`。

```tsx
function assertNever(value: never): never {
  throw new Error(`未处理的状态: ${JSON.stringify(value)}`);
}

function read<T>(state: RequestState<T>): T | string | undefined {
  switch (state.status) {
    case "idle":
    case "loading":
      return undefined;
    case "success":
      return state.data;
    case "error":
      return state.error.message;
    default:
      return assertNever(state);
  }
}
```

`assertNever` 的定义在 [any、unknown、never](/md/TypeScript/any%20unknown%20never.md)。四个 `case` 都写了，`default` 里的 `state` 是 `never`。以后加上 `"refreshing"` 却忘了渲染，编译会失败。

`status === "success"` 之后才能读 `data`。`read` 的返回值在成功时是 `T`，加载时没有数据。这是收窄，不是断言。收窄的其他写法见 [类型守卫与类型收窄](/md/TypeScript/类型守卫与类型收窄.md)。

更新时替换整份状态，不要在旧对象上改布尔值：

```ts
setState({ status: "success", data: user });
```

从 `error` 再请求，就整份换成 `loading`。旧的 `error` 不会残留，因为新对象上没有这个字段。

### 6. 类型安全的 EventBus

事件名和载荷放在一张表里。`on` 和 `emit` 用同一个键，把载荷从这张表里取出来。

```ts
type AppEvents = {
  "user:login": { id: string };
  "cart:add": { sku: string; count: number };
};

type EventBus<E extends Record<string, unknown>> = {
  on<K extends keyof E>(type: K, handler: (payload: E[K]) => void): () => void;
  emit<K extends keyof E>(type: K, payload: E[K]): void;
};

function createEventBus<E extends Record<string, unknown>>(): EventBus<E> {
  const listeners = new Map<keyof E, Set<(payload: any) => void>>();

  return {
    on(type, handler) {
      const set = listeners.get(type) ?? new Set<(payload: any) => void>();
      set.add(handler as (payload: any) => void);
      listeners.set(type, set);
      return () => {
        set.delete(handler as (payload: any) => void);
      };
    },
    emit(type, payload) {
      listeners.get(type)?.forEach((handler) => handler(payload));
    },
  };
}
```

```ts
const bus = createEventBus<AppEvents>();

const off = bus.on("user:login", (user) => user.id);
bus.emit("user:login", { id: "1" });
off();
```

| 调用 | 结果 |
| --- | --- |
| `on("user:login", user => user.id)` | `user` 是 `{ id: string }` |
| `emit("user:login", { id: "1" })` | 通过 |
| `emit("user:login", { id: 1 })` | 报错，`id` 不是 `string` |
| `emit("cart:add", { sku: "a" })` | 报错，缺 `count` |
| `on("logout", ...)` | 报错，事件名不在表里 |

Map 里用了 `any`，是因为一个 `Set` 存不下「这个键对应这个载荷」的关联。监听函数的参数更具体，不能直接放进 `(payload: any) => void`，所以只在放进 Map 时断言一次。对外的 `on` / `emit` 仍然用 `E[K]`，调用方接触不到这个 `any`。

没有载荷的事件不要省略参数后又在类型里变成可选。表里写成 `undefined`，`emit("modal:close", undefined)`，这样每个事件的参数个数都一样，实现不用再做条件元组。卸载时调用 `on` 返回的函数，不在组件外面留一个永远不删的监听。

跨页面的事件才放进这张全局表。一个功能内部的回调仍然用 props，不要为了类型安全把所有点击都做成事件。

### 7. 设计取舍

| 选择 | 得到 | 代价 |
| --- | --- | --- |
| 生成 DTO，手写领域类型 | 后端字段改动停在映射 | 多一层函数，不能 `as` 混过去 |
| 泛型放在组件函数上 | 调用方不用手写类型参数 | 无关字段不能共用一个 `T` |
| 请求状态用判别联合 | 读 `data` 时一定已经成功 | 要保留旧数据就得加 `refreshing`，不能偷偷把 `data` 加回 `loading` |
| EventBus 用事件表 | 事件名和载荷绑定 | Map 内部有一处不外泄的 `any`；功能内通信仍优先 props |
| `shared` 只放跨业务类型 | 依赖方向清楚 | 什么都往里放，会变成新的全局垃圾场 |

## 常见误区

### ❌ 有了 OpenAPI，组件里直接用生成类型就行

### ✅ 更准确的说法

生成类型停在 API 模块。组件依赖映射之后的领域类型。传输字段和页面字段不是同一个类型。

### 为什么？

生成类型一改，所有直接引用它的组件都会红，而且页面会依赖 UI 不该知道的字段。

---

### ❌ `React.FC<Props<T>>` 也能把 `T` 推断出来

### ✅ 更准确的说法

`T` 必须写在函数声明上。`React.FC` 固定的是一份已经确定的 props，调用方没有类型参数可以推。

### 为什么？

推断需要一个还没被填上的类型参数。先把 `T` 定死，选项再怎么传也只是在检查，不会反过来决定 `T`。

---

### ❌ `loading`、`data`、`error` 三个可选字段更灵活

### ✅ 更准确的说法

三个字段可以同时存在，类型允许非法组合。判别联合让 `data` 只出现在 `success`。

### 为什么？

渲染时要为每一种组合写防御代码，漏一个就可能对 `undefined` 点属性。联合把组合在类型里删掉。

---

### ❌ EventBus 写成 `(event: string, payload: any)` 再在业务里断言

### ✅ 更准确的说法

事件名和载荷放进同一张表，`emit` 的参数是 `E[K]`。`any` 如果出现，只能留在 Map 的实现里，不能出现在监听函数的参数上。

### 为什么？

公开签名一旦是 `any`，传错字段不会报错，类型安全只剩一个名字。

## 高频追问

### 通用下拉的类型参数放哪？为什么有时会推成 `unknown`？

放在 `function Select<const T>(props: SelectProps<T>)` 上。`<const T>` 才不会把 `"on"` 扩成 `string`。`options` 和 `value` 给推断提供位置。两个位置类型不一致会报错；如果谁都不传具体值，`T` 没有来源，就会变成 `unknown`。

### `useRequest` 的 `T` 从哪来？为什么不手写类型参数？

从 `query` 的返回值 `Promise<T>` 推。手写 `useRequest<User>` 在函数返回值改了之后可能和真实数据不一致。依赖数组不要参与这个推断。

### 刷新时想留着上一次的数据，怎么改这个联合？

不要把 `data` 加进所有 `loading`。增加 `{ status: "refreshing"; data: T }`，旧数据只在这个状态可读。

### 判别联合怎么发现漏掉的分支？

`switch` 的 `default` 调用参数为 `never` 的 `assertNever`。新状态没人处理时，那个值不再是 `never`。

### EventBus 里那处 `any` 为什么可以留下？

Map 保存的是不同事件的函数，类型系统关联不了「键 `K`」和「集合里的函数」。对外签名仍是 `E[K]`，`any` 不进入业务回调。

### 老项目怎么开始补这些类型？

先让 JS 和 TS 共存。先补 API 映射、公共组件和高频页面，不要先把所有文件改成 `.tsx`。`any` 可以留在补不上的第三方调用点，但不要作为模块的返回类型。
