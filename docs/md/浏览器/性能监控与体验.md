# 性能监控、可靠性与体验

## 面试回答

> 性能我分两套数据。实验室里用 Lighthouse 和 Performance 找原因；线上用真实用户监控看分布。Core Web Vitals 看的是每次访问的 75 分位，手机和桌面分开，不能拿自己电脑上的一次成功代替用户。LCP 是视口里最大的那块内容何时画出来，好的线在 2.5 秒。INP 是点击、按键之后到下一帧画出来的延迟，好的线在 200 毫秒；它在 2024 年 3 月取代了只看第一次输入延迟的 FID。CLS 是非预期布局跳动的会话窗口分数，好的线在 0.1。
>
> 从零建监控，我会在应用壳里采这三项，带上版本、路由和设备，在页面隐藏时用 `sendBeacon` 送出。告警看的是新版本相对基线的回归，并且要能追到 LCP 元素或 INP 的目标节点，而不是只收到一个变红的数字。
>
> 几千条记录的页面，我先问用户是不是必须一次看见全部。能分页就分页。必须连续滚动时做虚拟列表：只挂视口上下附近的行，用总高度撑开滚动条。纯计算丢给 Web Worker，Worker 不能碰 DOM，结果还是回主线程再画。React 里输入和重列表拆开，列表更新放进 transition；这能让输入先响应，但不会减少最终提交的 DOM，所以代替不了虚拟列表。
>
> 多余渲染用 Profiler 看是谁在这次交互里执行了，以及 props、state 还是 context 变了。先把状态下沉，再对稳定叶子使用 `memo`。异常监控收 `window` 错误、未处理的 Promise 拒绝和 Error Boundary 的组件栈，用版本对应的 source map 还原。恢复按路由或区块兜底，并防止资源版本错位时无限刷新。
>
> 用户说卡、我又复现不了，就去对那次访问的设备、数据量和版本，用 CPU 降速和同样的数据量再录一条 Performance。灰度用同一份不可变制品按人群切开，对照错误率和体验指标；能关开关就先关开关，否则把入口 HTML 指回仍留在 CDN 上的上一版资源。

**一句话总结：**

> 字段 p75 的 LCP / INP / CLS → 归因到元素和版本 → 大列表只挂视口 → 长计算进 Worker、长渲染要切片 → 错误可还原可恢复 → 灰度对照后回滚入口而不是重打一份未知包。

## 核心原理

### 1. 为什么要先分实验室和线上

实验室把机器、网络和缓存控制住，适合回答「慢在哪一步」。线上每个用户的 CPU、数据量和第三方脚本都不同。Core Web Vitals 的站点评分取的是页面访问的 **75 分位**，手机和桌面分开算。桌面中位数很好，不能说明手机上的 75 分位过线。

| | 实验室 | 线上真实用户 |
| --- | --- | --- |
| 工具 | Lighthouse、Performance 面板 | `web-vitals`、`PerformanceObserver`、RUM |
| 看什么 | 一次受控加载的瀑布和主线程 | 版本、路由、设备上的分布 |
| 适合 | 找 LCP 元素、长任务、布局抖动 | 判断这次发布有没有让多数用户变差 |

---

### 2. 监控怎么接上

```text
页面启动
  → 尽早注册 LCP / INP / CLS / long task
  → 指标就绪或页面隐藏时回调
  → 附上 release、路由、设备、网络
  → sendBeacon 送到采集端
  → 按页面模板聚合 p75
  → 和上一版本对照，退化再告警
```

注册要早，并且打开 `buffered`，否则观察者创建之前的 LCP 会丢。LCP 和 CLS 会随着加载被改写，INP 要等交互发生，所以真正上报常常在 `visibilitychange` 或页面关闭时。`sendBeacon` 允许页面离开时仍把这一小段 JSON 送走。

采样可以省流量，但必须按页面访问无偏抽样。若只上报「你觉得慢」的会话，p75 就不可比。告警不要钉死一个全局毫秒数。同一路由、同一设备档，新版本的 p75 相对基线持续变差，才值得叫人。单次访问的尖刺留在明细里查。

归因比分数重要。`web-vitals` 的 attribution 构建能带上 LCP 是哪个元素、INP 点的是哪个目标、等待分成输入延迟、处理时间和绘制延迟，以及 CLS 偏移最大的节点。没有这些，告警只是「变慢了」。

---

### 3. LCP、INP、CLS 各量什么

三者都是现场指标。实验室分数可以帮忙，但不能代替 75 分位。

| 指标 | 量什么 | 好 / 差 | 一次访问里怎么取值 |
| --- | --- | --- | --- |
| LCP | 视口内最大的图片、视频或文本块第一次画出来的时间 | ≤ 2.5s 好，> 4s 差 | 用户点击、滚动或按键后不再更新候选 |
| INP | 点击、轻触、按键从发生到下一帧绘制 | ≤ 200ms 好，> 500ms 差 | 交互少时取最慢的一次；每 50 次交互忽略一个最高值 |
| CLS | 用户没操作时，可见内容意外挪动了多少 | ≤ 0.1 好，> 0.25 差 | 取最大的会话窗口，不是从打开到关闭全部加总 |

LCP 的候选包括 `img`、SVG 里的 `image`、视频的海报或第一帧、用 `url()` 画出的背景图，以及成块的文本。算的是视口里可见的那一块有多大。优化时先在 Performance 里点出那个元素，再看它是等接口、等图片，还是等主线程有空才画。

INP 把一次交互拆成三段：事件开始前的输入延迟、事件处理、处理完到下一帧绘制。滚动和缩放不算。只优化点击回调还不够，回调前后的长任务和这次更新触发的布局都会算进去。2024 年 3 月起它取代 FID。FID 只看第一次输入等到处理开始的时间，不看处理本身，也不看后面的交互。

CLS 的单次分数大约是「受影响的可见面积比例 × 移动距离比例」。用户输入后约 500 毫秒内的挪动算预期，不计入。其余挪动放进会话窗口：中间空档超过 1 秒就收口，单个窗口最长约 5 秒。页面的 CLS 取这些窗口里最大的一个。所以无限下拉后面的小抖动，不会把开头那一下大跳动平均掉。

---

### 4. 几千条记录的页面

先减少要画的东西，再减少要算的东西。

```text
用户需要一次看完全部吗？
  → 不需要：接口分页或游标，页面上只有一页
  → 需要连续滚动：虚拟列表，DOM 只保留视口附近
  → 卡在排序、过滤、解析：Worker 算完，把结果交回虚拟列表
  → 卡在输入时整表重渲染：输入状态和列表状态拆开
```

五千行、每行四十像素，全部挂到文档里就是二十万像素高的 DOM。滚动时浏览器要为这些节点做样式和布局，React 还要协调它们。用户视口通常只有十行上下。

#### Trace：固定行高的窗口

一万行，行高 40，视口 400，`scrollTop` 为 2000，上下各多留 2 行。

| 量 | 计算 | 结果 |
| --- | --- | --- |
| 起始行 | `floor(2000 / 40)` | 50 |
| 视口能放下 | `ceil(400 / 40)` | 10 行，也就是 `[50, 60)` |
| 加上 overscan | 两端各 2 行 | 实际挂载 `[48, 62)`，14 个节点 |
| 窗口偏移 | `48 * 40` | 1920 |
| 滚动内容总高 | `10000 * 40` | 400000 |

总高用来撑开滚动条。14 个节点放进一个容器，再用 `translateY(1920px)` 推到滚动位置。快速滚动时，overscan 的那几行已经在视口外准备好，减少空白。

行的 key 用数据 id。若用窗口里的槽位下标当 key，组件状态会粘在槽位上，滚到下一行时输入框里仍是上一行的字。

行高不固定时，不能再用除法。先按估计高度撑开，渲染后测量真实高度，做前缀和，用二分查找定位 `scrollTop` 落在哪一行。测量结果要缓存，否则每滚一次都重新布局。

总高度特别大时，单个元素可能撞上浏览器的高度上限。这时改成分段撑开或分页，而不是继续加一个更长的空 div。

### 5. React 里不必要的渲染，以及主线程被堵住

父组件执行时，子组件默认也会再执行。`React.memo` 用 props 的浅比较跳过；函数组件自己的 bailout 看的是 props 引用是否同一个，并且这条 Fiber 上没有待处理的更新。Context 的 value 换了新对象，消费者也会执行。Bailout 的条件见 [Fiber 架构](/md/框架/React/Fiber架构.md)。

定位按这一次交互，不按感觉：

```text
Profiler 录下点击或输入
  → 哪些组件执行了、耗时多久
  → 原因是 props、state、hook 还是 context
  → props 变了的话，是不是渲染里新建的对象或函数
  → 先把状态放到真正用它的子树
  → 叶子的 props 已经稳定，再 memo
```

一个对象字面量 `style={{ color }}` 或内联函数，每次渲染都是新引用，`memo` 的浅比较会失败。这是引用变了，不是 React 随机多渲染。

主线程上，单个任务超过约 50 毫秒会被记成长任务。浏览器要等这个任务结束才能处理下一次输入和绘制。所以几千行的 `setState` 即使被批处理合成一次渲染，这次渲染本身仍可能是长任务。

| 手段 | 解决的部分 | 留在主线程的部分 |
| --- | --- | --- |
| 分页、虚拟列表 | 提交到文档的节点数 | 当前窗口那十几行 |
| `startTransition` | 输入先画，列表渲染可让出 | 列表最终仍会在主线程协调和提交 |
| 任务切片、`scheduler.yield()` | 把长循环拆开，中间能响应 | 拆开的每一小段 |
| Web Worker | 排序、过滤、解析不占主线程 | 把结果应用到 DOM |

`startTransition` 不会把协调搬进 Worker。列表如果仍要提交几千个 DOM，过渡只是让卡顿晚点出现。长循环的切片原理见 [浏览器事件循环](/md/浏览器/浏览器的事件循环.md)。

### 6. Web Worker 的边界

Worker 适合从主线程搬出去的 CPU 活：大列表排序过滤、图表降采样、文件解析、压缩、哈希。不适合校验一个短字符串，也不适合每次 `mousemove` 都发一次消息。

它和页面之间是消息，不是共享普通对象。`postMessage` 默认结构化克隆，大的 `ArrayBuffer` 可以转移所有权，转移后原来的线程不能再读这块缓冲。`SharedArrayBuffer` 才能真正共享内存，还要求跨源隔离，普通业务很少需要。

Worker 没有 `document`。算完的行数据要回主线程，由虚拟列表决定挂哪些节点。通信、创建线程和多出来的内存都是成本。Performance 里先确认长任务确实是可拆出去的计算，再上 Worker。细节见 [Web Worker](/md/浏览器/Web%20Worker.md)。

### 7. 异常监控和错误恢复

采集面要盖住渲染和渲染之外：

| 来源 | 能接到什么 | 接不到什么 |
| --- | --- | --- |
| `window.onerror` | 同步脚本错误 | 跨域脚本常常只剩 `Script error.` |
| `unhandledrejection` | 没人接的 Promise | 已经被 `catch` 的失败 |
| Error Boundary | 后代渲染和生命周期里的错误，以及组件栈 | 事件处理、普通异步、Boundary 自己 |
| 资源捕获 | 脚本、样式、图片加载失败 | 接口业务错误 |

React 19 的 `createRoot` 还可以用 `onUncaughtError`、`onCaughtError` 区分没被接住和已经被 Boundary 接住的渲染错误。上报字段至少有：消息、还原后的栈、release、路由、用户或租户、最近几步操作。source map 按这个 release 上传到平台，不要为了方便把完整 map 公开给所有访问者。跨域脚本要带 CORS，否则栈还原不了。

指纹用「版本 + 消息 + 栈顶帧」合并重复。浏览器扩展、`ResizeObserver loop` 这类已知噪声单独过滤，避免把告警打满。

恢复按块，不按整页白屏。壳子留着，出错的路由或卡片显示重试。发版后旧页面动态加载的 chunk 404，是入口 HTML 和带 hash 的资源不一致。可以自动刷新一次，并用 `sessionStorage` 记住已经刷新过，避免死循环。用户正在填的内容要先留在内存或本地，再刷新。

### 8. 反馈很卡，但本地不复现

本地流畅只说明这台机器、这份数据和这个版本没问题。先把反馈对齐到一次真实访问：

```text
发生时间、账号、路由、release
  → 设备、CPU 核数、内存档、网络
  → 该次会话的 INP、长任务、接口体积
  → 用同样的数据量，并把 CPU 降到 4 到 6 倍再录 Performance
  → 仍没有，就看是不是长时间停留后的内存增长、扩展或第三方脚本
```

只在低端安卓上出现的卡顿，优化目标是那一档设备的 p75，不是开发机的 Lighthouse。能让用户导出一段 Performance 录制，比反复问「还卡吗」有用。没有录制时，RUM 里同一路由、同一设备档的长任务脚本名，就是下一次实验的入口。

### 9. 灰度、告警和回滚

流水线产出一份不可变制品：带 hash 的 JS/CSS，加上指向它们的 `index.html`。灰度改变的是谁拿到新的 HTML，或谁的功能开关打开，不是在服务器上再打一个来历不清的包。制品和卡点见 [CI/CD](/md/工程化/体系与实践/CI&CD.md)。

```text
内部账号
  → 小比例用户，和未进入灰度的人对照
  → 看错误率、LCP/INP 的 p75、一个业务成功率
  → 没有持续回归再放大
  → 回归则先关开关；开关盖不住就切回上一份 HTML
```

旧的带 hash 资源要在 CDN 上留一段时间。回滚只改入口 HTML 时，浏览器仍能拿到旧包。若发布完立刻删掉旧资源，回滚会变成 404。

开关比重新部署快，但它救不了「新包一执行就崩、开关代码还没跑到」的故障。那种情况必须切 HTML。接口或数据如果已经按新版本写入，只回滚前端会让旧页面读不懂新数据。这种变更要先扩展字段、两边都能读，再删旧字段。

告警绑在灰度组和控制组的差值上，持续几分钟再通知能回滚的人。绝对阈值可以留作兜底，但不能代替对照，否则白天流量上来就会误报。

### 10. 设计取舍

| 选择 | 得到 | 代价 |
| --- | --- | --- |
| 只信 Lighthouse | 本地能复现实验 | 看不到低端设备和真实数据 |
| 虚拟列表 | DOM 数量跟视口走 | 不定行高要测量；搜索、无障碍和滚动恢复要单独做 |
| 全量 `memo` | 少数叶子会跳过 | 比较本身有成本，挡不住状态放错层 |
| Worker | 主线程能响应用点击 | 消息克隆和回主线程画 DOM 的成本还在 |
| 功能开关灰度 | 秒级关掉一条新路径 | 启动即崩溃的包仍要回滚 HTML |
| 错误全量上报 | 不漏单次异常 | 噪声和费用；要指纹、采样和过滤 |

## 常见误区

### ❌ FID 仍是当前的 Core Web Vital

### ✅ 更准确的说法

2024 年 3 月起，交互指标是 INP。它覆盖整次访问里的点击和按键，并包含处理时间和下一帧，不只是第一次输入等多久才开始处理。

### 为什么？

只优化第一次点击的等待，后面每次输入的长任务仍然会让页面看起来卡。

---

### ❌ CLS 把页面从打开到离开的所有偏移加在一起

### ✅ 更准确的说法

算的是最大的一段会话窗口。用户输入后约 500 毫秒内的偏移不计。

### 为什么？

若按全程累加，长页面会被后面许多次小挪动判成很差，开头那次真正的跳动反而看不清。

---

### ❌ 虚拟列表就是把看不见的行设成 `display: none`

### ✅ 更准确的说法

视口外的行不要创建。用总高度撑开滚动条，只挂载窗口里的节点，并用数据 id 做 key。

### 为什么？

`display: none` 的节点仍在文档里，创建和协调的成本还在。用槽位下标做 key，状态会串行。

---

### ❌ `startTransition` 或 Worker 可以替掉虚拟列表

### ✅ 更准确的说法

过渡让输入先画出来，Worker 搬走纯计算。几千个 DOM 的提交仍在主线程，还是要减少挂载数量。

### 为什么？

卡顿若来自布局和提交，计算挪走之后绘制仍然重。

---

### ❌ 用户说卡但本地流畅，就当成个例关掉

### ✅ 更准确的说法

对齐那次访问的设备、数据量和版本，用降速和同样的数据再录。优化目标是那一档的线上分布。

### 为什么？

开发机的一次加载不在 75 分位的定义里。

---

## 高频追问

### 前端性能监控从零怎么建？

壳里尽早采集 LCP、INP、CLS 和长任务，带上版本、路由、设备，页面隐藏时 beacon 出去。按模板和设备看 p75，用归因找到元素或脚本。告警比较的是新版本相对基线，采样必须无偏。

### LCP、INP、CLS 的线和取值规则是什么？

LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1 算好。站点看 75 分位，手机和桌面分开。INP 在交互很多时每 50 次丢掉一个最高值。CLS 取最大会话窗口。

### 几千条记录怎么做？虚拟列表的窗口怎么算？

能分页就分页。连续滚动时用 `scrollTop / 行高` 得到起始行，只挂视口加上 overscan 的节点，总高度撑开滚动条。key 用数据 id。不定行高改为测量、前缀和和二分查找。

### React 多余渲染怎么定位？主线程被大更新堵住怎么办？

Profiler 看这次交互里谁执行了，以及 props 引用、state、context 哪一个变了。先状态下沉，再 memo。虚拟列表减少 DOM，transition 保住输入，Worker 搬走纯计算，长循环再切片。

### Worker 适合什么，不适合什么？

适合排序、解析、压缩这种可搬离的 CPU 活。不能碰 DOM。默认是克隆消息，大缓冲可以转移所有权。很小的任务和必须马上改界面的逻辑留在主线程。

### 异常怎么监控，页面怎么恢复？

同步错误、未处理拒绝、Error Boundary 和资源失败分开接。用 release 对应的 source map 还原栈，按指纹去重。路由级兜底加重试；chunk 404 只自动刷新一次。

### 反馈很卡，本地不复现，怎么办？

拿到时间、路由、版本和设备，查那一档的 INP 和长任务。用同样数据量并降低 CPU 再录 Performance。没有现场数据，就不要用开发机的流畅否定反馈。

### 灰度和回滚怎么设计才不会半发布？

同一份带 hash 的制品，按人群切 HTML 或开关。对照错误率和 p75，再放大。旧资源留在 CDN。开关关不掉的启动崩溃，切回上一份 HTML。数据格式不兼容时，前端回滚要和接口的兼容窗口一起看。
