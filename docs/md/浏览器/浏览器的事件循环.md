# 浏览器的事件循环

## 面试定位

事件循环是浏览器方向的必考题，但很少只考「宏任务微任务谁先执行」。有经验的面试官会按一条追问链一层层往下钻，直到你答不出为止：

```text
事件循环是为了解决什么？
        ↓
你知道宏任务 / 微任务吗？
        ↓
知道它们怎么执行吗？
        ↓
知道为什么微任务会阻塞渲染吗？
        ↓
知道宏任务为什么也可能卡吗？
        ↓
知道定时器为什么不准吗？
        ↓
知道 setTimeout 和 setInterval 的区别吗？
        ↓
那你能不能解释浏览器到底怎么调度 JavaScript？
```

这条链背后只有一个考点：**主线程是稀缺资源，事件循环是主线程的调度器**。所有「卡不卡」「准不准」的问题，都是在问「这段代码什么时候能拿到主线程，拿到后占多久，渲染有没有机会插进来」。

常见失分点：

- 只会背 `1 4 3 2` 输出题，讲不出渲染在哪一步。
- 以为「微任务多会卡，宏任务多不会卡」，说不清两种卡的差别。
- 把定时器不准归结为「JS 单线程」四个字，说不出排队、最小延时、后台节流三个原因。
- 说不出 `setInterval` 的「丢拍」和「重叠」问题。

本文按这条追问链组织，每一节对应一层追问，可以直接顺着往下背。

## 面试回答

可以这样答（对应第一层问题，后面几层见各节的「口述版」）：

> 浏览器里 JavaScript 和渲染共用一个主线程，事件循环就是这个主线程的调度器。它每一轮先从任务队列取一个宏任务执行，执行完立刻清空微任务队列，然后看是否到了渲染时机，需要的话跑一遍样式、布局、绘制，再回头取下一个宏任务。
>
> 微任务包括 Promise.then、await 后续、queueMicrotask、MutationObserver，它们在当前宏任务结束后、渲染之前全部清空，所以微任务里持续追加微任务会把渲染彻底饿死，页面直接假死。宏任务像 setTimeout、事件回调、MessageChannel，每个宏任务之间都有渲染机会，所以持续追加宏任务不会假死，但如果单个任务超过 50ms 就会掉帧、输入延迟。
>
> 定时器不准是因为它只保证「到点后入队」，不保证「到点就执行」，前面排着的任务、嵌套后的 4ms 最小延时、后台标签页节流都会让它晚到。我在项目里做长列表和大屏渲染时，会用 Performance 面板看 Long Task，把超过 50ms 的同步计算切片或者丢到 Web Worker 里。

一句话总结：

> 事件循环 = 单线程主线程的调度器：取一个宏任务 → 清空微任务 → 有机会就渲染 → 下一个宏任务；卡顿的本质是主线程被占满，渲染插不进来。

## 核心原理

先给一张总图，后面每节都是在这张图上放大某一步。

```text
┌──────────────────────── 一轮事件循环 ────────────────────────┐
│                                                              │
│  1. 从任务队列取一个宏任务（task）执行                         │
│        同步代码直接进调用栈；异步 API 只是「登记回调」            │
│                                                              │
│  2. 调用栈清空后，执行微任务检查点（microtask checkpoint）       │
│        循环取微任务直到队列为空，新追加的也在这一步跑完          │
│                                                              │
│  3. 判断是否有渲染机会（rendering opportunity，约每 16.7ms 一次） │
│        有 → requestAnimationFrame → 样式 → 布局 → 绘制 → 合成    │
│        没有 → 跳过，直接回到 1                                  │
│                                                              │
│  4. 若这一帧还有空闲时间 → requestIdleCallback                 │
│                                                              │
└──────────────────────────── 回到 1 ──────────────────────────┘
```

| 追问层级 | 面试官在问什么 | 对应章节 |
| --- | --- | --- |
| 事件循环解决什么 | 你知不知道主线程是共享的 | §1 |
| 宏任务 / 微任务 | 你能不能正确分类 | §2 |
| 怎么执行 | 你能不能画出一轮循环 | §3 |
| 微任务为什么阻塞渲染 | 微任务检查点的位置 | §4 |
| 宏任务为什么也可能卡 | 渲染机会和长任务 | §5 |
| 定时器为什么不准 | 入队 ≠ 执行 | §6 |
| setTimeout vs setInterval | 调度方式差异 | §7 |
| 浏览器怎么调度 JS | 把上面所有点串成一帧 | §8 |

## 1. 事件循环是为了解决什么？

**问题的根源**：浏览器渲染进程的主线程要同时做四件事——执行 JavaScript、处理用户输入、计算样式和布局、绘制页面。JavaScript 被设计成单线程，是因为它要操作 DOM，多线程同时改 DOM 会带来复杂的锁和竞态问题。

单线程带来的问题是：**任何一段代码在跑的时候，其他所有事情都得等**。网络请求、定时器、用户点击如果都同步等待，页面就死了。

事件循环解决的是：

1. **异步不阻塞**：网络、定时器、I/O 交给浏览器其他线程去等，等完了把回调「登记」到队列，主线程空闲时再取出来执行。
2. **有序调度**：多个回调到期后，谁先执行有明确规则（任务队列 + 微任务队列）。
3. **给渲染留出时机**：在两个宏任务之间，浏览器有机会把页面画出来，响应用户。

口述版：

> 事件循环不是为了「实现异步」，异步是浏览器其他线程做的；事件循环是为了让单线程的主线程能在「执行回调」和「渲染页面」之间有序切换，不至于哪一边饿死。

**要点**：事件循环是调度器，不是执行器。回答这一层时把「渲染」说出来，后面几层才接得上。

## 2. 宏任务和微任务是什么？

HTML 规范里其实没有「宏任务」这个词，只有 task（任务）和 microtask（微任务）。「宏任务」是社区叫法，指的就是 task。

| 维度 | 宏任务（task） | 微任务（microtask） |
| --- | --- | --- |
| 常见来源 | `script` 整体代码、`setTimeout` / `setInterval`、用户交互事件、网络 I/O 回调、`MessageChannel`、`postMessage` | `Promise.then/catch/finally`、`await` 之后的代码、`queueMicrotask`、`MutationObserver` |
| 队列数量 | 可以有多个队列（按任务源分），浏览器可以给不同队列不同优先级，例如用户输入优先于定时器 | 只有一个微任务队列 |
| 每轮执行几个 | 一轮只取一个 | 一轮全部清空，包括执行过程中新追加的 |
| 与渲染的关系 | 两个宏任务之间有渲染机会 | 微任务和渲染之间没有间隙，渲染必须等微任务队列空 |

两个容易混的点：

- `requestAnimationFrame` 既不是宏任务也不是微任务，它属于渲染阶段的回调，在样式计算之前执行。
- `async/await` 本质是 Promise，`await` 后面的代码相当于放进 `.then`，走微任务。

```js
console.log(1);

setTimeout(() => console.log(2), 0);

Promise.resolve().then(() => console.log(3));

(async () => {
    console.log(4);
    await null;
    console.log(5); // await 之后 = 微任务
})();

console.log(6);

// 1 4 6 3 5 2
```

**要点**：分类时顺手说一句「微任务只有一个队列、必须一次清空」，这是后面「为什么阻塞渲染」的伏笔。

## 3. 它们是怎么执行的？

把 §核心原理 的总图具体到一次完整的执行：

```text
取宏任务 A
  ├─ 执行同步代码（进调用栈）
  ├─ 遇到 setTimeout → 交给定时器线程，到期后回调入宏任务队列
  ├─ 遇到 Promise.then → 回调入微任务队列
  └─ 调用栈清空
微任务检查点
  ├─ 取微任务 1 执行 → 又产生微任务 3 → 追加到队尾
  ├─ 取微任务 2 执行
  ├─ 取微任务 3 执行
  └─ 队列空
渲染机会（如果到了刷新时间点）
  └─ rAF → 样式 → 布局 → 绘制 → 合成
取宏任务 B
  └─ ……
```

两个细节经常被追问：

**Promise 构造函数是同步的，`then` 才是异步的**

```js
console.log("start");

new Promise((resolve) => {
    console.log("executor"); // 同步执行
    resolve();
}).then(() => {
    console.log("then"); // 微任务
});

console.log("end");

// start executor end then
```

**微任务嵌套会在同一个检查点里全部跑完**

```js
Promise.resolve().then(() => {
    console.log("A");
    Promise.resolve().then(() => console.log("B")); // 追加到同一轮微任务队列
});

setTimeout(() => console.log("C"), 0);

// A B C   —— C 必须等 A、B 都跑完
```

**要点**：微任务检查点是「清空到底」，不是「执行当前已有的那几个」。这就是 §4 的全部答案。

## 4. 为什么微任务会阻塞渲染？

面试原题：**如果一个微任务后面不断增加微任务，会卡顿吗？**

结论：**会，而且是最严重的那种卡——页面完全假死**，点击无响应、动画停止、最后浏览器弹「页面无响应」。

原因回到 §核心原理 总图的第 2 步和第 3 步：渲染机会在微任务检查点**之后**，而微任务检查点的规则是「循环取微任务直到队列为空」。只要队列一直不空，检查点就永远不结束，第 3 步永远到不了。

```js
// 微任务自我追加：页面直接假死
function loop() {
    queueMicrotask(loop); // 每执行一个就再追加一个，队列永远不空
}
loop();
```

从主线程视角看，这段代码和 `while (true) {}` 没有任何区别：

```text
宏任务 A 结束
  → 微任务检查点开始
      loop → 追加 loop → loop → 追加 loop → ……   ← 永远停在这一步
  → （渲染机会）                                    ← 永远到不了
  → （下一个宏任务：用户点击）                       ← 永远到不了
```

更危险的变体是**指数增长**：一个微任务追加两个，队列长度会爆炸式增长，内存很快耗尽。

```js
function boom() {
    queueMicrotask(boom);
    queueMicrotask(boom); // 1 → 2 → 4 → 8 …… 很快 OOM
}
```

实际项目里不会有人故意写死循环，真实的坑长这样：

- 在 `.then` 里递归处理一个很大的数组，每层处理一块，以为「异步了就不卡」——其实全在同一个微任务检查点里跑完，渲染一帧都插不进去。
- `MutationObserver` 回调里改 DOM，又触发新的 MutationObserver，形成微任务级别的循环。
- Vue 的 `watch` / React 的状态更新在微任务里互相触发，形成无限更新链。框架通常会检测并报错（Vue 会报 `Maximum recursive updates exceeded`），但检测之前主线程已经被占了一段时间。

正确做法是把「异步分片」放到宏任务粒度：`setTimeout`、`MessageChannel`、`scheduler.postTask` 或 `requestIdleCallback`，让每一片之间有渲染机会。

口述版：

> 微任务检查点的规则是清空到底，渲染排在检查点之后。所以微任务里不断追加微任务，等价于一个同步死循环，渲染和用户事件永远进不来，页面会直接假死。想异步分片，要用宏任务粒度，比如 setTimeout 或 MessageChannel。

**要点**：「微任务不给渲染留缝」，这是本节唯一需要记住的一句。

## 5. 宏任务为什么也可能卡？

面试原题：**如果一个宏任务不断追加宏任务，会卡顿吗？**

结论：**不一定假死，但很可能掉帧**。两种「卡」要分开说：

| 维度 | 微任务无限追加 | 宏任务无限追加 |
| --- | --- | --- |
| 渲染能不能插进来 | 不能，检查点永远不结束 | 能，每个宏任务之间都有渲染机会 |
| 用户事件能不能响应 | 不能 | 能，输入事件通常比定时器优先级高 |
| 表现 | 页面完全假死、浏览器提示无响应 | 每个任务很轻 → 基本无感；每个任务较重 → 掉帧、输入延迟 |
| 本质 | 一个永不结束的同步任务 | 很多个独立任务，卡不卡看单个任务耗时 |

先看「轻」的情况：

```js
// 每个任务几乎不耗时
function light() {
    setTimeout(light, 0);
}
light();
```

这段代码不会让页面卡死。每个 `light` 执行完就退出，主线程立刻空出来，渲染和点击都能插进去。代价是 CPU 一直在空转，耗电、发热，但用户感知不明显。（嵌套超过约 5 层后浏览器还会把最小延时抬到 4ms，见 §6。）

再看「重」的情况：

```js
// 每个任务占用 30ms
function heavy() {
    const start = performance.now();
    while (performance.now() - start < 30) {}
    setTimeout(heavy, 0);
}
heavy();
```

这时页面不会假死，但会明显卡：

```text
60Hz 下每帧预算约 16.7ms

heavy(30ms) → 渲染机会 → heavy(30ms) → 渲染机会 → ……
   ↑ 一个任务就吃掉近两帧的时间，渲染只能在任务缝隙里挤一下
   ↑ 用户点击要等当前 heavy 跑完才能处理，输入延迟 ≥ 30ms
```

浏览器只在两个宏任务**之间**有渲染机会，任务内部是不可打断的。所以宏任务卡不卡，看的是**单个任务的时长**，不是任务数量：

- 单个任务 < 16ms：基本不影响 60fps。
- 单个任务 > 50ms：被 Performance 面板标记为 **Long Task**，是 INP（Interaction to Next Paint）指标变差的主要原因。
- 单个任务 > 几秒：和微任务死循环体感一样，浏览器弹「无响应」。

宏任务级别的常见真实坑：

- 一次 `setTimeout` 回调里同步渲染几千个 DOM 节点。
- `scroll` / `resize` / `mousemove` 事件回调里做重计算，事件本身触发频率极高，每个回调又不轻。
- 定时器里做 JSON 大对象解析、复杂 diff。

解决方向：**切片 + 让出主线程**。把大任务拆成多个 < 5ms 的小任务，每片之间用 `setTimeout` / `MessageChannel` / `scheduler.yield()`（Chrome 129+ 稳定，其他浏览器需核实）让出主线程；或者干脆搬到 Web Worker。

口述版：

> 宏任务之间有渲染机会，所以不断追加宏任务不会假死，但如果单个宏任务超过 50ms，渲染只能在缝里挤一下，就会掉帧、输入延迟，Performance 里表现为 Long Task。微任务卡是「渲染进不来」，宏任务卡是「渲染来得太晚」。

**要点**：微任务问「有没有缝」，宏任务问「缝有多宽」。

## 6. 定时器为什么不准？

`setTimeout(fn, 100)` 的准确含义是：**至少 100ms 后，把 fn 放进宏任务队列**。它只保证「不早于」，不保证「恰好」。晚到有四个来源：

| 原因 | 机制 | 典型偏差 |
| --- | --- | --- |
| 排队等待 | 到期时主线程正在跑别的宏任务或微任务，必须等它们结束、再等队列前面的任务 | 取决于前面任务时长，几 ms 到几百 ms |
| 最小延时 | 嵌套调用超过约 5 层后，浏览器把小于 4ms 的延时抬到 4ms | 递归 `setTimeout(fn, 0)` 实测约 4ms 一次 |
| 后台节流 | 标签页不可见时，Chrome 把定时器限制到最多每秒一次；长时间后台后进一步降到每分钟一次 | 秒级到分钟级 |
| 渲染 / 优先级竞争 | 定时器任务源优先级通常低于用户输入和渲染相关任务，浏览器可能优先处理别的队列 | 一到几帧 |

最常见、也最该先说的是第一条：

```js
setTimeout(() => console.log("timer"), 100);

const start = Date.now();
while (Date.now() - start < 300) {} // 主线程被占 300ms

// "timer" 在约 300ms 后才打印，不是 100ms
// 定时器线程 100ms 时已经把回调入队了，但主线程在忙，取不到
```

```text
0ms      100ms                300ms
│ 同步 while 占用主线程 ──────────┤
│         ↑ 回调入队（准时）        ↑ 主线程空闲，才轮到它执行（晚了 200ms）
```

所以要说清楚：**「入队」是准的，「执行」是不准的**。这也是为什么 `setTimeout(fn, 0)` 不是「立刻执行」——它至少要等当前宏任务和所有微任务跑完。

需要精确节拍的场景（倒计时、动画、音频同步）不要相信 `setTimeout` 的间隔，而是每次执行时用 `performance.now()` 或 `Date.now()` 算真实流逝时间，用真实时间去修正下一次的延时或直接计算显示值。动画类直接用 `requestAnimationFrame`。

口述版：

> setTimeout 只保证到点后把回调入队，不保证到点就执行。主线程在忙就得排队，嵌套多了浏览器有 4ms 最小延时，后台标签页还会被节流到秒级甚至分钟级。所以需要精确计时时，我会用 performance.now() 算真实间隔来修正，动画用 rAF。

**要点**：定时器不准 = 排队 + 最小延时 + 后台节流。

## 7. setTimeout 和 setInterval 的区别

表面区别是「一次 vs 重复」，面试想听的是**调度方式的差异带来的两个坑**。

| 维度 | `setInterval(fn, 1000)` | 递归 `setTimeout(fn, 1000)` |
| --- | --- | --- |
| 下一次何时安排 | 浏览器按固定节拍安排，不管 fn 跑了多久 | fn 执行完才安排下一次 |
| fn 耗时 300ms 时的真实间隔 | 仍约 1000ms（fn 结束到下一次开始只剩约 700ms） | 约 1300ms（1000ms 等待 + 300ms 执行） |
| 主线程被阻塞 3s | 到期的回调不会排队补跑，浏览器最多保留一个待执行，中间几拍直接丢 | 只是整体推迟，本来就没有「补跑」概念 |
| fn 是异步操作（如 fetch） | 上一次请求没回来，下一次已经发出，可能重叠、乱序 | 可以在请求回来后再安排下一次，天然串行 |
| 动态调整间隔 | 需要 clear 再重新 set | 每次传不同的延时即可 |
| 停止 | `clearInterval(id)` | `clearTimeout(id)`，或者在递归里加条件不再调用 |

两个坑的口语版：

1. **丢拍**：`setInterval` 在主线程被占满时不会攒着多个回调等一起补跑，被跳过的那几次就没了。所以用它做倒计时，页面卡一下就会「跳秒」。
2. **重叠**：`setInterval` 里放 `fetch` 轮询，网络慢的时候会有多个请求同时在飞，后发的可能先回，状态被旧数据覆盖。

```js
// 轮询用递归 setTimeout，保证串行且可动态退避
let delay = 1000;

async function poll() {
    try {
        const res = await fetch("/api/status");
        const data = await res.json();
        delay = data.done ? 0 : 1000; // 根据结果决定要不要继续
    } catch {
        delay = Math.min(delay * 2, 30000); // 失败退避
    }
    if (delay) setTimeout(poll, delay);
}

poll();
```

补充：`setInterval` 的最小间隔同样受 4ms 限制，后台节流同样生效；组件销毁（React 卸载、Vue `onUnmounted`）时忘记 `clearInterval` 是经典内存泄漏和「组件已卸载还在 setState」告警的来源。

口述版：

> setInterval 按固定节拍安排下一次，不等回调执行完，所以主线程卡住会丢拍，回调是异步请求时会重叠。递归 setTimeout 是上一次跑完才安排下一次，天然串行，还能动态调整间隔。轮询类需求我一般用递归 setTimeout。

**要点**：`setInterval` 管节拍不管执行；递归 `setTimeout` 管执行不管节拍。

## 8. 浏览器到底怎么调度 JavaScript？

前面七层都是局部，这一层要把它们串成一帧。这是终极追问，能讲完整就是加分项。

### 8.1 线程分工

```text
渲染进程
├─ 主线程（Main Thread）
│    JS 执行 + 事件处理 + 样式计算 + 布局 + 绘制指令生成
├─ 合成线程（Compositor Thread）
│    把已绘制的图层合成为最终帧，可独立于主线程滚动 / 做 transform 动画
├─ 定时器 / 网络 / I/O 等辅助线程
│    等待完成后把回调「登记」进主线程的任务队列
└─ Web Worker 线程
     独立的 JS 执行环境，通过 postMessage 通信，不能碰 DOM
```

事件循环只调度主线程。合成线程独立，这是为什么 `transform` / `opacity` 动画在主线程忙的时候仍能流畅——它们不需要主线程参与。

### 8.2 任务队列有优先级

规范允许浏览器按任务源（task source）维护多个宏任务队列，并自行决定先取哪个。Chrome 的实现（Blink Scheduler）大致是：

```text
高 ── 用户输入（点击、键盘、触摸）
     渲染相关（rAF 之前需要处理的任务）
     网络加载完成回调
低 ── 定时器
     空闲任务（requestIdleCallback）
```

所以「宏任务队列是 FIFO」只在同一任务源内成立。一个 `setTimeout` 回调到期了，如果此时有用户点击排队，浏览器很可能先处理点击。这也是 §6 里「优先级竞争」导致定时器晚到的原因。

### 8.3 一帧里发生了什么

以 60Hz 为例，每帧约 16.7ms：

```text
│←──────────────────── 16.7ms ────────────────────→│
│ 宏任务 │ 微任务 │ 宏任务 │ 微任务 │  rAF  │ 样式 │ 布局 │ 绘制 │ 合成 │ 空闲(rIC) │
                                     └──────── 渲染阶段 ────────┘
```

1. 主线程在帧的前段执行若干个「宏任务 + 微任务检查点」。一帧内可能跑多个宏任务，也可能一个宏任务跨越多帧（那就掉帧了）。
2. 到了渲染机会，先跑 `requestAnimationFrame` 回调，再样式计算、布局、绘制，把结果交给合成线程。
3. 如果还有剩余时间，执行 `requestIdleCallback`，并告诉回调还剩多少毫秒。
4. 回到第 1 步。

各种 API 在这条时间线上的位置：

| API | 位置 | 适合做什么 |
| --- | --- | --- |
| `Promise.then` / `queueMicrotask` | 当前宏任务之后、渲染之前 | 状态合并、DOM 更新后立刻读取（Vue `nextTick`） |
| `setTimeout` / `MessageChannel` | 下一个宏任务 | 把大任务切片，让渡渲染机会 |
| `requestAnimationFrame` | 渲染前、样式计算前 | 每帧的 DOM 读写、JS 动画 |
| `requestIdleCallback` | 渲染后的空闲时间 | 日志上报、预加载等低优先级工作 |
| `scheduler.postTask` / `scheduler.yield` | 带优先级的宏任务（Chromium 系） | 显式声明优先级的任务调度 |

### 8.4 框架是怎么利用这套机制的

- **Vue**：多次状态修改合并到一个微任务里统一更新 DOM，`nextTick` 就是排在这个更新微任务之后的另一个微任务，所以 `await nextTick()` 后能读到新 DOM。
- **React**：并发渲染的 Scheduler 用 `MessageChannel` 产生宏任务来做时间切片，每片约 5ms，片与片之间让出主线程，让高优先级的用户输入先处理。不用 `setTimeout` 是为了绕开 4ms 最小延时。
- **两者共同点**：都在「微任务合并更新、宏任务切片长工作」这两个位置做文章，本质是配合事件循环给渲染留缝。

### 8.5 怎么验证和排查

- **DevTools Performance 面板**：录制后看 Main 轨道，红色三角标记的就是 Long Task（> 50ms），点开能看到调用栈。
- **`PerformanceObserver`** 监听 `longtask`，线上采集长任务数量和来源。
- **Core Web Vitals 的 INP**：衡量从用户交互到下一帧绘制的延迟，直接反映主线程被占用的程度。
- **验证切片是否有效**：切片前后对比 Long Task 数量和 INP 分布，而不是只看「总耗时」。

口述版：

> 浏览器渲染进程里 JS 和渲染共享主线程，事件循环按任务源优先级取宏任务，跑完立刻清空微任务，到刷新时间点就跑 rAF、样式、布局、绘制，交给合成线程，有剩余时间再跑 requestIdleCallback。合成线程独立，所以 transform 动画在主线程忙时也能流畅。框架层面 Vue 用微任务合并更新，React 用 MessageChannel 切片；排查时用 Performance 看 Long Task，用 INP 衡量结果。

**要点**：讲完这一层，前面七个问题的答案都能在这张时间线上指出来。

## 高频追问

### `setTimeout(fn, 0)` 为什么不是立刻执行？

它只是把回调入宏任务队列，必须等当前宏任务和全部微任务跑完、事件循环取到它时才执行。嵌套层数多了还会被抬到最小 4ms。

### 微任务无限追加和宏任务无限追加，哪个更严重？

微任务更严重：渲染排在微任务检查点之后，检查点不结束页面就完全假死。宏任务之间有渲染机会，不会假死，但单个任务超过 50ms 就会掉帧、输入延迟。

### `requestAnimationFrame` 和 `setTimeout` 做动画有什么区别？

rAF 在每次渲染前执行，节奏和屏幕刷新对齐，标签页隐藏时自动暂停；`setTimeout` 只按时间入队，和帧无关，容易一帧跑两次或两帧跑零次。

### 用户点击触发的两个监听器之间，微任务什么时候跑？

真实点击时，每个监听器执行完、调用栈清空，就会执行一次微任务检查点，所以第一个监听器里的 `Promise.then` 会在第二个监听器之前执行。如果用 `el.click()` 手动触发，两个监听器在同一个调用栈里同步跑完，微任务要等最后才执行。

### 为什么 React Scheduler 用 `MessageChannel` 而不是 `setTimeout`？

`setTimeout` 嵌套后有 4ms 最小延时，切片粒度 5ms 的话会浪费近一半时间；`MessageChannel` 没有这个限制，能真正做到零延时的下一个宏任务。

### Node.js 的事件循环和浏览器有什么不同？

浏览器围绕渲染组织：宏任务 → 微任务 → 渲染。Node 没有渲染，围绕 libuv 的阶段（timers、poll、check 等）组织，并且多了 `process.nextTick` 和 `setImmediate`。详见延伸阅读。
