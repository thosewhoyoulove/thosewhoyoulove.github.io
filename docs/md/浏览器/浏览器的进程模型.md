# 浏览器的进程模型

## 面试回答

> 现代浏览器，尤其是 Chromium，不是一个大进程把窗口、网络、页面、GPU 全包了，而是多进程协作。浏览器主进程管窗口、标签、导航和调度；网络进程专门拉资源；GPU 进程负责把各页面的图层真正画到屏幕；每个站点对应的页面跑在沙箱里的渲染进程。
>
> 页面里的 JavaScript 并没有因此变成多线程。JS、DOM、样式、布局、生成绘制指令，仍然挤在渲染进程的主线程上。主线程忙，点击和 layout 就会卡。但渲染进程里还有合成线程和光栅线程：合成线程管图层怎么叠、能不能直接滚、`transform` / `opacity` 能不能自己动；光栅线程或 GPU 进程把绘制指令变成像素块。所以主线程卡住时，合成友好的滚动和动画仍可能流畅。Dedicated Web Worker 通常是同一渲染进程里的另一条 JS 线程，能算不能碰 DOM。
>
> 这样拆的目的不是让单段 JS 算得更快，而是三件事：一个标签崩溃别拖死整个浏览器；不信任的网页别直接碰文件系统和别的站点内存；网络和上屏别跟页面 JS 抢同一条线程。面试里不要说成「一个标签一定一个进程」——桌面 Chrome 更接近按站点隔离，跨站 iframe 会进另一个渲染进程，内存紧张时同站标签还可能共用进程。

**一句话总结：**

> 主进程调度 → 网络进程拉资源 → 渲染进程沙箱跑页面 → 主线程 JS/layout/paint → 合成/光栅分担上屏 → GPU 进程画到屏幕；多进程隔离崩溃和权限，JS 仍在渲染主线程单线程执行。

## 核心原理

### 1. 为什么需要这个机制

如果浏览器是单进程，页面脚本、网络栈、窗口 UI、GPU 驱动都挤在一起：

- 一个标签的 JS 崩溃或驱动故障，整窗一起死。
- 恶意页面拿到的权限太大，容易读本机文件或别的站点数据。
- 下载、解码、上屏和 JS 互相堵，卡一下全卡。

所以 Chromium 把「不信任的网页」关进沙箱渲染进程，把「真正碰硬件和系统」的能力留在主进程 / GPU 进程，把「等网络」交给网络进程。

进程和线程不要混：

| | 白话 | 解决什么 | 面试怎么用 |
| --- | --- | --- | --- |
| **进程** | 操作系统分给浏览器的一块独立地盘，内存默认不共享 | 崩溃隔离、权限隔离 | 标签崩、站点隔离、沙箱 |
| **线程** | 同一进程里的多条执行线，共享这块内存 | 同一页面内并行，少抢主线程 | JS 卡 vs 滚动仍流畅 |

进程之间靠 **IPC** 通信。IPC 就是进程间发消息：渲染进程不能自己直接读磁盘或随便碰 GPU，要请主进程 / GPU 进程代劳。代价是拷贝和延迟，换来隔离。

### 2. 整体执行链路

先建立这张图。面试口述用它，不必背 Chromium 全部进程类型。

```text
浏览器
│
├─ 浏览器主进程 Browser Process
│     窗口 / 标签 / 地址栏 / 创建其他进程 / 导航调度
│
├─ 网络进程 Network Process
│     DNS / TCP / TLS / HTTP / 缓存
│
├─ GPU 进程 GPU Process（Chromium 里常叫 Viz）
│     光栅加速 / 把各进程的合成帧画到屏幕
│
└─ 渲染进程 Renderer Process（可有多个，按站点隔离）
      ├─ 主线程 Main Thread
      │     解析 HTML/CSS、跑 JS、样式、布局、生成绘制指令
      ├─ 合成线程 Compositor Thread
      │     图层、滚动、合成动画、把帧交给 GPU 进程
      ├─ 光栅线程 Raster Thread
      │     把绘制指令栅格化成图块（也可能在 GPU 进程做）
      ├─ Worker 线程
      │     Web Worker 等，独立 JS 环境，不能碰 DOM
      └─ 其他线程
            IO / 图片解码 / 音视频 / GC 辅助等
```

打开一个页面时，数据大致这样走：

```text
用户在地址栏回车
  → 主进程：解析 URL、决定用哪个渲染进程、发起导航
  → 网络进程：查缓存 / DNS / 建连 / 拿 HTML
  → IPC：把字节流交给对应渲染进程
  → 渲染主线程：DOM + CSSOM → 样式 → 布局 → Paint（显示列表）
  → Commit：把图层和绘制结果交给合成线程
  → 光栅：显示列表 → 图块像素（渲染进程光栅线程，或 GPU 进程）
  → GPU 进程：把本页和其他进程的帧合成，画到屏幕
```

读者随时能回答：当前在哪个进程、输入是什么、输出交给谁。

### 3. 四个核心进程各干什么

#### 浏览器主进程

浏览器启动时第一个起来的进程。它画 Chrome 自己的壳：标签栏、地址栏、菜单。它创建和回收其他进程，决定「这个 URL 交给哪个渲染进程」，并把用户输入路由出去。

它的权限比渲染进程高：能管文件、创进程、协调导航。所以恶意页面不能跑在这里。

主进程忙，表现是整个浏览器窗口的壳卡住，而不只是某一个页面里的 JS 卡。前端日常优化很少优化到它，但要能把它和「页面主线程卡」分开。

#### 网络进程

专门做资源加载。为了方便理解，可以先认为「所有 HTTP 都在网络进程」；更准确地说，Chromium 的 Network Service 在桌面默认跑在独立进程里，Android 上可能仍在浏览器进程内，为的是省内存。

它解决的是：等 DNS、等 TCP、解压缩、走 HTTP 缓存时，不要堵渲染主线程，也不要把完整网络栈暴露给沙箱页面。渲染进程需要资源时发 IPC，网络进程拿完再送回来。

和「从输入 URL 到展示」那条链的关系：URL 规范化在主进程，真正的 DNS / 握手 / 请求在网络进程，HTML 字节到达后才进入渲染进程。细节见 [从输入 URL 到页面展示](/md/网络/URL解析流程.md)。

#### GPU 进程

真正跟显卡打交道的进程。各渲染进程算出「这一层怎么画、放哪」，最后由它（RenderingNG 里叫 **Viz**）把多个标签、浏览器 UI、跨站 iframe 的合成帧聚合成一屏像素。

为什么单独拉出去：GPU 驱动复杂且会崩。崩在独立进程里，浏览器可以切软件渲染或重启 GPU 进程，而不必把所有标签一起杀掉。安全上，也不让每个网页进程都直接握着 GPU 接口。

#### 渲染进程

页面真正「活着」的地方：Blink 排版引擎 + V8。这里跑的是不信任的网页，所以沙箱最严——默认不能随便读盘、不能直接创建 socket。

桌面 Chrome 的工程模型是 **站点隔离（Site Isolation）**：

- 不同站点（粗略是 `协议 + eTLD+1`，如 `https://a.com` 和 `https://b.com`）进不同渲染进程。
- 同一个标签里的跨站 iframe 也是独立渲染进程，叫 **OOPIF**（out-of-process iframe）。
- 同站的多个标签通常也分进程，但相关窗口（比如 `window.open`）或内存压力大时，可能共用一个渲染进程。
- Android 上隔离更克制，不是所有站点都单独进进程。

所以「一个 tab 一个进程」只是入门口诀。更准确的面试句是：**按站点隔离渲染进程，一个标签里可以有多个渲染进程。**

还有扩展进程、工具进程、音视频相关进程等。三年岗点到「还有其他进程做插件/扩展隔离」即可，不必背名单。

### 4. 渲染进程里的线程

这是把「页面为什么卡、为什么 `transform` 动画还能动」讲清楚的一层。

#### 主线程 Main Thread

渲染进程里最稀缺的那条线。它要：

- 解析 HTML / CSS
- 跑页面 JavaScript 和事件回调
- 样式计算、布局（layout）
- Paint：生成 **显示列表**（display list，一套「怎么画」的指令，还不是屏幕上的最终像素）
- 命中测试、把输入事件派发给 DOM

**事件循环只调度这条主线程。** JS 单线程指的就是它。长任务占满它，点击、layout、普通绘制都得等。详见 [浏览器的事件循环](/md/浏览器/浏览器的事件循环.md)。

一个渲染进程通常只有 **一条** 主线程。若两个同站标签因为内存压力共用进程，它们会抢同一条主线程。这就是进程共享的性能代价。

#### 合成线程 Compositor Thread

主线程 paint 完会 **Commit**：把图层、属性树、显示列表拷到合成线程。合成线程负责：

- 决定页面怎么分层
- 处理合成器能独立完成的滚动和动画（典型是已分层的 `transform` / `opacity`）
- 不经过主线程 JS，直接产出合成帧，送给 GPU 进程

它解决的问题是：**主线程在跑 200ms 的 JS 时，用户仍然可能滚动已画好的内容。** 前提是这次滚动不需要主线程重新 layout / paint，且页面没有用 `touch` / `wheel` 监听把滚动抢走。

合成线程不能执行页面 JS，也不能改 DOM。它操作的是已经提交过来的图层数据。

#### 光栅线程 Raster Thread

**光栅（raster）** 就是把显示列表变成一块块位图/纹理。页面很大，浏览器按图块（tile）来栅格化，视口附近优先。

为了方便理解，可以先认为「合成线程旁边有一组光栅线程在画图块」。更准确地说：

- 合成线程负责调度，自己通常不干最重的画像素活。
- 有 GPU 加速时，光栅经常发生在 **GPU 进程**。
- GPU 不可用或驱动不稳时，回退到渲染进程里的合成器工作线程做 CPU 光栅。

面试不要说「光栅线程就是 GPU」。光栅是「指令变像素」这一步；这一步可能在 CPU 线程，也可能在 GPU 进程。

#### Worker 线程

`new Worker()` 创建的 **Dedicated Worker** 通常仍在 **当前渲染进程** 里，但是另一条线程、另一套 JS 事件循环。它能算、能 `fetch`，**不能读 DOM、不能碰 `window`**。通信靠 `postMessage`，对象默认结构化克隆。

它解决的是：把可拆出的 CPU 活从主线程挪走，降低 INP / 掉帧。它不能替代合成线程——Worker 算完还得把结果 `postMessage` 回主线程，主线程才能改 DOM。

Service Worker 更像网络代理，生命周期跟页面不同，往往不在「这个标签的主线程」里，也不应和 Dedicated Worker 混成一句话。细节见 [Web Worker](/md/浏览器/Web%20Worker.md)。

#### 其他线程

渲染进程里还有 IO 线程（收 IPC）、图片解码、音视频解封装、GC 辅助等。面试说到「主线程不是渲染进程的全部」即可；追问时能举出 IO / 解码，证明你知道并行发生在线程层。

### 5. 用一个页面把链路跑通

假设用户打开 `https://shop.example.com`，页面里嵌了 `https://ads.other.com` 的广告 iframe。首屏出来后，主线程被一段 200ms 的同步计算占住，用户同时滚动。

| 步骤 | 发生在哪 | 输入 | 做什么 | 输出 |
| ---: | --- | --- | --- | --- |
| 1 | 主进程 | 地址栏 URL | 规范化 URL，选渲染进程，发起导航 | 导航请求 |
| 2 | 网络进程 | 导航请求 | 缓存 / DNS / TLS / HTTP | HTML 字节 |
| 3 | 渲染进程 A（shop）主线程 | HTML | 解析、跑 JS、样式、布局、Paint | DOM + 显示列表 |
| 4 | 渲染进程 B（ads） | 广告 iframe HTML | 另一套解析和绘制，和 A 内存隔离 | 广告图层 |
| 5 | 合成线程 A / B | Commit 过来的图层 | 分层、准备合成帧 | 合成帧 |
| 6 | 光栅（GPU 进程或光栅线程） | 显示列表 / 图块 | 指令 → 像素块 | 纹理 |
| 7 | GPU 进程 | A 的帧 + B 的帧 + 浏览器 UI | 聚合成一屏并 Draw | 屏幕像素 |
| 8 | 主线程 A 被 200ms JS 占住 | 长任务 | 事件循环走不完，点击/layout 排队 | 页面 JS 卡 |
| 9 | 合成线程 A | 滚动手势 | 若只需平移已有图层 | 滚动仍可能流畅 |

第 4 步说明：**一个标签 ≠ 一个渲染进程。** 广告站崩了或算得很慢，商店主页面的进程不必陪葬。

第 8、9 步说明：**进程模型和事件循环是同一件事的两层。** JS 卡的是渲染主线程；合成线程独立，所以「卡 JS」和「卡滚动」可以分开。如果页面监听了 `wheel` / `touchmove` 并 `preventDefault`，滚动必须等主线程，合成线程也救不了。

为什么第 9 步成立：合成线程手里已经有上一帧提交的图层纹理。滚动很多时候只是改图层位置再交给 GPU 进程重画，不必让主线程重新 layout。一旦滚动导致新区域还没光栅过，合成线程会调度新的光栅；这一步仍可以不跑页面 JS。

### 6. 和渲染流水线怎么对上

[浏览器的渲染原理](/md/浏览器/浏览器的渲染原理.md) 里的流水线，落到线程上是：

```text
主线程：  DOM → CSSOM → Style → Layout → Paint（显示列表）→ Commit
合成线程：Layerize → 滚动 / 合成动画 → 提交合成帧
光栅：    显示列表 → 图块像素
GPU 进程：Aggregate（多进程的帧）→ Draw 上屏
```

所以：

- 改 `width` / 插 DOM：主线程 layout + paint，再走合成。代价最高。
- 改 `color`：主线程可能重绘，仍占主线程。
- 已分层的 `transform` / `opacity`：合成线程就能做完，主线程可以在忙别的。

「动画走合成」不是魔法属性，而是：**这条更新能不能跳过主线程的 style / layout / paint。** 跳不过，合成线程再独立也没用。

### 7. 设计取舍

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 单进程单线程 | 实现简单、内存省、无 IPC | 一崩全崩，权限过大，JS 一卡整窗死 |
| 多进程 + 站点隔离 | 稳定、安全、跨站性能隔离 | 每个渲染进程都有内存基线，标签多了吃 RAM |
| 渲染进程内再拆合成 / 光栅线程 | 滚动和合成动画不被 JS 长任务拖死 | Commit 有延迟；不是所有更新都能不上主线程 |
| Worker 分担计算 | 主线程更闲，INP 更好 | 不能碰 DOM；消息拷贝有成本；创建线程本身不免费 |

Chrome 愿意用内存换隔离。低端设备或移动端会合并进程、减弱站点隔离，这是同一套架构在内存预算下的收缩，不是另一套理论。

Firefox 也是多进程（Electrolysis + Fission），Safari 同样有进程隔离，但线程名和进程切分不要按 Chromium 原样套。面试默认讲 Chrome 模型，被问到再说「其他引擎目标类似、实现不同」。

## 常见误区

### ❌ 一个标签页一定对应一个渲染进程

### ✅ 更准确的说法

桌面 Chrome 按 **站点** 隔离。一个标签里的跨站 iframe 会进另一个渲染进程；同站多标签在内存紧张时可能共用进程。

### 为什么？

站点隔离要防的是跨站读内存（包括 Spectre 一类），不是「按标签计数」。标签只是用户看到的窗口单元。

---

### ❌ 浏览器都多进程了，所以 JavaScript 是多线程的，JS 会因此更快

### ✅ 更准确的说法

网页 JS 默认仍在 **渲染进程主线程** 单线程执行。多进程让网络、GPU、其他站点不跟你抢同一块地址空间，并不能让某一段 JS 自己跑得更快。要并行算，得自己开 Worker，且仍不能直接改 DOM。

### 为什么？

DOM 不是线程安全的。多个 JS 线程同时改同一棵 DOM，锁和竞态会把模型打爆，所以页面脚本被钉在主线程。

---

### ❌ 合成线程可以执行 JS，或者光栅线程就是 GPU 加速本身

### ✅ 更准确的说法

合成线程处理图层、滚动和合成动画，不跑页面脚本。光栅是「绘制指令 → 像素块」，可能在渲染进程的光栅/工作线程，也可能在 GPU 进程。GPU 进程是「碰显卡、最终 Draw」的那个进程。

### 为什么？

面试官听「GPU 加速」想确认你分得清：主线程 paint、合成、光栅、真正提交到 GPU。四步叠在一起，就说不清为什么 `transform` 有时顺、有时仍掉帧。

---

### ❌ 开了 Worker，滚动和输入就一定不卡

### ✅ 更准确的说法

Worker 只能搬走 **不碰 DOM 的计算**。改 DOM、layout、paint 仍在主线程；带 `preventDefault` 的触摸/滚轮监听也会把滚动绑回主线程。合成线程救的是「已提交图层上的合成器滚动/动画」，不是所有卡顿。

### 为什么？

卡顿要先定位在哪一层：主线程 JS、主线程 layout/paint、合成/光栅过重、还是 GPU 过载。层找错，优化就会开错药。

---

### ❌ 网络请求是页面 JS 线程发出去、也在 JS 线程里等回来

### ✅ 更准确的说法

`fetch` / `XHR` 由页面脚本发起，真正的套接字和等待在网络进程（或浏览器的网络服务）里。回来之后，回调作为任务排队进 **渲染主线程** 的事件循环。所以「请求在飞」时主线程可以去干别的；「响应回调里同步算 200ms」仍然会卡。

### 为什么？

异步的本质是别的进程/线程在等，主线程只在回调执行时被占用。这和事件循环、INP 是同一条链。

---

## 高频追问

### 浏览器都有哪些进程？各干什么？

常说四个：主进程管窗口和调度，网络进程拉资源，GPU 进程上屏，渲染进程跑页面。还可以提扩展进程。重点说清 **隔离目的**，不要背进程清单。

### 多进程和 JS 单线程矛盾吗？

不矛盾。多进程是浏览器架构；JS 单线程是渲染主线程的执行模型。一个页面崩不影响壳，但这个页面自己的主线程照样会被长任务占满。

### 为什么一个页面崩溃通常不会带走整个浏览器？

页面在沙箱渲染进程里。进程崩了，主进程可以收掉这个进程、显示崩溃页，其他渲染进程和浏览器壳还在。GPU 进程崩了也常常只是重启 GPU，而不是退出 Chrome。

### 站点隔离是什么？为什么跨站 iframe 要单独进进程？

不同站点放进不同渲染进程，降低「一个站点的渲染进程被打穿后读另一个站点内存」的风险。跨站 iframe 若和父页共用进程，父页和广告页就在同一块地址空间，隔离会失效。

### 渲染进程里主线程和合成线程怎么分工？

主线程：JS、DOM、style、layout、paint。合成线程：图层、合成器滚动和 `transform` / `opacity` 一类动画，并把帧交给 GPU 进程。主线程 Commit 之后，合成线程可以在主线程忙时继续滚已有内容。

### 为什么主线程卡住时，有的动画还能动、有的不能？

能走合成线程的更新，不依赖这一帧的 JS / layout / paint。改宽高、改文字、依赖 JS 每帧 `setState` 的动画，都必须等主线程。监听器用 `preventDefault` 接管滚动时，滚动也会等主线程。

### 光栅发生在哪？一定是渲染进程的光栅线程吗？

不一定。合成线程调度光栅；有 GPU 时常常在 GPU 进程里把显示列表栅格成纹理；失败再回退到渲染进程的工作线程做 CPU 光栅。面试说「指令变像素，可能在渲染进程或 GPU 进程」即可。

### Web Worker 跑在哪个进程、哪条线程？为什么不能操作 DOM？

Dedicated Worker 一般在 **当前渲染进程的另一条线程**。DOM 只属于主线程那套文档生命周期，Worker 没有这份 DOM，只能通过消息把结果交回主线程再改页面。
