# 上下文与 Token 体验

## 面试定位

上下文窗口和 Token 成本是 Agent 产品的隐性门槛。面试官想听你能否把**截断、用量、附件入上下文**做成用户能理解的体验，而不是后台报错后前端一片空白。

## 面试回答

可以这样答：

> 上下文管理不是简单保留最近 N 轮，而是按优先级构建每次请求的 context：系统约束、当前目标、用户固定事实、必要的工具结果和检索证据优先，闲聊与可重新获取的大结果可以摘要或裁剪。摘要是有损压缩，不能拿它替代精确 ID、金额、审批状态等事实；这类信息应进入结构化 task state。Token 估算只能用于体验提示，因为不同模型 tokenizer、系统提示和工具 schema 都会占窗口，最终预算由服务端决定。前端要让用户看见当前引用了哪些文件、哪些内容被摘要或截断，并支持移除、固定与重新选择。服务端保存权威上下文清单和版本，避免刷新后 UI 声称“已引用”但实际请求没带上。

一句话总结：

> Token 体验 = 可见的用量与截断策略 + 可理解的附件/引用入模过程。

---

## 核心原理

```text
历史消息 + 系统提示 + 附件/引用 + 当前输入
  → Tokenizer / 估算
  → 未超限：正常请求
  → 将满：提示用户或自动摘要/裁剪
  → 超限：阻断发送或强制压缩后发送
  → 响应侧也可能因 max tokens 截断
```

---

## 1. 用量展示与将满提示

| 手段 | 作用 | 注意 |
| --- | --- | --- |
| 百分比/进度条 | 建立成本与容量直觉 | 前端估算可能与服务端不完全一致 |
| 将满 Toast/横幅 | 引导新开会话或压缩 | 要提前，不要等到 100% 才报错 |
| 每次请求费用提示 | 企业版成本透明 | 需后端返回 usage，前端勿瞎猜精确价 |

**要点**：可以说“约”，但要在文案标明估算；以服务端 `usage` 为准做最终展示更稳妥。

---

## 2. 截断与摘要策略

常见策略：

1. **滑动窗口**：只保留最近 N 轮。
2. **摘要压缩**：把旧对话收成摘要再入模。
3. **优先级裁剪**：系统约束与当前任务优先，闲聊历史先丢。
4. **用户显式“清除上下文”**。

更稳妥的做法是把信息分层：

| 层 | 示例 | 策略 |
| --- | --- | --- |
| 不可丢的约束 | 系统规则、权限、当前目标 | 固定并版本化 |
| 结构化事实 | 订单 ID、确认参数、任务状态 | 放 task state，不依赖摘要记忆 |
| 可压缩历史 | 讨论过程、解释性文本 | 摘要并保留来源范围 |
| 可再获取内容 | 大段工具结果、文档片段 | 保存引用，需要时重新检索 |

产品文案示例：

- “为继续对话，已摘要更早的 12 条消息”
- “该附件过长，仅使用前 50KB 内容”

**不适用**：静默丢弃用户刚 @ 的关键文件还不提示——这是信任事故。

---

## 3. 每次请求的上下文到底由谁提供

模型通常只处理本次请求实际携带的输入；历史对话、附件和工具结果要由宿主或服务端会话机制组织，并受当前请求预算限制。应用数据库里“存着”一份资料，不代表模型本次就读到了它。

```text
当前目标 + 任务状态 + 历史记录 + Skill / 工具描述 + 可读资料
  → 按权限选取
  → 按优先级分配 Token 预算
  → 历史摘要、工具结果裁剪、资料检索
  → 组装实际输入
  → 请求模型
  → 保存新状态与产物引用
```

设一个教学模型窗口上限为 32,000 Token，预留输出 4,000、安全余量 2,000，则输入预算为 26,000。固定约束、工具描述、当前问题和必要任务状态先占 6,000，留给历史和证据的空间只有 20,000。预算按模型和接口实际限制核对，不把这里的数字当成某款模型参数。

| 材料 | 原始大小 | 本次选择 | 处理原因 |
| --- | ---: | ---: | --- |
| 固定约束与必要状态 | 6,000 | 6,000 | 保留目标、权限和精确业务字段 |
| 历史对话 | 18,000 | 4,000 | 保留最近相关交流，其余摘要 |
| 文档与工具结果 | 30,000 | 12,000 | 检索相关片段，大结果只带摘要及引用 |
| 合计 | 54,000 | 22,000 | 低于输入预算 26,000 |

这不是机械截掉最旧的内容。订单 ID、用户已确认的参数和未完成步骤要保存为结构化状态；被省略的日志保留可重新读取的引用。摘要如果漏掉关键否定条件，例如“禁止对生产库写入”，会直接改变任务含义，所以固定约束不应仅依赖摘要保存。

用户一次提交超长资料时，先判断是让模型阅读全文，还是从大资料中回答局部问题。局部问答可分片检索；跨全文比较可以分段处理再汇总，但汇总需要携带统一字段和来源，避免各段标准不一致。对无法放入的原文应说明覆盖范围，不声称已经读完。

Agent 循环还要限制工具结果增长：大表格保存成文件，模型只读必要列和统计；已经完成的中间步骤保留结论与产物位置。子任务可以隔离上下文，但总协调者仍需获得可验证产物、限制和失败信息，否则只是把信息丢在另一个会话里。

## 4. 附件与 @ 引用队列

```text
选择文件 / @文档
  → 上传
  → 解析（文本提取 / OCR 等）
  → 计入上下文预算
  → 成功：可发送；失败：可移除并说明原因
```

前端要点：

- 多文件并行时显示队列与单个失败态
- 解析中禁用发送或允许“先发文字、附件稍后”
- 解析失败要可复制错误信息，便于支持排查

**场景（示例）**：对客文档助手支持上传 PDF；超过上下文预算时提示拆分文档或只引用某一章节。

**验证**：构造超长历史与大附件，确认提示文案与是否仍可发送；核对服务端实际 prompt 是否与 UI 声明一致。

## 高频追问

### 前端为什么不能只信自己的 Token 计数？

不同模型 tokenizer 不同，BFF 还可能插入系统提示与工具结果。前端估算用于预警，结算与是否超限以服务端为准。

### 输出被 max tokens 截断怎么处理？

标记“回复可能不完整”，提供继续生成；结构化 JSON 场景应校验完整性，不完整则重试或降级。

### 和 Prompt 工程的关系？

系统提示过长会挤占用户上下文。Prompt 要精炼，详见 [LLM 与 Prompt Engineering](/md/Agent/LLM与PromptEngineering.md)。
