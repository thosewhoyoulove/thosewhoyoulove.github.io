# 上下文与 Token 体验

## 面试定位

上下文窗口和 Token 成本是 Agent 产品的隐性门槛。面试官想听你能否把**截断、用量、附件入上下文**做成用户能理解的体验，而不是后台报错后前端一片空白。

## 面试回答

可以这样答：

> 上下文体验的核心是让用户知道“模型此刻能看到什么、还剩多少空间、哪些内容会被丢掉”。前端可以展示大致 Token 用量或进度条，在接近上限时提示压缩历史、开启新会话或减少附件。附件和 @ 引用要进队列，展示解析进度与失败原因；超长内容应在入模前截断并明确告知。历史策略通常是滑动窗口、摘要或由 BFF 做优先级裁剪，前端负责把结果说清楚。验证看：将满提示是否提前出现、截断后回答是否仍可追溯来源、用户是否理解为何模型“忘了”早期内容。

一句话总结：

> Token 体验 = 可见的用量与截断策略 + 可理解的附件/引用入模过程。

---

## 核心原理

```text
历史消息 + 系统提示 + 附件/引用 + 当前输入
  → Tokenizer / 估算
  → 未超限：正常请求
  → 将满：提示用户或自动摘要/裁剪
  → 超限：阻断发送或强制压缩后发送
  → 响应侧也可能因 max tokens 截断
```

---

## 1. 用量展示与将满提示

| 手段 | 作用 | 注意 |
| --- | --- | --- |
| 百分比/进度条 | 建立成本与容量直觉 | 前端估算可能与服务端不完全一致 |
| 将满 Toast/横幅 | 引导新开会话或压缩 | 要提前，不要等到 100% 才报错 |
| 每次请求费用提示 | 企业版成本透明 | 需后端返回 usage，前端勿瞎猜精确价 |

**要点**：可以说“约”，但要在文案标明估算；以服务端 `usage` 为准做最终展示更稳妥。

---

## 2. 截断与摘要策略

常见策略：

1. **滑动窗口**：只保留最近 N 轮。
2. **摘要压缩**：把旧对话收成摘要再入模。
3. **优先级裁剪**：系统约束与当前任务优先，闲聊历史先丢。
4. **用户显式“清除上下文”**。

产品文案示例：

- “为继续对话，已摘要更早的 12 条消息”
- “该附件过长，仅使用前 50KB 内容”

**不适用**：静默丢弃用户刚 @ 的关键文件还不提示——这是信任事故。

---

## 3. 附件与 @ 引用队列

```text
选择文件 / @文档
  → 上传
  → 解析（文本提取 / OCR 等）
  → 计入上下文预算
  → 成功：可发送；失败：可移除并说明原因
```

前端要点：

- 多文件并行时显示队列与单个失败态
- 解析中禁用发送或允许“先发文字、附件稍后”
- 解析失败要可复制错误信息，便于支持排查

**场景（示例）**：对客文档助手支持上传 PDF；超过上下文预算时提示拆分文档或只引用某一章节。

**验证**：构造超长历史与大附件，确认提示文案与是否仍可发送；核对服务端实际 prompt 是否与 UI 声明一致。

## 高频追问

### 前端为什么不能只信自己的 Token 计数？

不同模型 tokenizer 不同，BFF 还可能插入系统提示与工具结果。前端估算用于预警，结算与是否超限以服务端为准。

### 输出被 max tokens 截断怎么处理？

标记“回复可能不完整”，提供继续生成；结构化 JSON 场景应校验完整性，不完整则重试或降级。

### 和 Prompt 工程的关系？

系统提示过长会挤占用户上下文。Prompt 要精炼，详见 [LLM 与 Prompt Engineering](/md/Agent/LLM与PromptEngineering.md)。
