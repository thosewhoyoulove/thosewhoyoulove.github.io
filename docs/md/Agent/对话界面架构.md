# 对话界面架构

## 面试定位

对话 UI 是 Agent 产品的门面。面试官想听你是否设计过**消息模型、多会话、流式更新下的状态一致性**，而不是只会放一个输入框和气泡列表。

## 面试回答

可以这样答：

> 我会把对话界面拆成会话层、消息层、流式连接层和输入层。消息模型至少区分 user、assistant、system、tool，每条有稳定 id；如果支持编辑重试或分支，还需要 parentId 或版本链。发送时可以先乐观插入用户消息和一条 pending 的助手消息，但最终内容必须以服务端 SSE/事件流为准，避免本地猜测和真实事件打架。多会话要隔离草稿、进行中的 AbortController 和未读状态。输入层处理附件、@ 引用、slash 命令，但上传与解析进度要进统一任务队列。验证上我会看：取消是否干净、切换会话是否串流、刷新后历史是否与流式中的临时态一致。

一句话总结：

> 对话架构 = 清晰消息模型 + 以服务端事件为准的状态机 + 可取消的流式连接。

---

## 核心原理

```text
SessionList
  → 当前 sessionId
  → MessageList（按 id 归一）
  → StreamingConnection（SSE / fetch stream）
  → 事件：text_delta / tool_* / error / done
  → Reducer 更新消息与 UI 状态
  → Composer（文本 / 附件 / 命令）
```

---

## 1. 消息模型

建议字段（示意，非某厂商 API）：

```ts
type Role = 'user' | 'assistant' | 'system' | 'tool'

interface Message {
  id: string
  role: Role
  content: string
  status: 'pending' | 'streaming' | 'done' | 'error' | 'cancelled'
  parentId?: string
  toolName?: string
  createdAt: number
}
```

设计原则：

- **用 id 更新，不要只靠数组下标**：流式中频繁 patch 同一条助手消息。
- **tool 消息单独角色或独立块**：方便折叠与权限展示。
- **分支/编辑**：编辑用户消息后从该节点重新生成，旧分支可保留或归档。

**要点**：先定数据模型，再写组件，否则流式和工具态会把 props 钻成蜘蛛网。

---

## 2. 乐观 UI vs 服务端真相

| 策略 | 做法 | 风险 |
| --- | --- | --- |
| 纯乐观 | 本地直接追加最终回复 | 与真实流不一致，难恢复 |
| 纯等待 | 等首包才出助手气泡 | 体感慢 |
| 推荐 | 乐观插入骨架，内容只由事件填充 | 实现稍复杂，但可取消、可对齐 |

冲突处理：

- 收到 `done` 后，用服务端最终文本覆盖本地缓冲。
- 收到 `error` 时保留已生成部分（可选）并标记失败，提供重试。
- 用户取消：`AbortController.abort()`，消息标 `cancelled`，停止渲染调度。

---

## 3. 多会话与输入层

多会话要注意：

- 每个 session 独立的 in-flight 请求与 AbortController。
- 切换 Tab 不中断后台流，或明确提示“离开将停止生成”——产品二选一，但要一致。
- 草稿按 session 存，避免串台。

输入层常见能力：

- 多模态附件（图片/文件）与解析失败提示
- `@` 引用文件/文档进入上下文
- `/` 命令触发 Skill 或预设 Prompt

**场景（示例）**：云厂商对客助手支持多会话排障；用户在会话 A 生成中切换到 B，A 的流继续，标题旁显示生成中指示器。

**验证**：E2E 覆盖发送/取消/重试/切会话；用慢网与断网模拟串流。

## 高频追问

### 为什么不要把整段 assistant 文本每次都新建一条消息？

流式是同一条消息的增量更新。每次新建会导致列表跳动、虚拟列表 key 错乱，也无法表达“正在生成”。

### 历史消息和正在流式的消息如何统一？

历史用 REST 拉取最终态；进行中用事件流。进入页时若发现未完成 run，应恢复订阅或展示可继续/可取消状态。

### 虚拟列表要注意什么？

流式时底部锚点、图片与代码块高度变化会导致抖动；需要“用户上翻则解除自动贴底”的交互。
