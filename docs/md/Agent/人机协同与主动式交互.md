# 人机协同与主动式交互

## 面试定位

下一代 Agent 体验不止聊天框。面试官想听：**人机协同（HITL）如何产品化**，以及 **主动式交互**（Agent 发起、提醒、推进任务）如何在浏览器里落地，尤其是 B2B 高密度工作台。

## 面试回答

可以这样答：

> 人机协同我会分成三级：信息级（展示推理与来源，人只读）、确认级（高风险操作 approve/reject/edit）、协作级（人改参数、改短名单、补约束后 Agent 续跑）。主动式交互则是 Agent 在任务进度、外部信号或定时策略下发起：例如发现新供应商匹配、风险变化，推送到收件箱或工作台，而不是干等用户提问。前端上要把“对话”和“工作台”打通——多轮上下文在会话里，结构化结果沉淀在可筛选的面板；主动卡片要可静音、可延后、可追溯。验证看：误打扰率、确认转化、从主动提醒到任务完成的转化时长。

一句话总结：

> 人机协同 = 分级介入；主动式 = Agent 可发起但必须可管理、可追溯。

---

## 核心原理

```text
被动：用户问 → Agent 答/行动
主动：信号/进度 → Agent 提案 → 用户收件箱
协同：提案 → 人编辑/确认 → Agent 续跑 → 业务落库
```

协同分级：

| 级别 | 示例 | 前端形态 |
| --- | --- | --- |
| 信息 | 趋势摘要、来源引用 | 只读卡 + citation |
| 确认 | 联系供应商、改价、验证通过 | Approve 条 |
| 协作 | 调整筛选、重排短名单 | 可编辑表单/画布后再续跑 |

---

## 1. 多轮上下文不只在气泡里

B2B Agent 常见双轨：

- **对话轨**：意图、澄清、解释。
- **工件轨（artifacts）**：对比表、寻源列表、验证报告——可跨轮次保留、可导出。

上下文管理产品点：

- 显式“基于这份短名单继续”
- 切换任务时提示是否继承上下文
- 主动消息引用原 runId，一键回到当时工件

详见 [上下文与 Token 体验](/md/Agent/上下文与Token体验.md)；此处强调 **业务对象级上下文**，不只 Token 计数。

## 2. 主动式交互的工程约束

主动推送必须回答三个问题：

1. **为何现在推**：触发条件可读（新匹配、SLA 到期）。
2. **人能做什么**：查看 / 接受 / 延后 / 忽略。
3. **忽略后果**：是否还会再推、如何关闭该类提醒。

```text
push_card
  → inbox（未读）
  → 用户打开 → 进入 awaiting_user run
  → 决策写入审计
```

反模式：无节制 Toast、无法关闭、与当前任务抢焦点。

---

## 3. 高密度富交互工作台

Accio 类场景（趋势、寻源、多模态匹配、商家验证）适合：

- 左对话 / 右工件，或底栏任务线
- 批量选择 + 二次确认
- 多模态：图搜款、图文对齐结果并排
- 生成式 UI 块嵌入工作台，而不是塞进一条超长气泡

**场景（示例）**：Agent 主动提示“3 家新供应商匹配你的新品企划”；用户打开对比卡，改交期权重后点“按此条件重新排序”，Agent 续跑并 patch 同一表格。

**验证**：打扰率、主动卡片 CTR、确认后业务成功率、协同编辑冲突率。

## 高频追问

### 主动式会不会变成通知骚扰？

会。要用频率上限、用户偏好、重要性分级；低优进收件箱，高优才打断。

### 和普通审批流有何不同？

审批流步骤固定；Agent 协同的下一步依赖模型与工具结果，前端要展示“当前为何停在这”，并允许人改约束后分支续跑。

### HITL 是否只做在工具层？

工具层是底线；业务层（选商、验商）同样需要确认级/协作级，协议上可统一为 `awaiting_user`。
