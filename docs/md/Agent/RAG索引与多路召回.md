# RAG 索引与多路召回

## 面试回答

> 我会从知识准备、在线检索和效果取舍三个层面回答。
>
> 首先，**RAG 在生成前取回与问题相关的外部证据**。离线先解析文档、按语义边界分片，保存文档版本和权限，再构建关键词及向量索引。在线把用户问题转换成检索请求，拿到候选片段，筛选后放进模型上下文。
>
> 第二，**多路召回利用不同检索方式互补**。关键词适合错误码、型号等精确表达，向量适合措辞不同但语义接近的问题。多路结果先按片段 ID 去重，再融合排名，必要时通过重排模型比较问题和候选内容，选出真正适合回答的证据。
>
> 第三，**索引用额外存储和维护成本换取重复查询的效率**。倒排索引从词找到包含它的片段；向量索引用近似搜索减少大库中的逐一比较。小数据量可以全量扫描，近似搜索也可能漏结果，所以要结合规模、过滤条件和召回率选择。
>
> **RAG 不等于把整个知识库塞进 Prompt，也不保证没有幻觉**。检索、排序、引用和回答都需要分别评测。

**一句话总结：** 文档分片建索引 → 带权限多路召回 → 去重融合 → 重排 → 按预算提供证据 → 生成并校验引用。

## 核心原理

### 知识库怎样变成可查的证据

模型训练时见过的内容，不能替代企业刚更新的产品政策。RAG 将变化频繁的知识留在可更新的数据层，每次回答时再取回证据。它不必为每次文档变更重新训练模型，但要维护解析、索引和权限一致性。

```text
离线：文档 → 解析与清洗 → 分片 → 元数据和 ACL → 倒排 / 向量索引
在线：问题 → 查询处理 → 权限过滤下召回 → 融合去重 → 重排
     → 上下文预算与引用映射 → 生成 → 校验和呈现
```

分片过小可能把条件和结论拆散，过大则浪费上下文并混入噪声。可以按标题、段落和列表组织片段，保留适度重叠，必要时召回后补父段落。片段需关联 `documentId`、`version`、`chunkId` 和权限元数据：它们用于引用定位、更新替换、去重及访问控制。

查询向量与文档向量需要使用兼容的嵌入模型和预处理方式。换模型时仅让维度相同并不足够，向量空间含义可能已经变化，应评估重建索引或双索引迁移。

### 为什么倒排索引能少看很多文档

假设三个片段分别包含：A“设备 E42 过热”，B“设备连接失败”，C“E42 需要检查风扇”。倒排索引预先建立从词到片段的映射：

```text
E42 → A, C
过热 → A
连接 → B
```

搜索 `E42 过热` 时，先找到相关 posting lists，也就是这些词对应的片段列表，再根据 AND / OR 等查询语义合并并评分。不必重新解析每份原文。BM25 等排序方法进一步考虑词频、词的稀有程度与文档长度；分词器、同义词规则和字段权重也会改变结果。

这是用离线维护换在线查询效率，不是零成本：新增、修改和删除文档后要更新索引，索引也会占用存储。低频、极小数据集直接扫描可能更简单。

### 向量检索为什么需要专门的索引

Embedding 把内容映射到数值向量，使模型认为相近的语义更容易在向量空间中接近，但相似不等于事实正确。精确向量搜索可以对每个片段都算距离，N 个 d 维向量的距离计算成本通常随 N×d 增长。

当数据变大且查询频繁时，HNSW 等近似最近邻方法会构建可导航的结构，尽量只探索有希望的候选。它用内存、建索引时间和一定召回损失换低延迟；搜索候选越多通常越容易找全，但更耗时。不要把所有向量索引都描述成同一种算法或固定 O(log N)。精确与近似检索的区别见 [Elastic kNN 文档](https://www.elastic.co/docs/solutions/search/vector/knn)。

### 多路召回怎样合成一个排名

假设用户问“E42 发烫怎么处理”。关键词路召回 `[A, C, B]`，语义路召回 `[D, A, C]`。D 虽没有使用“发烫”这个词，却可能描述散热处理，因此两路有互补价值。[混合检索](https://www.elastic.co/docs/solutions/search/hybrid-search) 将关键词匹配和向量相似结合，但两者原始分数通常不在同一尺度，直接相加缺少依据。

可以使用基于排名的 RRF：每一路按 `1 / (k + rank)` 给片段贡献分数，再相加。rank 从 1 开始，未出现的路贡献 0；k 是平滑常数，不是最终返回条数。下面取 k=60，仅用于演算：

| 片段 | 关键词排名 | 向量排名 | RRF 得分约值 |
| --- | ---: | ---: | ---: |
| A | 1 | 2 | 0.03252 |
| C | 2 | 3 | 0.03200 |
| D | 无 | 1 | 0.01639 |
| B | 3 | 无 | 0.01587 |

先合并出 A、C、D、B 四个唯一片段，再得到融合顺序 `[A, C, D, B]`。A 和 C 在两路都靠前，累计贡献更高。这里不是把重复片段拼接两遍，而是对同一个 chunk 汇总排名贡献。算法定义参见 [RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

融合后还可以重排：重排器同时读取问题和单个候选片段，判断它对这个问题的相关程度。它比只比较预先生成的向量更细，但在线推理成本较高，所以通常只处理召回候选，不能期待它找回从未召回的内容。

多路也可以包括不同字段、多个查询改写或不同数据源，不必每次都启动全部路。错误码查询可提高精确匹配的重要性，泛化问题可更依赖语义召回。路数和候选数应由效果、延迟、成本与权限约束共同决定。

### 为什么不每次直接扫描全部知识库

先区分两种“扫描”。数据库逐条计算相似度，主要承担 I/O 和距离计算成本；把所有原文都送给模型，主要承担 Token、上下文上限、延迟及注意力噪声。两者不能混为一个问题。

几百条短文本、低并发或很强的权限过滤后，精确搜索可能足够好，还避免了近似漏召回。百万片段、高并发时，反复扫描会消耗大量资源，索引往往更划算。把全库塞给模型还可能携带无权限资料；索引也不能自动解决权限，必须在检索和取回阶段保证不会把越权片段送入模型。

权限过滤不当还会损害召回：如果先取全局 Top10，再把无权限结果删掉，剩下的结果可能远少于 10 条。应使用检索引擎支持的过滤机制，或设计不会越权且能补足候选的方案，并单独测量权限下的 Recall@K。

### 怎样判断是检索问题还是生成问题

固定一组“问题—相关证据—期望答案”样本。先看正确证据是否进入候选集，再看它是否进入最终上下文，最后检查模型是否正确使用。没召回要查分片、词表、嵌入与过滤；召回了但排后要查融合和重排；证据已经给到但答错，要查提示、证据冲突与生成约束。

界面应呈现检索中、无证据、生成中和失败，并让引用能定位到具体版本。引用存在只能证明格式合法，引用是否支持结论仍需校验。前端细节回到 [RAG 与检索增强体验](/md/Agent/RAG与检索增强体验.md)。

## 常见误区

### ❌ RAG 就是向量数据库

✅ RAG 是生成前获取外部证据的系统，检索可以用关键词、向量或混合方式。为什么：不同数据和问题需要不同检索策略。

### ❌ 向量检索永远比关键词准确

✅ 错误码、SKU 和人名可能更适合精确匹配。为什么：语义接近并不等于标识符相同。

### ❌ 有索引就完全不需要扫描

✅ 检索仍会访问和计算候选；某些过滤条件或小数据场景还可能选择精确扫描。为什么：索引是在成本和召回之间取舍，不是消除所有计算。

## 高频追问

### 多路召回和多轮检索有什么区别？

多路是在一次检索阶段用不同策略取候选；多轮是根据已有结果修改问题后再次检索。可以组合，但延迟和循环预算要分别控制。

### rerank 能修复漏召回吗？

不能，它只在给定候选里重排。应先检查候选 Recall@K，再优化排序。

### 文档删除后怎么避免继续被引用？

更新索引并在取回时核对有效版本和权限；缓存按文档版本失效。删除原文而不清理索引和缓存仍可能泄露内容。

### TopK 越大越好吗？

候选集更大可能提高召回，但进入上下文的材料过多会增加成本和噪声。召回 K、重排 K 和最终证据数量是不同参数。
