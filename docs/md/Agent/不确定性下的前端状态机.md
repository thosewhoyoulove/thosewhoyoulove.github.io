# 不确定性下的前端状态机

## 面试定位

JD 强调：流式、非结构化、不确定数据下仍要 **流畅且确定的体验**。面试官想听你有没有把 Agent 运行建模成 **可推导的状态机**，而不是一堆布尔值和临时 `useState`。

## 面试回答

可以这样答：

> 我会把一次 Agent 运行抽象成 Run：有 id、状态（idle/running/awaiting_user/succeeded/failed/cancelled）、当前步骤和关联的消息/UI blocks。所有 SSE 事件都是对 Run 的命令，经 reducer 纯函数更新，UI 只订阅快照。不确定数据用三态表达：unknown（未到达）、partial（已有片段）、final（校验通过）。冲突时以服务端事件序号为准，本地乐观更新可回滚。用户取消、超时、工具失败都有显式迁移，避免“转圈但不可解释”。这样模型输出可以随机，但界面状态迁移是确定、可测、可回放的。

一句话总结：

> 不确定的是模型内容；确定的是 Run 状态机与事件归约。

---

## 核心原理

```text
用户意图 / 主动推送
  → 创建 Run
  → 事件流：text / ui_block / tool / ask_user / error / done
  → reducer(run, event) → nextRun
  → 视图按 run.status 与 blocks 渲染
```

```ts
type RunStatus =
  | 'idle'
  | 'running'
  | 'awaiting_user'
  | 'succeeded'
  | 'failed'
  | 'cancelled'

type Field<T> =
  | { kind: 'unknown' }
  | { kind: 'partial'; value: T }
  | { kind: 'final'; value: T }
```

---

## 1. 为什么要用状态机

| 没有状态机 | 有状态机 |
| --- | --- |
| 多个 `isLoading` 互相打架 | 同一时刻一个主状态 |
| 取消后仍写入旧流 | 事件带 runId，过期事件丢弃 |
| 无法复现 bug | 事件日志可回放 |
| 不确定字段用 `any`/`null` 混用 | `unknown/partial/final` 语义清晰 |

**要点**：先画状态迁移图，再写组件。

---

## 2. 关键迁移与不变式

典型迁移：

```text
idle → running（用户发送或 Agent 主动发起）
running → awaiting_user（HITL / 澄清问题）
awaiting_user → running（用户提交）
running → succeeded | failed | cancelled
```

不变式（面试可背）：

1. 非 `running/awaiting_user` 时不接受该 run 的 delta（或仅接受迟到的 `done` 校正）。
2. `cancelled` 后本地 buffer 冻结，新事件若 runId 匹配也丢弃（除非服务端声明 resume）。
3. `partial` 不得驱动不可逆业务写（下单、打款）；只有 `final` + 用户确认可以。

---

## 3. 与流式、生成式 UI 的衔接

- 文本：`partial` 字符串 append，`final` 可再 normalize。
- UI block：同一 `blockId` patch；`status` 从 partial → ready。
- 工具：独立子状态机挂在 run 下，见工具展示文。

**场景（示例）**：商家验证 Agent 先流式给出“疑似风险点”partial 列表，校验完再变 final；在 partial 阶段“一键冻结店铺”按钮禁用，避免基于半成品决策。

**验证**：属性测试式用例（乱序事件、重复 seq、取消后迟到包）；Storybook 回放失败 run。

## 高频追问

### 乐观更新还能做吗？

能，但要绑定 `expectedSeq` 或临时 clientId；服务端权威事件到达后 reconcile，冲突时回滚并提示。

### 多会话怎么隔离？

每个 session 独立 run 队列与 AbortController；切会话不共享 reducer 状态。

### 和 Redux/Zustand 什么关系？

状态机是领域模型；Redux/Zustand 只是存放 run 快照的容器。关键是事件归约是否纯、是否可回放。
