# 可观测性与 Debug 体验

## 面试定位

Agent 难排障：链路跨前端、BFF、模型、工具。面试官想听你是否设计过**requestId、时延指标、开发者面板**，以及如何把一次失败对话复现出来。

## 面试回答

可以这样答：

> Agent 可观测性要把一次 Run 看成分布式 Trace：前端请求、排队、检索、模型调用、每个工具、人工审批和流式渲染分别是 span，用 traceId 贯穿，runId 表示业务执行，requestId 表示一次网络尝试。TTFT 还要拆成排队、首字节、模型首 token 和前端首次绘制，否则只看到“慢”却不知道慢在哪。除成功率和时延，还要记录 token/成本、工具循环次数、断线恢复、审批等待和取消后仍执行。复现依靠版本化输入、事件日志和脱敏后的状态快照，不记录模型隐藏推理过程。日志按敏感级别采样和限时留存，Debug 面板默认对客关闭。最终目标是拿一个 runId，就能定位故障 span、关联 Eval 结果并安全回放。

一句话总结：

> Agent 可观测 = 统一 runId + 关键路径埋点 + 可开关的事件级 Debug。

---

## 核心原理

```text
runId / requestId
  → 前端事件：send / first_token / tool_* / done / error / cancel
  → 日志与指标系统
  → Debug 面板（可选）回放 event 列表
  → 支持与客服/研发对齐同一 ID
```

---

## 1. 必打的指标

| 指标 | 含义 |
| --- | --- |
| TTFT 分解 | 排队、网关、模型首 token、首次绘制分别耗时 |
| 端到端时延 | 完整回答耗时 |
| 取消率 | 是否过慢或答非所问 |
| 工具失败率 | 集成与权限问题 |
| 解析失败率 | 结构化输出不稳 |
| 重试成功率 | 恢复能力 |
| Token / 成本 | 单 Run 与各模型调用的资源消耗 |
| 工具步数 / 重复调用 | 发现失控循环与低效规划 |

用户侧错误文案应带短码，例如 `STREAM_TIMEOUT`，方便检索日志。

---

## 2. 开发者面板设计

适合内网或 `?debug=1`：

- 原始 SSE/事件列表（可过滤）
- 模型 id、温度、usage tokens
- 每个 tool 的耗时与状态
- 检索、模型、工具、审批的 Trace 瀑布图
- Prompt/模型/索引/工具 schema 与前端协议版本
- 一键复制“复现包”（runId + 脱敏消息）

对客环境默认关闭；展示前再次脱敏。

不要为了“可复现”记录原始密钥、完整 PII 或模型的隐藏推理文本。通常保留结构化事件、工具摘要、版本号、usage 和允许审计的输入输出即可；原文是否采集由数据分级、采样和留存策略决定。

---

## 3. 与产品 Debug 模式的差异

| 场景 | 目标 |
| --- | --- |
| 对客聊天失败 | 可重试、可反馈、少暴露内部 |
| 研发排障面板 | 事件级真相、对齐后端 trace |
| IDE Agent Debug | 更偏代码变更 diff、终端输出 |

**场景（示例）**：官网 AI 助手在内网开启 Debug，定位“首包 8 秒”为网关缓冲而非模型慢；关闭缓冲后首 token 降到亚秒级。

**验证**：故障注入（工具 500、流中断）；确认 ID 贯穿前后端；大盘有告警阈值。

## 高频追问

### 为什么必须有 runId？

没有统一 ID，前端、BFF、模型网关的日志对不上，只能靠时间戳猜，Agent 多步调用时几乎不可查。

### 前端埋点会不会太重？

只打关键路径与采样即可；事件内容避免明文密钥。面板数据可按需拉取，不必全量常驻内存。

### 如何复现一次工具审批失败？

保存 awaiting_approval 时的参数快照与用户动作；用同一 mock 事件流在 Storybook/E2E 回放。
