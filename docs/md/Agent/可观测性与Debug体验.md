# 可观测性与 Debug 体验

## 面试定位

Agent 难排障：链路跨前端、BFF、模型、工具。面试官想听你是否设计过**requestId、时延指标、开发者面板**，以及如何把一次失败对话复现出来。

## 面试回答

可以这样答：

> 可观测性要同时服务用户与研发。对用户：失败可复制、有错误码、能重试。对研发：每次 run 有 requestId/traceId，前端上报首 token 时间、完整回复时间、取消率、工具失败率；Debug 面板可查看原始事件流、模型名、usage、工具入参出参（脱敏后）。复现时用同一 session 快照和事件序，而不是只靠截图。和 IDE 类 Debug 模式不同，对客产品默认隐藏内部细节，对内或开了调试开关再展示。验证靠埋点大盘和一次真实故障演练：能否在 5 分钟内定位是网关缓冲、模型超时还是工具权限问题。

一句话总结：

> Agent 可观测 = 统一 runId + 关键路径埋点 + 可开关的事件级 Debug。

---

## 核心原理

```text
runId / requestId
  → 前端事件：send / first_token / tool_* / done / error / cancel
  → 日志与指标系统
  → Debug 面板（可选）回放 event 列表
  → 支持与客服/研发对齐同一 ID
```

---

## 1. 必打的指标

| 指标 | 含义 |
| --- | --- |
| 首 token 时延 | 体感响应速度 |
| 端到端时延 | 完整回答耗时 |
| 取消率 | 是否过慢或答非所问 |
| 工具失败率 | 集成与权限问题 |
| 解析失败率 | 结构化输出不稳 |
| 重试成功率 | 恢复能力 |

用户侧错误文案应带短码，例如 `STREAM_TIMEOUT`，方便检索日志。

---

## 2. 开发者面板设计

适合内网或 `?debug=1`：

- 原始 SSE/事件列表（可过滤）
- 模型 id、温度、usage tokens
- 每个 tool 的耗时与状态
- 一键复制“复现包”（runId + 脱敏消息）

对客环境默认关闭；展示前再次脱敏。

---

## 3. 与产品 Debug 模式的差异

| 场景 | 目标 |
| --- | --- |
| 对客聊天失败 | 可重试、可反馈、少暴露内部 |
| 研发排障面板 | 事件级真相、对齐后端 trace |
| IDE Agent Debug | 更偏代码变更 diff、终端输出 |

**场景（示例）**：官网 AI 助手在内网开启 Debug，定位“首包 8 秒”为网关缓冲而非模型慢；关闭缓冲后首 token 降到亚秒级。

**验证**：故障注入（工具 500、流中断）；确认 ID 贯穿前后端；大盘有告警阈值。

## 高频追问

### 为什么必须有 runId？

没有统一 ID，前端、BFF、模型网关的日志对不上，只能靠时间戳猜，Agent 多步调用时几乎不可查。

### 前端埋点会不会太重？

只打关键路径与采样即可；事件内容避免明文密钥。面板数据可按需拉取，不必全量常驻内存。

### 如何复现一次工具审批失败？

保存 awaiting_approval 时的参数快照与用户动作；用同一 mock 事件流在 Storybook/E2E 回放。
