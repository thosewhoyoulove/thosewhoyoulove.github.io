# 工具调用与结果展示

## 面试定位

有 Agent 就会有工具调用 UI。面试官想听：**状态机、参数/结果展示、Human-in-the-loop**，以及和纯文本气泡的差异。

## 面试回答

可以这样答：

> 工具调用不能当普通 Markdown 渲染。我会为每个 tool call 建独立 UI 块，状态至少包括 pending、running、success、error、cancelled。参数默认折叠，提供 JSON 高亮与复制；大结果分页、截断或下载，避免撑爆会话。对写操作、删除、对外发送这类高风险工具，走 Human-in-the-loop：展示影响面，用户 approve / reject / edit 参数后再执行。流式场景里 tool 事件和文本 delta 会交错，前端按 event 路由到对应消息块。验证看：拒绝后是否绝不执行、超时是否可重试、失败信息是否可行动。

一句话总结：

> 工具 UI = 明确状态机 + 可折叠细节 + 高风险人工确认。

---

## 核心原理

```text
text_delta → 更新助手文本
tool_call_start → 插入工具卡片（running）
tool_call_args → 填充/修正参数
（可选）等待用户 approve
tool_result → success/error + 结果摘要
继续 text_delta 或下一轮 tool
```

---

## 1. 展示态设计

| 状态 | 用户感知 | 交互 |
| --- | --- | --- |
| pending / running | 正在调用某某工具 | 可取消（若产品允许） |
| success | 成功摘要 | 展开原始结果 |
| error | 原因 + 建议 | 重试 / 改参数 |
| cancelled | 已取消 | 重新发起 |

参数与结果：

- 默认一行摘要：`查询订单 orderId=…`
- 展开后只读 JSON；超长截断并提供下载
- 密钥、Token、手机号在展示层脱敏

**要点**：先让用户看懂“Agent 在干什么”，再给高级用户看原始载荷。

---

## 2. Human-in-the-loop

适用：

- 变更云资源、删除数据、发送邮件/短信
- 费用相关、不可逆操作
- 企业合规要求人工审计的步骤

流程：

```text
模型提议 tool call
  → UI 进入 awaiting_approval
  → 用户 approve / reject / edit
  → 仅 approve 后运行时执行
  → 结果回写上下文
```

注意：确认框要展示**资源 ID、影响范围、操作者**；不能只有“是否继续？”这种空确认。

---

## 3. 与消息列表集成

- 工具块可内嵌在 assistant 消息中，或作为 `role: tool` 的独立气泡。
- 同一 run 内多个工具并行时，用 `toolCallId` 对齐，避免结果张冠李戴。
- 失败后模型若自动换策略，UI 应保留失败卡片，形成可追溯时间线。

**场景（示例）**：内部运营 Agent 调用“发放优惠券”，前端展示券批次与人数，运营确认后执行；拒绝则向模型回传 rejected，由模型改口播报。

**验证**：自动化测试锁定“未 approve 不发执行请求”；埋点统计人工拒绝率与误操作率。

## 高频追问

### 为什么不把工具结果全部喂给用户当最终答案？

工具结果是中间证据；最终答复应由模型组织，或产品用确定性模板渲染。同时要防止把内部错误栈直接暴露给对客用户。

### 并行工具调用怎么展示？

多卡片并排或列表，各自独立进度；全部完成后再继续后续文本，或按返回顺序增量更新。

### 和 MCP 工具列表 UI 的关系？

设置页展示已连接 Server、可用 Tool、权限开关；会话内展示当次调用。概念见 [MCP 与工具调用概念](/md/Agent/MCP与工具调用概念.md)。
