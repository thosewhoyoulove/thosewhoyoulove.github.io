# LLM 与 Prompt Engineering

## 面试定位

这题考察你是否真正理解大模型，而不是只会说“调一下 ChatGPT”。面试官想听：**模型能力边界、上下文窗口、幻觉、Prompt 结构，以及前端如何消费和约束模型输出**。

## 面试回答

可以这样答：

> LLM 是基于上下文预测 token 的概率模型，不是事实数据库，也不是权限系统。Prompt Engineering 的价值不是“套万能咒语”，而是把目标、指令优先级、输入数据、约束、示例和输出契约组织清楚，并配合检索、工具和 Eval 形成完整系统。结构化输出或 JSON Schema 能约束语法，却不能保证字段在业务上真实、安全、有权限，因此 BFF 仍要做语义校验和鉴权。系统指令与外部内容分层能减少混淆，但不能彻底消灭 Prompt Injection；来自用户、网页、RAG 和工具的文本都按不可信数据处理。前端只渲染通过协议校验的结果，失败时安全降级，并把 Prompt、模型、工具 schema 与评测集一起版本化。

一句话总结：

> LLM 是有边界的生成器；Prompt Engineering = 把任务、约束、格式讲清楚，并让前端可校验、可降级。

---

## 核心原理

把一次模型调用看成“输入上下文 → 生成续写 → 解析消费”：

```text
System / 开发者约束
  + 对话历史（受窗口裁剪）
  + 当前用户输入 / 工具结果
  → LLM 生成 token 流
  → 前端/BFF 解析文本、JSON、工具调用
  → 校验、渲染或进入下一轮 Agent 循环
```

## 1. LLM 能力与边界

你需要能口述这些边界：

| 维度 | 含义 | 产品影响 |
| --- | --- | --- |
| 上下文窗口 | 一次请求能塞进的 token 上限 | 历史过长要摘要/截断，否则报错或静默丢上下文 |
| 幻觉 | 看似合理但事实错误 | 关键结论要引用检索/工具结果，不能只信模型 |
| 非确定性 | 同输入可能不同输出 | 评测用固定参数；UI 要允许重试 |
| 知识截止 | 训练数据有时效 | 实时信息走检索/API，不硬背模型记忆 |
| 结构化能力 | 可约束输出 schema，但不保证业务事实正确 | 还要做语义校验、鉴权与失败降级 |

**要点**：面试里说“模型很强”不够，要说清什么场景必须接工具、检索或人工确认。

## 2. Prompt 的基本结构

一个可维护的 Prompt 通常包含：

1. **角色与目标**：你是谁、要完成什么。
2. **硬约束**：不能做什么、安全与合规边界。
3. **输出格式**：纯文本 / Markdown / JSON / 分步骤。
4. **少样本示例**：1～3 个正例，必要时加反例。
5. **当前任务**：用户输入与必要上下文。

```text
[System]
你是云计算控制台助手。只基于给定文档回答。
不知道就说不知道。输出 Markdown。

[Examples]
用户：如何开通某某服务？
助手：1. 进入控制台… 2. …

[User]
当前产品文档片段：...
用户问题：...
```

前端/BFF 实践建议：

- 系统提示与用户/检索内容分离，明确指令与数据边界；这能降低混淆，但不是 Prompt Injection 的安全边界。
- 对 JSON 输出约定字段，解析失败时展示“生成格式异常，可重试”，不要把半截 JSON 当业务数据。
- 对通过 schema 的结果继续校验资源是否存在、金额是否合理、用户是否有权操作；“格式正确”不等于“可以执行”。

**要点**：Prompt 是产品契约的一部分，应版本化，而不是散落在组件字符串里。

## 3. 前端如何消费模型输出

常见消费形态：

| 输出类型 | 前端做法 |
| --- | --- |
| 流式 Markdown | 增量渲染，处理未闭合代码块 |
| 结构化 JSON | 校验后驱动表单/卡片，失败重试 |
| 工具调用意图 | 进入 Tool UI 状态机，而不是当纯文本 |
| 引用/溯源 | 渲染 citation，可跳到来源 |

和参数相关的产品直觉（具体默认值以所用模型文档为准）：

- **temperature**：越高越发散；需要稳定格式时偏低。
- **max tokens**：限制单次回复长度，影响成本与截断体验。
- **停止条件 / 工具循环上限**：防止 Agent 空转。

**场景（示例）**：对客 AI 文档助手里，前端只渲染通过校验的回答卡片；若解析失败，展示重试并上报 `parse_error`，而不是把原始乱码塞进 DOM。

**验证**：评测集正确率、格式失败率、用户重试率、首 token 时延。

## 高频追问

### Prompt Engineering 和微调有什么区别？

Prompt 是推理时约束行为，成本低、迭代快；微调改模型权重，适合稳定的领域风格或格式，但成本和数据门槛更高。多数产品前端岗位先把 Prompt、检索和工具调用做好。

### 为什么不能把用户输入直接拼进系统提示？

用户可能注入“忽略以上规则”。应分层传递，并对高权限操作做服务端鉴权，而不是只靠 Prompt 自律。

### 前端为什么还要关心 Token？

Token 影响费用、延迟和是否触发截断。产品上要把“上下文将满/已截断”变成可理解提示，详见 [上下文与 Token 体验](/md/Agent/上下文与Token体验.md)。
