# Skills、MCP 与 A2A 的区别

## 面试回答

> 我会从任务方法、能力接入和 Agent 协作三个层面区分它们。
>
> 首先，**Skill 保存的是完成一类任务的方法与材料**。例如代码审查 Skill 可以包含审查步骤、脚本和参考规范。宿主先通过名称与描述发现它，需要执行时再加载正文。Skill 是任务知识包，不是一个天然运行着的远程服务。
>
> 第二，**MCP 规范宿主怎样发现和使用外部能力**。Host 是承载 Agent 的应用，Client 负责与 Server 通信，Server 暴露工具、资源和提示模板。Skill 可以告诉 Agent“先查日志再诊断”，实际查日志则可以调用 MCP 工具。模型产生调用意图，宿主负责校验和执行。
>
> 第三，**A2A 关注独立 Agent 之间如何交接任务**。调用方可以发现对方的能力，提交任务，跟踪状态并接收产物，而不必知道对方内部用了哪个模型或工具。它更适合跨系统的 Agent 协作；同一进程里的多 Agent 并不必然需要 A2A。
>
> **三者可以组合，但不等于同一层协议**。Skill 给方法，MCP 接能力，A2A 交接任务；权限和验收仍由应用落实。

**一句话总结：** Skill 指导怎么做 → MCP 接入可用工具与数据 → A2A 委派给另一个 Agent。

## 核心原理

### 同一个任务为什么会涉及三个概念

设想用户让售后助手诊断设备报错。它加载“设备诊断” Skill，按规范收集型号和错误码；通过 MCP 查询日志；发现涉及保修判断后，把该子任务交给另一个组织维护的保修 Agent；最后合并结论。

```text
用户授权的诊断目标
  → 加载诊断 Skill：确定步骤和验收条件
  → MCP 日志工具：读取当前设备证据
  → A2A 保修 Agent：处理独立子任务
  → 接收状态与产物，核对来源
  → 汇总诊断结果
```

Skill 的输入是任务描述及已有上下文，输出是指导当前 Agent 行动的材料。MCP 让应用知道某项能力有哪些参数和返回值。A2A 则让应用和另一个自主处理任务的主体交互。区分点是交互契约与责任边界，不是“工具一定简单、Agent 一定复杂”：一个 MCP 工具也完全可以在内部运行复杂 Agent。

| 维度 | Skill | MCP | A2A |
| --- | --- | --- | --- |
| 主要对象 | 任务知识与资源包 | Host / Client / Server | 调用方与远端 Agent |
| 核心问题 | 这类任务怎么做 | 能力如何发现与调用 | 任务如何委派和跟踪 |
| 常见载体 | SKILL.md、脚本、参考资料 | 协议消息、工具和资源描述 | Agent Card、任务状态、产物 |
| 谁负责执行 | 加载它的宿主与运行时 | Server 执行能力，Host 管控调用 | 接收任务的 Agent 自行处理内部步骤 |
| 是否自动授权 | 否 | 否 | 否 |

Agent Card 是对外发布的能力说明，供调用方发现能做什么以及如何连接。任务状态说明处理中、等待补充还是已结束；产物是任务输出，如诊断报告。具体字段及传输方式应按部署采用的 A2A 版本核对，不能把某个 SDK 的对象结构当成所有实现。

### Skill 为什么要分层加载

假设有 100 个 Skill，每个正文 2,000 Token。全部塞入会先花掉约 200,000 Token，还未包含用户任务和工具结果。大多数 Skill 与当前问题无关，却增加上下文成本并干扰选择。

```text
发现阶段：只读名称、描述等元数据
  → 匹配阶段：按任务选择候选 Skill
  → 激活阶段：读取选中 Skill 的 SKILL.md
  → 执行阶段：按需读取 references、运行 scripts
  → 记录版本与结果，释放无关大段材料
```

这是渐进披露：先提供足够发现能力的少量信息，再提供执行所需细节。它减少无关上下文，代价是多一次发现或读取；缓存可以降低重复读取成本，但权限或版本变化后要失效。Agent Skills 的目录与元数据格式参见 [官方规范](https://agentskills.io/specification)。宿主的路由与缓存方式则是具体工程选择，并非规范保证模型自动准确选择。

### 多个 Skill 怎样组合

以“检索证据 → 写报告 → 事实校验”为例，组合应传递明确产物，而不是把三份长提示词直接拼接。检索步骤输出带来源的片段集合；写作步骤输出引用片段 ID 的草稿；校验步骤输出结论与证据是否一致的报告。

| 阶段 | 读取什么 | 输出什么 | 未满足条件时 |
| --- | --- | --- | --- |
| 检索 | 问题、用户权限、检索 Skill | 带来源 ID 的证据集合 | 无证据则询问或降级 |
| 写作 | 证据、写作 Skill | 草稿与引用关系 | 不足部分明确标记 |
| 校验 | 草稿、证据、校验 Skill | 通过项和修订项 | 返回写作阶段有限重试 |

顺序依赖必须串行；互不依赖的资料读取可以并行，但需要限制并发与汇合条件。共享状态保存任务 ID、已选版本、产物引用和错误信息。加载 Skill 后也不能扩大用户权限；冲突时由宿主指令优先级裁决，无法兼容的任务规则应显式终止或请求澄清。

### A2A 交接任务时怎样避免失控

一次“提交成功”只证明对方接收了请求，不证明任务完成。调用方应区分提交、运行、等待输入、终态，并验证产物是否满足验收条件。网络超时后也不能盲目重提写任务：应保存任务标识，先查询状态，再结合业务幂等键决定是否重试。这些是可靠性设计，不由“用了协议”自动获得。

MCP 的 Host / Client / Server 关系依据 [架构文档](https://modelcontextprotocol.io/docs/learn/architecture)；A2A 的任务协作定位依据 [官方概述](https://a2a-protocol.org/latest/topics/what-is-a2a/)。本文讲概念分工，接入时需固定协议版本。

## 常见误区

### ❌ Skill 就是一个 MCP Tool

✅ Skill 可以指导如何使用工具，也可以包含脚本，但其任务知识包与工具调用协议的职责不同。为什么：读到操作手册并不等于外部动作已经执行。

### ❌ 有多个 Agent 就必须使用 A2A

✅ 内部模块可以直接通过函数或队列协作。为什么：A2A 的价值在于独立 Agent 的互操作，引入协议也增加运维和鉴权成本。

### ❌ Skill 描述写了允许删除，就能删除

✅ 执行权限必须来自用户授权和运行时校验。为什么：加载的内容可以被修改，不能成为权限真相来源。

## 高频追问

### Skill 是谁加载的？

宿主或运行时执行读取；模型可以建议使用某个 Skill，但模型并不凭空拥有文件内容。

### Skill 的脚本是否必须原样全文放进上下文？

不必。宿主可以执行脚本，只向模型返回必要结果；需要修改或理解脚本时再读取源码。

### A2A 与 MCP 能互相封装吗？

可以，但需要明确任务生命周期如何映射为工具结果、如何取消和如何鉴权；封装不意味着两者语义相同。

### 多 Skill 循环修订何时结束？

预先定义质量门槛和最大轮数、时间、Token 预算。到预算仍不通过时返回失败原因和待处理项。
