# AI 输出 Eval 与质量体系

## 面试定位

JD 要求面对模型随机性，建设 **针对 AI 输出的自动化评测（Eval）**。前端/全栈候选人要能讲清：Eval 评什么、如何进 CI、失败样本如何回到产品与 Prompt/协议迭代；并与性能可观测区分开。

## 面试回答

可以这样答：

> 可观测性回答“系统是否正常运行”，Eval 回答“这次输出和整条执行轨迹是否完成了任务”。我会按确定性分层：schema、状态迁移、工具参数和权限用规则测试；有标准答案的关键字段与黄金集比对；开放生成再用人工标注或经过校准的 LLM judge。Agent 不能只评最终文案，还要评工具选型、参数、调用顺序、是否越权、是否按预算终止。数据集按正常、边界、对抗、语言和客户权限切片，记录模型、Prompt、检索索引、工具 schema 版本。CI 跑快速契约集，预发跑完整回归，线上用灰度、抽样和用户反馈发现分布漂移。门禁比较候选版本与基线及置信区间，而不是迷信一次平均分。

一句话总结：

> Eval = 契约检查 + 黄金任务集 + 线上反馈闭环；和延迟监控一起才叫质量体系。

---

## 核心原理

```text
变更（Prompt / 模型 / 协议 / 检索）
  → 跑 Eval Suite
  → 契约分 / 任务分 / 安全分
  → 不通过：阻断或灰度
  → 通过：发布
  → 线上反馈与抽样 → 回灌黄金集
```

| 层 | 测什么 | 典型失败 |
| --- | --- | --- |
| 契约 | schema、citation 结构、禁用 HTML | 解析失败、未知 UI type |
| 任务 | 黄金问答/寻源用例 | 选错供应商、编造交期 |
| 安全 | 越权工具、泄密话术 | 未 HITL 执行写操作 |
| 体验代理 | 空检索强答、无限循环步数 | 差体验但未报错 |
| 轨迹 | 工具选择、参数、顺序、终止条件 | 答案碰巧正确但执行越权或浪费 |

## 1. 和可观测性怎么分工

| 可观测 | Eval |
| --- | --- |
| 首 token、错误率、工具失败 | 答案对不对、协议合不合法 |
| 排障用 | 防质量回退用 |
| 实时大盘 | 集批跑 + 抽样 |

两者用同一 `runId` 关联：先看系统是否失败，再看成功 run 的质量分。详见 [可观测性与 Debug 体验](/md/Agent/可观测性与Debug体验.md)。

---

## 2. 前端在 Eval 里做什么

1. **稳定序列化**：把最终消息、UI blocks、工具轨迹导出为评测快照（脱敏）。
2. **契约测试**：Renderer 对非法 block 必须降级——单测锁住。
3. **反馈组件**：点踩必选原因，带 runId 回传。
4. **Debug 入口**：内网可打开“本 run 评测标签”（仅员工）。

自动化不一定全在浏览器跑；前端保证 **产物可评、反馈可追**。

---

## 3. 随机性下的发布策略

- 固定 Prompt、模型版本、工具 schema、知识库快照与采样参数，尽量减少无关变量；即便平台支持 seed，也不能把生成当成严格确定。
- 核心 B2B 动作（验商结论、自动联系）提高门禁阈值。
- 模型或 Prompt 变更走灰度，盯 Eval 分与投诉率。
- 评测集做版本管理并防止污染；新增线上失败样本时保留独立 holdout，避免只对公开题“刷分”。

LLM-as-judge 适合规模化评估开放回答，但 Judge 自身也有位置偏差、措辞偏好和知识盲区。要用人工样本校准，与规则指标组合，并保存 rubric、Judge 模型和版本，不能只存一个总分。

**场景（示例）**：生成式供应商对比卡升级协议 v2；CI 跑 200 条寻源黄金集 + schema 校验；citation 缺失率高于阈值则禁止全量。

**验证**：门禁真实挡住一次坏变更；线上点踩能在一周内变成新用例。

## 高频追问

### 没有标准答案的开放生成怎么评？

用分级：契约必须自动过；语义用 LLM-as-judge（需抽检校准）或人工抽检；关键槽位（ID、价格字段）仍要规则比对。

### Eval 会不会拖慢迭代？

分层：每次提交跑快检契约；每日/预发跑全量任务集。不要所有变更都等数小时全量。

### 前端为什么要懂 Eval？

因为很多“质量问题”表现在 UI 协议与交互路径上；不会评测就只能凭感觉改样式，扛不住随机性。
