# RAG 与检索增强体验

## 面试定位

JD 要求对 Embedding / RAG 有基本认知。前端岗不必会调向量库，但要讲清：**RAG 解决幻觉与私有知识问题，以及检索过程如何做成可理解、可降级的体验**（含 citation、空结果、多模态检索）。

## 面试回答

可以这样答：

> RAG 是先检索再生成：把问题变成向量或关键词去查私有知识库，把相关片段塞进上下文，再让 LLM 基于证据回答，从而降低胡编并支持业务文档更新。Embedding 把文本或图片映射到向量空间，用来做相似度召回。前端要展示检索中/命中数/来源卡片，回答必须可点回片段；检索为空时明确降级（仅通用知识或拒绝回答），不能装作很确定。多模态匹配场景下，还要展示图文对齐的证据，而不是只给一句结论。验证看：有引用回答占比、用户点击来源率、空检索时的错误承诺率。

一句话总结：

> RAG 体验 = 可见的检索过程 + 可点击的证据 + 空结果诚实降级。

## 核心原理

```text
用户问题 / 图片
  → 检索（向量 / 关键词 / 混合）
  → TopK 片段（含元数据）
  → 组装 Prompt（系统约束 + 证据 + 问题）
  → LLM 生成（要求引用）
  → 前端渲染回答 + citation
```

认知层（面试够用）：

| 概念 | 一句话 |
| --- | --- |
| Embedding | 把内容变成向量，相近语义距离更近 |
| 检索 | 按相似度或关键词取证据 |
| 增强生成 | 生成时以证据为条件，减少瞎编 |

细节实现（分片、rerank、索引）偏后端；前端聚焦状态与证据 UX。

## 1. 前端必须暴露的状态

| 状态 | 用户感知 |
| --- | --- |
| retrieving | 正在查知识库/商品库 |
| hits | 命中 N 条，可预览 |
| generating | 基于证据生成中 |
| empty | 未找到依据，说明下一步 |
| stale | 索引可能落后，提示更新时间 |

反模式：检索失败仍输出斩钉截铁的业务结论。

---

## 2. Citation 与信任设计

```text
回答句子
  → [1][2] 角标
  → 侧栏/底部来源卡（标题、片段、链接、更新时间）
```

要求：

- 无 citation 的关键数字（价格、MOQ、合规结论）视觉降权或标“未验证”
- 来源打不开时保留片段快照
- 工具结果与 RAG 片段在 UI 上区分开（“实时 API” vs “知识库”）

安全上按不可信内容渲染，见 [安全与合规（前端）](/md/Agent/安全与合规（前端）.md)。

## 3. B2B / 多模态场景要点

- **寻源**：检索供应商与历史成交，对比卡带证据字段。
- **多模态匹配**：以图搜款，展示相似图 + 相似度/属性差；生成解释必须锚定到匹配特征。
- **商家验证**：政策与案例库 RAG + 人工确认，避免自动定性。

**场景（示例）**：用户上传产品图问“哪些供应商能做类似款”；UI 先出检索中，再出匹配画廊，最后生成“推荐理由”并引用具体商品卡。

**验证**：离线评测集（见 Eval 文）+ 线上 citation 点击率；抽检无依据却给确定答案的比例。

## 高频追问

### RAG 能完全消灭幻觉吗？

不能。检索错、片段不全、模型不遵守引用都会幻觉。产品上要降级策略与人工确认，而不是承诺“绝对正确”。

### 前端要不要自己算 Embedding？

一般不用。浏览器算向量成本高且模型难更新；上传内容由服务端嵌入。前端负责进度与失败态。

### 和长上下文直接塞文档有何差别？

长上下文贵且有窗口上限；RAG 按需取 TopK，更适合大知识库。也可混合：短文档全量，长库检索。
