# RAG 与检索增强体验

## 面试定位

JD 要求对 Embedding / RAG 有基本认知。前端岗不必会调向量库，但要讲清：**RAG 解决幻觉与私有知识问题，以及检索过程如何做成可理解、可降级的体验**（含 citation、空结果、多模态检索）。

## 面试回答

可以这样答：

> RAG 不是简单“向量 TopK 后塞 Prompt”，而是一条可评测的证据链：查询改写，带租户与文档 ACL 的混合召回，rerank，按 Token 预算组装上下文，再生成和校验引用。Embedding 适合语义召回，关键词检索擅长产品型号、错误码等精确词，两者通常融合。权限必须在检索阶段过滤，不能先召回越权片段再靠前端隐藏。前端展示检索、命中、生成和降级状态，并让结论能定位到具体文档版本与片段。还要区分“引用存在”和“引用真的支持结论”：前者是格式正确，后者才是 grounded。离线分别评召回 Recall@K、排序质量和答案忠实度，线上再看来源点击、无依据强答率和用户反馈。

一句话总结：

> RAG 体验 = 可见的检索过程 + 可点击的证据 + 空结果诚实降级。

---

## 核心原理

```text
用户问题 / 图片
  → 查询改写 + ACL / metadata filter
  → 混合召回（向量 + 关键词）
  → rerank 得到 TopK 片段
  → 按 Token 预算组装上下文
  → LLM 生成（要求引用）
  → 引用校验 → 前端渲染回答 + citation
```

认知层（面试够用）：

| 概念 | 一句话 |
| --- | --- |
| Embedding | 把内容变成向量，相近语义距离更近 |
| 检索 | 按相似度或关键词取证据 |
| 增强生成 | 生成时以证据为条件，减少瞎编 |

细节实现（分片、rerank、索引）偏后端；前端聚焦状态与证据 UX。

## 1. 前端必须暴露的状态

| 状态 | 用户感知 |
| --- | --- |
| retrieving | 正在查知识库/商品库 |
| hits | 命中 N 条，可预览 |
| generating | 基于证据生成中 |
| empty | 未找到依据，说明下一步 |
| stale | 索引可能落后，提示更新时间 |

反模式：检索失败仍输出斩钉截铁的业务结论。

## 2. Citation 与信任设计

```text
回答句子
  → [1][2] 角标
  → 侧栏/底部来源卡（标题、片段、链接、更新时间）
```

要求：

- 无 citation 的关键数字（价格、MOQ、合规结论）视觉降权或标“未验证”
- 来源打不开时保留片段快照
- 工具结果与 RAG 片段在 UI 上区分开（“实时 API” vs “知识库”）
- citation 绑定稳定的 `documentId + version + chunkId`，避免文档更新后角标指向错误内容
- 用户无权打开来源时不能泄露标题和片段；应显示权限态或请求访问入口

安全上按不可信内容渲染，见 [安全与合规（前端）](/md/Agent/安全与合规（前端）.md)。

## 3. B2B / 多模态场景要点

- **寻源**：检索供应商与历史成交，对比卡带证据字段。
- **多模态匹配**：以图搜款，展示相似图 + 相似度/属性差；生成解释必须锚定到匹配特征。
- **商家验证**：政策与案例库 RAG + 人工确认，避免自动定性。

**场景（示例）**：用户上传产品图问“哪些供应商能做类似款”；UI 先出检索中，再出匹配画廊，最后生成“推荐理由”并引用具体商品卡。

**验证**：离线评测集（见 Eval 文）+ 线上 citation 点击率；抽检无依据却给确定答案的比例。

评测要拆开看：检索层关注 Recall@K、MRR/nDCG 和 ACL 泄露率；生成层关注答案正确性、对证据的忠实度与引用覆盖率。否则最终回答变差时，很难判断是“没找到”还是“找到了但模型没用对”。

## 高频追问

### RAG 能完全消灭幻觉吗？

不能。检索错、片段不全、模型不遵守引用都会幻觉。产品上要降级策略与人工确认，而不是承诺“绝对正确”。

### 前端要不要自己算 Embedding？

一般不用。浏览器算向量成本高且模型难更新；上传内容由服务端嵌入。前端负责进度与失败态。

### 和长上下文直接塞文档有何差别？

长上下文贵且有窗口上限；RAG 按需取 TopK，更适合大知识库。也可混合：短文档全量，长库检索。
